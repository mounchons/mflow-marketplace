## Claude Code specifics
- mflow hooks inject a briefing at session start and, before a `git commit`, ask once for the STATUS.md entry to go into that commit. Treat the briefing as the current state; never add a STATUS.md update after an answer.
- Commit each finished piece of work without asking, its files added by name (never `git add -A`). Push, merge and deploy only on the user's word, asked once in one line at the end, never as a numbered menu. A change's own branch `feat/<change>`, pushed once its apply is committed, and the `checks/*` branches are the exceptions (below).
- `/opsx:apply` archives the change in the same turn and commits once. "Do X to the end" runs propose, apply and archive in one go, asking only what the user must decide.
- `/opsx:propose`, `/opsx:apply` and `/opsx:archive` are this project's `openspec-propose`, `openspec-apply-change` and `openspec-archive-change` skills, so run the next one yourself; never end a reply telling the user to type one. Run it at once when the user's last message already asked for that step (a change request they said to do, "ทำ", "do it"). Once the user has answered the questions that plan a change (the ones asked before its proposal, a discussion settled in chat), go from its proposal straight into `/opsx:apply` without asking: apply works on the change's own branch `feat/<change>`, so main stays as it is until the user says to merge; when apply has committed, push that branch without asking (`git push -u origin feat/<change>`, never main, no pull request), then ask in one line about the merge as apply says. Otherwise ask in one line whether to go on, such as proposing the next of a proposal's Later changes, and run it on any yes ("ทำ", "ได้", "a"). If the Skill call is refused, read `.claude/skills/<name>/SKILL.md` and follow it. `/mflow:*` commands still run only when the user types them.
- Parallel work asked for in words, without `/mflow:worktree` ("แยก folder", "ทำพร้อมกัน", "เปิดอีก session ทำ X", "ให้ codex ทำ X"): make the change's worktree yourself, following the steps the mflow briefing names under `## Parallel work`, then give the command that starts the tool there. Other `/mflow:*` commands still run only when the user types them.
- When `.mflow/config.json` has `checks`: after each merge into main, put the change into the open checks batch and publish it, as `sync` and `publish` of the checks skill say (the briefing's `## Checks` names its path), without asking: `checks/*` branches and their draft pull requests are pushed on the user's standing word, never main, and a pull request is never merged by Claude. When the user gives a job of the batch to a tool in words ("test2 ให้ agy", "R1 ให้ codex"), follow the `<job> to <tool>` part of that skill without waiting for `/mflow:checks`, and its `Jobs given to another tool` part when the user hands a job to a tool or says the tool is done; Claude running jobs itself (`next`) still waits for the command.
- Not sure which command fits: `/mflow:help`. Big or fuzzy business logic: `/mflow:hotspot`. A fix that changes no behaviour the specs describe: just ask, no change. New or changed behaviour: `/opsx:propose`.
- A rule the user describes in chat, without a command, that crosses screens or is costly if wrong (prices and fees, approval chains, stock and ledgers, a document's states, money or legal impact) and needs more answers or worked examples than this conversation can settle: say once, in one line before the work, that `/mflow:hotspot <idea>` charts it first, with the idea filled in, because mflow commands run only when the user types them. Then carry on with what was asked; it is advice, not a question to wait on. A rule this conversation can settle gets no line.
- Never enter plan mode, even when tasks.md asks for it: an OpenSpec change's design.md and tasks.md are the plan the user approved, and a plan dialog stops an unattended run. Before a task labelled `hotspot` or one touching an aggregate's invariants, reread its part of design.md and the hotspot's rules.md, then write the code.
