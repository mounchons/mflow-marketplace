# ข้อตัดสินใจของแพ็ก api

### API-D01: endpoint อยู่ที่ไหน
- **คำตอบ:** ทุก endpoint อยู่ใต้ `api.route_prefix` (`/api/v1`) ไม่มี endpoint นอก prefix นี้ path ที่ไม่มีอยู่ใต้ prefix ตอบ 404 `NOT_FOUND` ด้วย error body มาตรฐาน ไม่ใช่หน้า HTML ของเว็บ
- **เหตุผล:** proxy ส่งต่อด้วยกฎเดียว แยก API ออกจากหน้าเว็บได้ชัด และมีที่ให้รุ่นถัดไปเมื่อจำเป็น
- **ถ้าผิด:** แก้ยาก — path ของทุก endpoint client ที่สร้างจาก contract และกฎของ proxy เปลี่ยนทั้งหมด
- **ถามเมื่อ:** ไม่ถาม

### API-D02: ตั้งชื่อ resource รูปแบบ JSON และ method อย่างไร
- **คำตอบ:** path เป็นคำนามพหูพจน์แบบ kebab-case ตามด้วย id (`/purchase-orders/<id>`) การกระทำที่ไม่ใช่การบันทึกธรรมดาเป็น `POST .../<id>/<action>` ชื่อฟิลด์ JSON และ query เป็น camelCase ค่า enum ส่งเป็นชื่อ ไม่ใช่ตัวเลข id ส่งเป็น string GET ไม่เปลี่ยนข้อมูล POST สร้างตอบ 201 พร้อมระเบียน PUT บันทึกทั้งฟอร์มตอบ 200 การกระทำตอบ 200 พร้อมระเบียนหลังทำ DELETE ตอบ 204 ไม่ใช้ PATCH
- **เหตุผล:** อ่าน path แล้วรู้ว่าทำอะไร client ที่สร้างจาก contract ได้ชนิดที่อ่านออก และไม่ต้องเถียงเรื่องแก้บางฟิลด์
- **ถ้าผิด:** แก้ยาก — ชื่อฟิลด์และ path เป็นส่วนของ contract ที่ client ทุกตัวใช้
- **ถามเมื่อ:** ไม่ถาม

### API-D03: เปลี่ยน API แบบที่ client เดิมพังได้เมื่อไร
- **คำตอบ:** เว็บกับ API deploy พร้อมกันเสมอ ในรุ่นเดียวกันเพิ่มได้ตลอด (endpoint ใหม่ ฟิลด์ใหม่ ฟิลด์ขาเข้าที่ไม่บังคับ) ส่วนการลบ เปลี่ยนชื่อ เปลี่ยนชนิดของฟิลด์ หรือทำให้ฟิลด์บังคับ ทำได้ใน change เดียวกับที่สร้าง contract และ client ของเว็บใหม่ ไม่เปิด `/api/v2`
- **เหตุผล:** client มีแค่เว็บของโปรเจกต์ที่ออกพร้อมกัน การดูแลสองรุ่นพร้อมกันเป็นภาระที่ไม่มีใครได้ประโยชน์
- **ถ้าผิด:** แก้ทีหลังได้ — เปิดรุ่นใหม่ข้างรุ่นเดิมเมื่อมีผู้เรียกจากภายนอก
- **ถามเมื่อ:** มีระบบอื่นหรือแอปมือถือที่ออกรุ่นแยกจากเว็บเรียก API นี้
- **ตัวเลือกอื่น:** b) การเปลี่ยนที่ทำให้ client พังเปิดรุ่นใหม่ (`/api/v2`) และเก็บรุ่นเดิมไว้จนผู้เรียกย้ายครบ พร้อมประกาศวันปิด c) ห้ามเปลี่ยนแบบพังเลย เพิ่มได้อย่างเดียว

### API-D04: error ตอบหน้าตาอย่างไร
- **คำตอบ:** ทุกคำตอบ 4xx และ 5xx เป็น `application/problem+json` ตาม RFC 9457: `type` `title` `status` ของสถานะ HTTP, `detail` ข้อความสำหรับคน, ส่วนขยาย `code` (UPPER_SNAKE_CASE ไม่เปลี่ยนข้ามรุ่น) และ `requestId` ส่วน `VALIDATION_FAILED` มี `errors` ที่มีทุกฟิลด์ที่ผิดในครั้งเดียว คีย์เป็นชื่อฟิลด์ตามคำขอ (`lines[0].quantity`) ค่าเป็นรายการข้อความ client ตัดสินจาก `status` และ `code` เท่านั้น ไม่อ่านข้อความ ไม่มี stack trace, SQL, ชื่อ exception หรือ path ของไฟล์ในคำตอบ
- **เหตุผล:** มาตรฐานที่ framework และเครื่องมือรู้จัก `code` ให้ client แยกกรณีได้โดยไม่ผูกกับข้อความ และ `requestId` พาไปหา log ได้ทันที
- **ถ้าผิด:** แก้ยาก — ทุกจุดที่เว็บอ่าน error และทุก test ของ API เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### API-D05: ข้อความใน error เป็นภาษาอะไร
- **คำตอบ:** `detail` และข้อความรายฟิลด์เขียนตาม `api.message_language` (ค่าเริ่มต้นคู่ `English · ไทย` แบบเดียวกับป้ายบนจอ) เว็บแสดงข้อความนี้ได้ตรงๆ และใช้ `code` เพื่อเลือกว่าจะทำอะไร ไม่ใช่เพื่อแปล
- **เหตุผล:** กฎตรวจข้อมูลอยู่ที่ server ข้อความจึงควรมาจากที่เดียว ไม่ต้องมีตารางข้อความซ้ำในเว็บ
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนที่มาของข้อความโดยไม่เปลี่ยน `code`
- **ถามเมื่อ:** ผู้ใช้เลือกภาษาของจอเองได้ หรือมีมากกว่าสองภาษา
- **ตัวเลือกอื่น:** b) server เลือกภาษาตาม `Accept-Language` ของแต่ละคำขอ c) server ส่งแค่ `code` และรหัสรายฟิลด์ เว็บถือข้อความทุกภาษาเอง

### API-D06: ใช้สถานะ HTTP อะไรบ้าง
- **คำตอบ:** 400 `VALIDATION_FAILED` ข้อมูลขาเข้าผิดไม่ว่าระเบียนอยู่สถานะไหน (รวม JSON เสียและชนิดผิด) / 401 ไม่มีเซสชันหรือเซสชันหมด / 403 เข้าระบบแล้วแต่ไม่มีสิทธิ์ / 404 `NOT_FOUND` ไม่มีระเบียน ถูกลบ หรืออยู่นอกขอบเขตข้อมูลของผู้เรียก (body เหมือนกัน) / 409 บันทึกจากข้อมูลเก่า หรือสถานะปัจจุบันของระเบียนไม่ยอมให้ทำ (รหัสของกรณีนั้น เช่น `ORDER_CLOSED`) / 413 คำขอใหญ่เกิน / 429 เรียกถี่เกิน / 500 `INTERNAL_ERROR` / 503 ฐานข้อมูลหรือระบบที่คำขอต้องใช้ไม่ตอบ ไม่ใช้ 422
- **เหตุผล:** แยก "กรอกผิด" (แก้ฟอร์ม) จาก "สถานะเปลี่ยน" (โหลดใหม่) ได้จากสถานะเดียว และ 404 ไม่บอกคนนอกขอบเขตว่าระเบียนมีอยู่
- **ถ้าผิด:** แก้ยาก — เว็บและ test ทุกตัวอ่านสถานะเหล่านี้
- **ถามเมื่อ:** ไม่ถาม

### API-D07: กันการบันทึกทับกันบนสายอย่างไร
- **คำตอบ:** ระเบียนที่คนแก้ได้ส่ง `version` ในคำตอบ ทุก PUT การกระทำ และ DELETE ส่ง `version` ที่หน้าจออ่านมากลับมา `version` เก่ากว่าที่เก็บตอบ 409 `<RESOURCE>_CHANGED` (เช่น `ORDER_CHANGED`) และไม่เปลี่ยนอะไร ไม่ส่ง `version` ตอบ 400 บนฟิลด์ `version` บันทึกสำเร็จได้ `version` ใหม่กลับไป การเก็บเลขรุ่นในตารางเป็นกติกาของแพ็ก `audit`
- **เหตุผล:** ใส่ใน body ได้ทั้งฟอร์ม HTML และ JSON และรหัสบอกได้ว่าระเบียนไหนถูกแก้ไปก่อน
- **ถ้าผิด:** แก้ยาก — ทุกคำสั่งเขียนและทุกฟอร์มต้องพา `version` ไปด้วย
- **ถามเมื่อ:** ไม่ถาม

### API-D08: รายการแบ่งหน้า เรียง และค้นอย่างไร
- **คำตอบ:** query `page` (เริ่ม 1) และ `pageSize` (ค่าเริ่ม `api.page_size_default` สูงสุด `api.page_size_max` เกินตอบ 400) คำตอบมี `items` `total` `page` `pageSize` หน้าที่เกินท้ายได้ `items` ว่างพร้อม `total` จริง `sort` เป็นชื่อฟิลด์คั่นด้วยจุลภาค นำหน้า `-` คือมากไปน้อย ใช้ได้เฉพาะฟิลด์ที่รายการประกาศ ทุกลำดับปิดท้ายด้วย id `search` ตัดช่องว่างหัวท้าย ไม่สนตัวพิมพ์ หาแบบมีคำนี้อยู่ในฟิลด์ที่รายการประกาศ ตัวกรองเป็น query ที่มีชื่อ ใช้ร่วมกันแบบ AND
- **เหตุผล:** ทุกจอรายการใช้ component เดียวกันได้ และหน้าไม่ซ้ำหรือข้ามแถวเมื่อค่าที่เรียงเท่ากัน
- **ถ้าผิด:** แก้ยาก — ทุก endpoint รายการและตารางทุกจอ
- **ถามเมื่อ:** ไม่ถาม

### API-D09: วันเวลาบนสายและเขตเวลา
- **คำตอบ:** เวลาส่งเป็น ISO-8601 แบบ UTC (`Z`) รับได้ทุก offset ที่ระบุ ไม่มี offset ตอบ 400 วันที่ไม่มีเวลาส่งเป็น `YYYY-MM-DD` เก็บเวลาเป็น UTC วันที่เป็น date "วันนี้" วันครบกำหนด และตัวกรองช่วงวันที่คิดในเขตเวลา `api.time_zone` ตัวกรอง `from` และ `to` รวมทั้งสองวัน `to` ก่อน `from` ตอบ 400 การจัดรูปแบบให้คนอ่านทำที่เว็บเท่านั้น
- **เหตุผล:** ไม่มีเวลาที่เพี้ยนไปเจ็ดชั่วโมงเพราะเดาเขตเวลา และกฎ "เลยกำหนดหรือยัง" ตอบเหมือนกันทุกที่
- **ถ้าผิด:** แก้ยาก — ข้อมูลที่เก็บผิดเขตเวลาไปแล้วแก้ย้อนยาก
- **ถามเมื่อ:** ผู้ใช้หรือสาขาอยู่ต่างเขตเวลากัน
- **ตัวเลือกอื่น:** b) เขตเวลาต่อสาขาหรือต่อผู้ใช้ เก็บไว้กับระเบียนนั้น และคิด "วันนี้" ตามเขตเวลาของระเบียน

### API-D10: เวลาปัจจุบันมาจากไหน และ test เลื่อนเวลาอย่างไร
- **คำตอบ:** ทุกกฎที่อ่านเวลาปัจจุบันหรือวันนี้อ่านจากนาฬิกาตัวเดียวของระบบ โค้ดธุรกิจไม่อ่านเวลาของเครื่องเอง (architecture test ตรวจ) test แทนนาฬิกาเพื่อตั้งและเลื่อนเวลา ไม่มี endpoint เลื่อนเวลา
- **เหตุผล:** test เรื่องหมดอายุและครบกำหนดได้ผลเหมือนเดิมทุกครั้ง โดยไม่มีทางเปิดให้ใครเลื่อนเวลาของระบบจริง
- **ถ้าผิด:** แก้ทีหลังได้ — ไล่เปลี่ยนจุดที่อ่านเวลาเองมาใช้นาฬิกากลาง
- **ถามเมื่อ:** test แบบ end-to-end ต้องข้ามวันหมดอายุหรือรอรอบของงานตามเวลา
- **ตัวเลือกอื่น:** b) testing control เลื่อนนาฬิกาไปข้างหน้า บอก offset และ reset มีเฉพาะเมื่อโหมด prototype เปิด ไม่อยู่ใน contract และตอบ 404 เมื่อโหมดปิด

### API-D11: health และ readiness
- **คำตอบ:** `<prefix>/health` ตอบ 200 เมื่อ process ยังรับคำขอ ไม่แตะฐานข้อมูล บอก `status` และโหมด prototype `<prefix>/health/ready` ตอบ 200 เมื่อฐานข้อมูลตอบ และ 503 `DATABASE_UNAVAILABLE` เมื่อไม่ตอบ ทั้งสองไม่ต้องเข้าระบบ ไม่ถูกนับในตัวจำกัดอัตรา และไม่บอก connection string ชื่อเครื่อง รหัสผ่าน หรือรุ่นของไลบรารี
- **เหตุผล:** docker และ proxy แยก "process ตาย" (restart) จาก "ยังไม่พร้อม" (รอ) ได้ และคนนอกไม่ได้ข้อมูลของ infra
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มสิ่งที่ readiness ตรวจได้ใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### API-D12: contract ของ API อยู่ที่ไหน
- **คำตอบ:** เอกสาร OpenAPI สร้างจากโค้ดของ API และ commit ไว้ที่ `api.contract_path` test ล้มเมื่อไฟล์ที่ commit ต่างจากที่ API สร้าง ทุก endpoint ประกาศคำตอบสำเร็จและ error ของตัวเอง client ของเว็บที่เรียก API สร้างจากไฟล์นี้ ไม่เขียนเอง testing control ไม่อยู่ใน contract
- **เหตุผล:** เห็นการเปลี่ยน API ใน diff ของ review และเว็บกับ API ไม่มีทางเห็นชนิดข้อมูลไม่ตรงกัน
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม test เทียบไฟล์และสร้าง client ใหม่ได้ทุกเมื่อ
- **ถามเมื่อ:** ไม่ถาม

### API-D13: เปิดหน้าเอกสาร API ที่สภาพแวดล้อมไหน
- **คำตอบ:** Development, Prototype และ Staging เปิดเอกสารที่ `<prefix>/openapi.json` และหน้าอ่านที่ `<prefix>/docs` Production ตอบ 404 ทั้งสอง
- **เหตุผล:** ทีมและผู้ทดสอบของลูกค้าลองเรียกได้ระหว่างพัฒนา ส่วน Production ไม่เปิดรายชื่อ endpoint ให้คนนอก
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งต่อสภาพแวดล้อม
- **ถามเมื่อ:** ระบบภายนอกต้องอ่านเอกสารบน Production หรือ Staging เปิดสู่ internet
- **ตัวเลือกอื่น:** b) Production เปิดเอกสารเฉพาะผู้ที่เข้าระบบแล้ว c) ไม่เปิดหน้าใดนอก Development ใช้ไฟล์ที่ commit อย่างเดียว

### API-D14: log และ request id
- **คำตอบ:** ทุกคำขอมี request id หนึ่งค่า รับจาก `api.request_id_header` ที่เข้ามาเมื่อเป็นตัวอักษร ตัวเลข `.` `_` `-` ไม่เกิน 64 ตัว ไม่อย่างนั้นสร้างใหม่ ส่งกลับใน header เดียวกันทุกคำตอบ ใส่ใน `requestId` ของทุก error และในทุกบรรทัดของ log log เป็น JSON บรรทัดละรายการออก stdout มีเวลา UTC ระดับ ข้อความ request id และ id ของผู้ทำ (ไม่ใช่อีเมลหรือชื่อ) หนึ่งบรรทัดสรุปต่อคำขอ ระดับ Debug เฉพาะ Development
- **เหตุผล:** ผู้ใช้แจ้งรหัสที่เห็นบนจอแล้วหา log ของคำขอนั้นได้ทันที และ log อ่านด้วยเครื่องมือได้โดยไม่ต้อง parse ข้อความ
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มฟิลด์ใน log ได้ แต่ log เก่าที่ไม่มี request id ย้อนหาไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### API-D15: ความลับใน log และคำตอบ
- **คำตอบ:** log ไม่มีค่าของรหัสผ่าน โทเค็น รหัส OTP cookie header `Authorization` CSRF token connection string หรือกุญแจ ค่าเหล่านี้เขียนเป็น `***` ไม่ log body ของคำขอและคำตอบ response model ไม่มีฟิลด์ที่ชื่อมี `password` `secret` `token` หรือ `otp` ยกเว้นชื่อที่อยู่ในรายการยกเว้นจุดเดียวพร้อมเหตุผล architecture test ตรวจ
- **เหตุผล:** log อ่านได้หลายคนและเก็บนาน ความลับที่หลุดลง log หรือคำตอบไปแล้วเรียกคืนไม่ได้
- **ถ้าผิด:** แก้ยาก — ความลับที่รั่วไปแล้วต้องเปลี่ยนทุกตัว
- **ถามเมื่อ:** ไม่ถาม

### API-D16: จำกัดอัตราคำขออย่างไร
- **คำตอบ:** คำขอที่ไม่มีเซสชันจำกัด `api.anonymous_requests_per_minute` ครั้งต่อนาทีต่อที่อยู่ของ client เกินแล้วตอบ 429 `TOO_MANY_REQUESTS` พร้อม `Retry-After` ที่อยู่ของ client อ่านจาก header ของ proxy เฉพาะคำขอที่มาจาก proxy ที่รู้จัก health ไม่ถูกนับ คำขอที่เข้าระบบแล้วไม่ถูกจำกัดด้วยกฎนี้ ส่วนการล็อกเมื่อเข้าผิดซ้ำเป็นของแพ็ก `auth` และนับแยก
- **เหตุผล:** กันการยิงหน้าเข้าระบบ ลืมรหัส และ endpoint สาธารณะ โดยไม่กระทบผู้ใช้ที่ทำงานอยู่
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับค่าหรือเพิ่มกฎใน change ถัดไป
- **ถามเมื่อ:** ผู้ใช้จำนวนมากออก internet ผ่านที่อยู่เดียว หรือพอร์ทัลเปิดสู่ internet และต้องกันผู้ที่เข้าระบบแล้วเรียกถี่
- **ตัวเลือกอื่น:** b) เพิ่มกฎต่อบัญชีสำหรับคำขอที่เข้าระบบแล้วตามค่าที่โปรเจกต์ตั้ง c) ยกเว้นหรือเพิ่มเพดานให้เครือข่ายที่ลูกค้าระบุ

### API-D17: เว็บของ origin อื่นเรียก API ได้ไหม (CORS)
- **คำตอบ:** ไม่ได้ เว็บกับ API อยู่ origin เดียวกันผ่าน proxy API ไม่ส่ง header อนุญาต CORS เมื่อ `api.cors_origins` มีรายการ อนุญาตเฉพาะ origin เหล่านั้นแบบตรงทั้ง scheme host และ port ไม่ใช้ `*` ระหว่างพัฒนาให้ dev server ของเว็บส่งต่อคำขอ API แทนการเปิด CORS
- **เหตุผล:** cookie ของเซสชันไม่ถูกใช้จากเว็บอื่น และไม่มีค่าตั้งที่ลืมปิด
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม origin ในค่าตั้ง
- **ถามเมื่อ:** เว็บกับ API อยู่คนละ host หรือ port ใน Production หรือเว็บของระบบอื่นต้องเรียก API จาก browser
- **ตัวเลือกอื่น:** b) ใส่ origin ที่อนุญาตใน `api.cors_origins` และถือเซสชันแบบ token ตามแพ็ก `auth` โดยเว็บนั้นต้องอยู่ site เดียวกับ API

### API-D18: proxy ข้างหน้าทำอะไร และรับคำขอใหญ่แค่ไหน
- **คำตอบ:** proxy ตัวเดียวให้บริการทุก `{portal}` ส่งทุก path ใต้ prefix ไปที่ API พร้อม host port scheme และที่อยู่ของ client เดิม path ของหน้าที่ไม่มีได้หน้า 404 ของเว็บนั้น คำขอใหญ่เกิน `api.body_max_mb` ตอบ 413 โดยไม่ถึง API และ API ใช้ค่าเดียวกัน นอก Development และ Prototype รับเฉพาะ HTTPS ทุกคำตอบมี `X-Content-Type-Options: nosniff` และหน้าเว็บไม่ถูกฝังในเว็บอื่น ระบบที่มีหลายเว็บแยก host หรือ port ต่อเว็บ
- **เหตุผล:** ขนาดที่ตรงกันทำให้ผลเหมือนกันไม่ว่าใครปฏิเสธ และแยกเว็บต่อ host ทำให้ปิดเว็บหนึ่งจาก internet ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งของ proxy และ API
- **ถามเมื่อ:** ไม่ถาม

### API-D19: ความลับมาจากไหน
- **คำตอบ:** รหัสผ่านฐานข้อมูล SMTP และกุญแจของระบบอื่นมาจาก env หรือที่เก็บความลับของเครื่องเท่านั้น repo มีแค่ `.env.example` ที่เป็นค่าตัวอย่าง ขาดค่าที่ต้องมีแล้ว API หยุดตอน start พร้อมบอกชื่อค่า ไม่บอกค่า นอก Development ถ้าค่าเท่ากับค่าตัวอย่าง API หยุดตอน start
- **เหตุผล:** repo เปิดให้หลายคนอ่าน และค่าตัวอย่างที่หลุดไปถึงเครื่องจริงต้องถูกจับตั้งแต่ start
- **ถ้าผิด:** แก้ยาก — ความลับที่ commit ไปแล้วอยู่ในประวัติ git ต้องเปลี่ยนทุกตัว
- **ถามเมื่อ:** ไม่ถาม

### API-D20: เปิดทั้งชุดอย่างไร และจำกัดหน่วยความจำไหม
- **คำตอบ:** `docker compose up` คำสั่งเดียวเปิด proxy, API, ฐานข้อมูล และเว็บ ฐานข้อมูลมี healthcheck และ API เริ่มหลังฐานข้อมูลพร้อม ทุก container มีเพดานหน่วยความจำ (`api.memory_proxy_mb`, `api.memory_api_mb` ที่รวมงานเบื้องหลังใน process เดียว, `api.memory_web_mb`, `api.memory_db_mb`)
- **เหตุผล:** เครื่องใหม่ขึ้นระบบได้ในคำสั่งเดียว และ container ตัวเดียวกินหน่วยความจำจนเครื่องล่มไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับ compose และค่าเพดานใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### API-D21: ใครรัน migration
- **คำตอบ:** API รันเองตอน start ในทุกสภาพแวดล้อม: รอฐานข้อมูลไม่เกิน `api.db_wait_seconds` วินาที ใช้บัญชีเจ้าของ schema รัน migration ที่ค้าง แล้วรับคำขอด้วย role ของแอป migration ล้มแล้ว process จบด้วย error และไม่ตอบคำขอใด schema เปลี่ยนผ่าน migration เท่านั้น ตารางของไลบรารีงานเบื้องหลังอยู่ schema ของตัวเอง ไม่อยู่ใน migration ของแอป
- **เหตุผล:** deploy คือเปลี่ยน image แล้ว start ไม่มีขั้นที่ลืมทำ และ API ไม่มีทางรับคำขอด้วย schema ที่ไม่ตรงกับโค้ด
- **ถ้าผิด:** แก้ทีหลังได้ — ย้าย migration ไปเป็นขั้นแยกของการ deploy ได้โดยไม่เปลี่ยน migration
- **ถามเมื่อ:** Production มี API มากกว่าหนึ่งตัว หรือ DBA ของลูกค้าต้องตรวจ SQL ก่อนรัน
- **ตัวเลือกอื่น:** b) Production รัน migration เป็นขั้นแยกก่อน deploy (เครื่องมือ migration หรือ SQL ที่ตรวจแล้ว) และ API ไม่ยอม start เมื่อยังมี migration ค้าง

### API-D22: มีสภาพแวดล้อมอะไรบ้าง และต่างกันอย่างไร
- **คำตอบ:** สี่ชุด: Development (เครื่องนักพัฒนา), Prototype (เครื่องให้ลูกค้าลอง ข้อมูลตัวอย่าง), Staging (ลูกค้าทดสอบก่อนใช้จริง ตั้งค่าเหมือน Production), Production ค่าตั้งเดียวบอกว่าเป็นชุดไหน ค่าอื่นหรือไม่มีค่าแล้ว API ไม่ start ความต่างอยู่ในตารางของ requirement "Environments" เท่านั้น
- **เหตุผล:** ทุกคนรู้ว่าอะไรเปิดที่ไหน และไม่มีพฤติกรรมที่ต่างกันโดยไม่มีใครเขียนไว้
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือรวมสภาพแวดล้อมได้ โดยเติมคอลัมน์ในตาราง
- **ถามเมื่อ:** ลูกค้าไม่มีเครื่อง Staging หรือต้องมีสภาพแวดล้อมเพิ่ม เช่น เครื่องอบรม
- **ตัวเลือกอื่น:** b) ไม่มี Staging ลูกค้าทดสอบบน Production ก่อนเปิดใช้ แล้วล้างข้อมูลทดสอบ c) เพิ่มสภาพแวดล้อมที่ตั้งค่าเหมือน Staging

### API-D23: โหมด prototype เปิดที่ไหน
- **คำตอบ:** สวิตช์โหมด prototype ใน env เปิดได้เฉพาะ Development และ Prototype API ไม่ยอม start เมื่อสวิตช์เปิดใน Staging หรือ Production ของที่แพ็กอื่นผูกกับโหมดนี้ (บัญชี seed ตัวสลับผู้ใช้ mailbox ของ prototype testing control) ไม่มีอยู่เมื่อปิด endpoint ของมันตอบ 404 คำตอบของ health บอกว่าโหมดเปิดหรือไม่ ให้เว็บแสดงแบนเนอร์ได้
- **เหตุผล:** เครื่องมือที่ข้ามรหัสผ่านหรือเห็นอีเมลของทุกคนต้องไม่มีทางไปถึงระบบจริง แม้ตั้งค่าผิด
- **ถ้าผิด:** แก้ยาก — ถ้าหลุดไปเปิดบน Production ทุกคนสลับเป็นใครก็ได้และเห็นรหัสในอีเมล
- **ถามเมื่อ:** ไม่ถาม
