# ข้อตัดสินใจของแพ็ก foundation

## API

### FOUND-D01: back end ใช้อะไร
- **คำตอบ:** ASP.NET Core บน .NET รุ่น `foundation.dotnet_major` (LTS) ด้วย C# รุ่น `foundation.csharp_major` งานที่ไม่ใช่ web (worker, งานรันครั้งเดียว) เป็น .NET รุ่นเดียวกันใน solution เดียว รุ่นเต็มเลือกรุ่นเสถียรล่าสุดตอนเริ่ม และจดใน AGENTS.md
- **เหตุผล:** LTS ได้รับ support นาน ทีมใช้รุ่นนี้กับทุกระบบที่ทำล่าสุด และงานทุกชนิดใช้ entity กับชุด test ร่วมกันได้
- **ถ้าผิด:** แก้ยาก — เปลี่ยน runtime คือเขียน back end ใหม่ ส่วนขยับรุ่น LTS ถัดไปเป็นงานย้ายรุ่นตามปกติ
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D02: endpoint เขียนแบบ controllers หรือ Minimal APIs
- **คำตอบ:** controllers (`[ApiController]`) จัดตาม module ไม่มีกฎธุรกิจใน controller
- **เหตุผล:** ระบบส่วนใหญ่ของทีมใช้แบบนี้ attribute ตรวจสิทธิ์อยู่ติด action ทุกตัว และ `[ApiController]` ตอบ 400 ให้เองเมื่อข้อมูลที่ส่งมาอ่านไม่ออก
- **ถ้าผิด:** แก้ยาก — ทุก endpoint และ test ที่อ้างถึงต้องเขียนใหม่ แม้กฎธุรกิจจะไม่เปลี่ยน
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) Minimal APIs จัดกลุ่มตาม feature ใต้ route group โค้ดสั้นกว่า แต่ต้องเขียนการตรวจข้อมูลและ filter ของกลุ่มเอง

### FOUND-D03: ใช้ mediator และ mapping library ไหม
- **คำตอบ:** ไม่ใช้ทั้งสองอย่าง endpoint เรียก service ของ Application ตรงๆ และเขียน mapping เอง
- **เหตุผล:** อ่านโค้ดตามได้ตรง ไม่มีเรื่อง licence ต้องคอยดู และงานเขียน mapping เพิ่มเพียงเล็กน้อย
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม mediator หรือ mapping แบบ source generator ทีละ use case ได้
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) Mediator กับ Mapperly (ฟรีทั้งคู่ แบบ source generator) ได้ pipeline สำหรับตรวจข้อมูล transaction และการวัดเวลา แต่เพิ่มแนวคิดที่ทีมต้องเรียน c) MediatR กับ AutoMapper ทีมคุ้น แต่ใช้เชิงพาณิชย์ต้องซื้อ licence หรือยอมเงื่อนไขเปิดโค้ด จึงเป็นการตัดสินใจเรื่องเงินของคุณ

### FOUND-D04: ตรวจข้อมูลขาเข้าด้วยอะไร
- **คำตอบ:** FluentValidation เขียน validator คู่กับ use case ใน Application รูปแบบของคำตอบเมื่อไม่ผ่านเป็นกติกาของแพ็ก `api`
- **เหตุผล:** กฎข้ามหลายฟิลด์เขียนและ test ได้ในที่เดียว และชั้น Application ไม่ต้องพึ่ง ASP.NET Core
- **ถ้าผิด:** แก้ทีหลังได้ — ย้ายทีละ use case โดยคำตอบของ API ไม่เปลี่ยน
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ไม่เพิ่ม library ใช้ DataAnnotations และการตรวจที่ framework มีให้ บวกโค้ดของ Service เองสำหรับกฎข้ามฟิลด์

## ข้อมูล

### FOUND-D05: ฐานข้อมูลและตัวเข้าถึงข้อมูลคืออะไร
- **คำตอบ:** PostgreSQL รุ่น `foundation.postgres_major` เข้าถึงด้วย EF Core รุ่นเดียวกับ .NET ผ่าน provider ของ Npgsql DbContext, entity configuration และ migration อยู่ใน Infrastructure schema เปลี่ยนผ่าน migration เท่านั้น migration ไปถึงแต่ละสภาพแวดล้อมอย่างไรเป็นกติกาของแพ็ก `api`
- **เหตุผล:** ฟรี ทีมใช้กับทุกระบบ และ test กับฐานข้อมูลรุ่นเดียวกับของจริงได้
- **ถ้าผิด:** แก้ยาก — ชนิดข้อมูล migration และ query เฉพาะของ PostgreSQL ต้องทำใหม่ทั้งหมด
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D06: ชื่อตาราง ชื่อคอลัมน์ และชนิดของเงิน
- **คำตอบ:** ชื่อตารางและคอลัมน์เป็น snake_case โดยไม่ต้องเขียนชื่อเองทีละคอลัมน์ ชื่อใน C# เป็น PascalCase ตามปกติ เงินเป็น `decimal` ในโค้ดและ `foundation.money_precision` ในฐานข้อมูล ปริมาณและน้ำหนักเป็น `decimal` ไม่ใช้ float หรือจำนวนเต็ม และกำหนดความละเอียดทุกคอลัมน์
- **เหตุผล:** PostgreSQL ไม่ต้องใส่เครื่องหมายคำพูดรอบชื่อ คนเขียน SQL อ่านง่าย และเงินไม่เพี้ยนจากการปัดของเลขทศนิยมแบบ float
- **ถ้าผิด:** แก้ยาก — เปลี่ยนชื่อทุกตาราง หรือแปลงข้อมูลเงินที่เก็บไปแล้ว
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D07: Application เข้าถึงข้อมูลอย่างไร
- **คำตอบ:** repository หนึ่งตัวต่อ aggregate root สำหรับเขียน และ query หนึ่งชุดต่อ module สำหรับอ่าน interface อยู่ใน Application ตัวจริงอยู่ใน Infrastructure Application ไม่อ้าง EF Core
- **เหตุผล:** โหมด prototype สลับเป็นข้อมูลปลอมได้ด้วย DI โดยไม่แก้ endpoint และชั้น Application test ได้โดยไม่ต้องมีฐานข้อมูล
- **ถ้าผิด:** แก้ยาก — ทุก use case เขียนวิธีเข้าถึงข้อมูลใหม่
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) interface `IAppDbContext` ใน Application เปิด `DbSet` ให้ query ด้วย LINQ ได้เลย โค้ดน้อยกว่า แต่ Application ผูกกับ EF Core และโหมด prototype ต้องเติมข้อมูลลงฐานหรือมีตัวอ่านปลอมแยก

### FOUND-D08: ระบบรองรับหนึ่งองค์กรหรือหลายองค์กร
- **คำตอบ:** หนึ่งองค์กรต่อหนึ่งการติดตั้ง ไม่มีคอลัมน์ tenant
- **เหตุผล:** ไม่มีกฎแยกข้อมูลที่ต้องดูแลในทุก query เมื่อระบบไม่ได้ขายเป็นบริการให้หลายองค์กร
- **ถ้าผิด:** แก้ยาก — เพิ่มคอลัมน์ tenant ทีหลังกระทบทุกตาราง ทุก index และทุก query
- **ถามเมื่อ:** ระบบให้บริการหลายองค์กรที่ข้อมูลต้องแยกจากกัน หรือเอกสารลูกค้าเอ่ยถึงหลายบริษัทในระบบเดียว
- **ตัวเลือกอื่น:** b) ฐานเดียว ตารางร่วม ทุกแถวมี tenant id มี query filter ของ EF Core และ row level security ของ PostgreSQL เป็นด่านที่สอง c) ฐานข้อมูลแยกต่อองค์กร แยกขาดที่สุด แต่ migration และ backup คูณตามจำนวนองค์กร

## Web

### FOUND-D09: เว็บใช้อะไร
- **คำตอบ:** ตาม profile ที่เลือกตอน `/mflow:init` `react-vite`: React รุ่น `foundation.react_major` กับ Vite และ TypeScript แบบ `strict` build เป็นไฟล์ static ที่ proxy เสิร์ฟ ใช้ Node รุ่น `foundation.node_major` ตอน build `mvc-htmx`: ASP.NET Core MVC กับ Razor และ HTMX
- **เหตุผล:** ทั้งสอง profile เป็นแบบที่ mflow รองรับเต็ม และเว็บแบบ static ไม่ต้องมี Node ใน production
- **ถ้าผิด:** แก้ยาก — หลังมี kit หรือหน้าจอแล้ว การเปลี่ยนคือสร้าง kit และหน้าจอใหม่
- **ถามเมื่อ:** ระบบมีหน้าสาธารณะที่ต้อง render ก่อนถึง browser เพื่อ SEO หรือยังไม่ได้เลือก profile
- **ตัวเลือกอื่น:** b) Next.js แบบ static export ได้ routing ของ framework และหน้าสาธารณะที่ค้นเจอได้ แต่เป็น profile `custom` ที่ mflow ยังไม่ได้ทดสอบ c) Next.js แบบมี server ต้องมี Node ใน production

### FOUND-D10: ฐาน CSS ของเว็บคืออะไร
- **คำตอบ:** `react-vite` ใช้ Tailwind CSS 4 อ่าน token จาก `tokens.css` ของ kit `mvc-htmx` ใช้ Bootstrap 5 กับ bridge ของ kit สีและระยะมาจาก token เท่านั้น หน้าตาและ component เป็นเรื่องของ `/mflow:theme`
- **เหตุผล:** เว็บ React ของทีมใช้ Tailwind ทั้งหมด ส่วน profile `mvc-htmx` ของ mflow เขียนบน Bootstrap
- **ถ้าผิด:** แก้ยาก — หลังมีหน้าจอแล้วต้องแปลง class ทุกหน้า
- **ถามเมื่อ:** ลูกค้ามี template หรือชุด CSS ที่บังคับใช้
- **ตัวเลือกอื่น:** b) ใช้ template ของลูกค้า โดยให้ `tokens.css` ของ kit แทนค่าสีและระยะ c) `react-vite` กับ Bootstrap 5 แล้วเขียน component ห่อเอง

### FOUND-D11: เว็บ React ใช้ library อะไรเป็นหลัก
- **คำตอบ:** React Router สำหรับ route และเก็บตัวกรองกับหน้าไว้ใน URL, TanStack Query สำหรับดึงข้อมูล, React Hook Form กับ Zod สำหรับฟอร์ม, type และ client สร้างจาก OpenAPI ด้วย openapi-typescript กับ openapi-fetch ตารางใช้ component ของ kit ที่แบ่งหน้าที่ API
- **เหตุผล:** เป็นชุดที่เว็บ React ของทีมใช้ซ้ำกันมากที่สุด ฟรีทั้งหมด และ type ไม่มีทางหลุดจาก API
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนทีละ feature ได้ แต่ router กระทบทุกหน้า
- **ถามเมื่อ:** profile เป็น `react-vite`
- **ตัวเลือกอื่น:** b) ชุดเดียวกัน แต่ใช้ TanStack Router แทน React Router c) ใช้ Orval สร้าง hook ของ TanStack Query จาก OpenAPI แทน openapi-fetch เขียนเองน้อยกว่า แต่ปรับพฤติกรรมของ hook ยากกว่า

### FOUND-D12: เว็บใช้ตัวจัดการแพ็กเกจและ lint อะไร
- **คำตอบ:** npm (ใช้ workspaces เมื่อมีหลายเว็บ) กับ ESLint และ Prettier
- **เหตุผล:** npm มากับ Node ไม่ต้องติดตั้งเพิ่ม ทีมใช้กับระบบส่วนใหญ่ และ ESLint ตรวจตาม type ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยน lockfile และไฟล์ตั้งค่า lint โดยโค้ดของแอปไม่เปลี่ยน
- **ถามเมื่อ:** โปรเจกต์มีเว็บที่ build ด้วย Node
- **ตัวเลือกอื่น:** b) pnpm กับ oxlint ติดตั้งเร็วกว่าและ lint เร็วกว่า แต่กฎน้อยกว่า ESLint c) pnpm กับ ESLint และ Prettier

## ไฟล์และเอกสาร

### FOUND-D13: อ่านและเขียน Excel ด้วยอะไร
- **คำตอบ:** ClosedXML ทั้งการอ่านและเขียน `.xlsx` ไม่ใช้ EPPlus รูปแบบไฟล์และขั้นตอนนำเข้าส่งออกเป็นเรื่องของแพ็ก `import-export`
- **เหตุผล:** ทุกระบบของทีมที่ทำงาน Excel ใช้ตัวนี้ ฟรีเชิงพาณิชย์ ส่วน EPPlus ต้องซื้อ licence
- **ถ้าผิด:** แก้ทีหลังได้ — โค้ดอยู่หลัง interface ใน Infrastructure
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D14: สร้าง PDF ด้วยอะไร
- **คำตอบ:** ยังไม่เลือก จะเลือกเมื่อมีเอกสารพิมพ์ใบแรกในขอบเขต จากตัวอย่างเอกสารจริงของลูกค้า และตรวจ licence ตอนนั้น
- **เหตุผล:** ทางเลือกขึ้นกับหน้าตาของเอกสาร และเงื่อนไข licence ของ library PDF เปลี่ยนบ่อย
- **ถ้าผิด:** แก้ทีหลังได้ — โค้ดอยู่หลัง interface ใน Infrastructure เปลี่ยนตัวสร้างได้โดยจอไม่เปลี่ยน
- **ถามเมื่อ:** ขอบเขตของ release นี้มีเอกสารที่ต้องพิมพ์หรือส่งเป็น PDF
- **ตัวเลือกอื่น:** b) แปลง HTML เป็น PDF ด้วย Chromium คุมหน้าตาด้วย CSS แต่ image ใหญ่ขึ้น c) PDFsharp วาดเองทีละส่วน d) QuestPDF เขียนง่าย แต่ฟรีเฉพาะตามเงื่อนไข community ทุกตัวตรวจ licence รุ่นที่ใช้ก่อนเลือก และแบบเสียเงินเป็นการตัดสินใจของคุณ

## Container และ environment

### FOUND-D15: รันระบบอย่างไร
- **คำตอบ:** ทุก service เป็น container และมี `docker-compose.yml` สำหรับเครื่องนักพัฒนา คำสั่งเดียวเปิดทั้งชุด ระหว่างเขียนโค้ดเปิดเฉพาะฐานข้อมูลใน compose แล้วรัน API และเว็บจากเครื่องได้ Dockerfile เป็นแบบ multi-stage ไม่มี SDK หรือซอร์สโค้ดใน image ที่รันจริง สิ่งที่อยู่ใน compose และเพดานหน่วยความจำเป็นกติกาของแพ็ก `api`
- **เหตุผล:** เครื่องใหม่ขึ้นระบบได้ทันที และ image ที่รันจริงเล็กและมีของที่โจมตีได้น้อย
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับ compose และ Dockerfile โดยโค้ดของแอปไม่เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D16: ฐานข้อมูลบนเครื่องนักพัฒนาใช้ port และ volume อย่างไร
- **คำตอบ:** เปิดที่ port `foundation.db_dev_port` ไม่ใช้ 5432 ผูกกับ loopback ของเครื่องเท่านั้น ข้อมูลอยู่ใน volume ที่มีชื่อ ซึ่งอยู่รอดหลัง `docker compose down`
- **เหตุผล:** เครื่องเดียวรันได้หลายโปรเจกต์โดยไม่ชนกัน และฐานข้อมูลไม่เปิดให้เครื่องอื่นในวง LAN เข้าถึง
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนใน `.env` และ compose
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D17: reverse proxy ใช้ตัวไหน
- **คำตอบ:** nginx จาก image ทางการ ไฟล์ตั้งค่าอยู่ใน `foundation.deploy_folder` proxy ส่งอะไรไปไหนและรับคำขอใหญ่แค่ไหนเป็นกติกาของแพ็ก `api`
- **เหตุผล:** ทุกระบบของทีมใช้ตัวนี้ ฟรี และเสิร์ฟไฟล์ static ของเว็บได้ในตัว
- **ถ้าผิด:** แก้ทีหลังได้ — กฎของ proxy อยู่ในไฟล์เดียว
- **ถามเมื่อ:** ไม่ถาม

## Test

### FOUND-D18: unit และ integration test ใช้อะไร
- **คำตอบ:** .NET ใช้ xUnit v3 บน Microsoft Testing Platform, integration test รันกับ PostgreSQL รุ่นเดียวกับของจริงผ่าน Testcontainers ไม่ใช้ฐานข้อมูลจำลอง เว็บ React ใช้ Vitest กับ Testing Library กฎธุรกิจ test แบบ data-driven จาก golden data ใน `Golden/` ของ `<ProjectName>.Domain.Tests` ทั้งหมดรันบนเครื่องนักพัฒนาด้วยคำสั่ง test ปกติ
- **เหตุผล:** ฐานข้อมูลจริงจับเรื่อง migration, constraint และ query เฉพาะของ PostgreSQL ที่ตัวจำลองมองไม่เห็น

## โครง repo และ solution

### FOUND-D21: repo วางโฟลเดอร์ระดับบนอย่างไร
- **คำตอบ:** repo เดียว มีแอปและ layer ทุกตัวใต้ `src/` แล้วมี `tests/`, `docs/`, `deploy/` และ `<ProjectName>.slnx` ที่ root
- **เหตุผล:** path สั้น ตรงกับค่าเริ่มต้นของ mflow และเครื่องมือ .NET
- **ถ้าผิด:** แก้ยาก — ย้ายทุก project แก้ path ใน solution, Dockerfile, compose และตาราง `## Stack`
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) `apps/` สำหรับของที่ deploy และ `packages/` สำหรับของที่หลายแอปใช้ร่วม เหมาะเมื่อมีหลายเว็บหรือ package ร่วม แต่ path ยาวขึ้น

### FOUND-D22: solution แบ่ง layer และอ้างถึงกันอย่างไร
- **คำตอบ:** solution ไฟล์เดียวแบบ `.slnx` ที่ root มีสี่ชั้น `<ProjectName>.Domain` (entity และกฎธุรกิจ ไม่อ้างอะไรเลย), `.Application` (use case, DTO, การตรวจข้อมูล, interface ที่ชั้นนอกทำให้), `.Infrastructure` (EF Core, ไฟล์, อีเมล, ระบบภายนอก) และแอป (endpoint, การเข้าระบบ, middleware, การต่อ DI) อ้างเข้าด้านในเท่านั้น: แอป → Infrastructure → Application → Domain แอปใช้ Infrastructure เฉพาะตอนต่อ DI architecture test ตรวจทุกครั้งที่รัน test และบอกชื่อกฎที่ผิด เว็บ React ไม่อยู่ใน solution
- **เหตุผล:** กฎธุรกิจไม่ผูกกับ framework และการอ้างผิดชั้นถูกจับตั้งแต่บนเครื่องนักพัฒนา ไม่ต้องรอ review
- **ถ้าผิด:** แก้ยาก — ย้าย class ข้าม project หลังมีโค้ดแล้วกระทบทั้ง solution
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D23: แบ่ง module และโฟลเดอร์ข้างในอย่างไร
- **คำตอบ:** หนึ่งโฟลเดอร์ต่อ bounded context ในทุก layer ใช้ DbContext ตัวเดียว ใน Application หนึ่งโฟลเดอร์ต่อ use case (`Features/<Module>/<UseCase>/`) รวม request, handler หรือ service, validator และ DTO ไว้ด้วยกัน เว็บใช้ `features/<module>/` แบบเดียวกัน
- **เหตุผล:** งานข้าม context อยู่ใน transaction เดียวได้ง่าย และเปิดโฟลเดอร์เดียวเห็นทั้ง use case
- **ถ้าผิด:** แก้ยาก — แยกเป็น project ทีหลังต้องแก้ DbContext และ transaction ที่ข้าม context
- **ถามเมื่อ:** มีหลายทีมแยกกันดูแล หรือต้อง deploy แต่ละ context แยกกัน
- **ตัวเลือกอื่น:** b) project ต่อ context ต่อ layer และ DbContext ต่อ module ขอบเขตแข็งแรงที่สุด แต่จำนวน project คูณตาม context และงานข้าม context ใน transaction เดียวทำยาก

## ชื่อและ namespace

### FOUND-D24: ตั้งชื่อ project โฟลเดอร์ และ namespace อย่างไร
- **คำตอบ:** แอปที่ deploy ได้เป็น `<ProjectName>.<Kind>` หรือ `<ProjectName>.<Kind>.<Part>` ทั้ง project โฟลเดอร์ และ root namespace (`Web`, `Api`, `Worker`, `Mobile`; `Backend` หลังบ้าน, `Frontend` หน้าบ้าน) เว็บที่ไม่ใช่ .NET ใช้ชื่อโฟลเดอร์เดียวกัน และชื่อแพ็กเกจเป็นตัวพิมพ์เล็กคั่นขีด ชั้นในสุดชื่อ `.Domain` ไม่ใช้ `.Core` test project คือชื่อที่ test ต่อท้าย `.Tests` และมี `<ProjectName>.ArchitectureTests` namespace ตามโฟลเดอร์ ชื่อในโค้ดมาจาก Domain vocabulary ใน AGENTS.md
- **เหตุผล:** เห็นชื่อแล้วรู้ว่าเป็นแอปอะไรของใคร และกฎของ mflow กับ golden data อ้างชื่อเหล่านี้
- **ถ้าผิด:** แก้ยาก — เปลี่ยนชื่อ project โฟลเดอร์ และ namespace ทั้ง solution
- **ถามเมื่อ:** ไม่ถาม

### FOUND-D25: แอปชนิดเดียวกันมี Part ตั้งแต่แรกไหม
- **คำตอบ:** มีแอปชนิดนั้นตัวเดียวและไม่มีแผนเพิ่ม ไม่ต้องมี Part (`<ProjectName>.Api`)
- **เหตุผล:** ชื่อสั้นเมื่อไม่มีตัวที่ต้องแยก
- **ถ้าผิด:** แก้ยาก — เพิ่ม Part ให้แอปเดิมทีหลังคือการเปลี่ยนชื่อ project และ path ใน `## Stack`
- **ถามเมื่อ:** ขอบเขตหรือแผนของระบบมีแอปชนิดเดียวกันมากกว่าหนึ่งตัว หรือยังบอกไม่ได้ว่าจะมีไหม
- **ตัวเลือกอื่น:** b) ทุกแอปของชนิดนั้นมี Part ตั้งแต่ตัวแรก (`<ProjectName>.Web.Backend`, `<ProjectName>.Web.Frontend`) จึงไม่ต้องเปลี่ยนชื่อภายหลัง
