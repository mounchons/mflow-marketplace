# jobs: ข้อที่ตอบไว้แล้ว

### JOB-D01: งานแบบไหนต้องทำเบื้องหลัง
- **คำตอบ:** งานที่อาจนานเกิน `jobs.request_wait_seconds` วินาที งานที่เรียกระบบภายนอกหรือส่งอีเมล งานที่ทำกับรายการจำนวนมาก และงานตามเวลา ทำเบื้องหลังทั้งหมด request แค่บันทึกสิ่งที่ผู้ใช้สั่ง เข้าคิว แล้วตอบทันที งานเล็กที่อยู่ในการบันทึกเดียวและไม่พึ่งระบบอื่นทำใน request ได้ แพ็กเจ้าของงานกำหนดข้อยกเว้นได้ เช่นปุ่มส่งทดสอบ
- **เหตุผล:** ผู้ใช้ไม่ต้องรอ request ไม่ค้างเพราะระบบอื่นช้า และงานที่ล้มลองใหม่ได้โดยผู้ใช้ไม่ต้องกดซ้ำ
- **ถ้าผิด:** แก้ทีหลังได้ — ย้ายงานไปเบื้องหลังเป็น change แยก แต่คำตอบของ API นั้นเปลี่ยนจาก 200 เป็น 202
- **ถามเมื่อ:** ไม่ถาม

### JOB-D02: งานมีกี่ชนิด และเข้าคิวอย่างไร
- **คำตอบ:** สองชนิด งานตามรอบเวลาที่ตัวจับเวลาเริ่มเอง และงานครั้งเดียวที่ request หรืองานอื่นเข้าคิว ทุกงานมีรหัสใน catalog ในโค้ดรายการเดียว งานครั้งเดียวเข้าคิวด้วยการเขียนแถว `job_run` ใน transaction เดียวกับการบันทึกที่ทำให้เกิดงาน ระบุ `subject_key` บอกว่าทำกับอะไร เก็บแค่รหัสอ้างอิง ไม่เก็บความลับหรือข้อมูลทั้งก้อน request ตอบ 202 พร้อมรหัสรอบ
- **เหตุผล:** การบันทึกที่ล้มไม่ทิ้งงานค้าง งานไม่หายเมื่อเครื่องดับหลังบันทึก และผู้ใช้ตามผลจากรหัสรอบได้
- **ถ้าผิด:** แก้ยาก — งานเข้าคิวนอก transaction ทำให้งานหายหรือเกินจากข้อมูลจริง ไล่แก้ย้อนหลังยาก
- **ถามเมื่อ:** ไม่ถาม

### JOB-D03: รอบเวลาเก็บที่ไหน ใครแก้
- **คำตอบ:** ค่าเริ่มต้นอยู่ใน catalog ตอน start เขียนลง `job_definition` ครั้งแรกเท่านั้น หลังจากนั้นค่าที่เก็บชนะ ผู้ถือ `{job_manage_key}` แก้บนจองานได้ 3 รูปแบบ: ทุก N นาที ทุกวัน และช่วงวันของเดือน เก็บเป็น cron 5 ช่อง มีผลรอบถัดไปโดยไม่ restart ไม่อยู่บนหน้าตั้งค่าระบบ งานที่แพ็กเจ้าของกำหนดรอบไว้แล้วแก้รอบบนจอไม่ได้ แต่เปิดปิดได้
- **เหตุผล:** ลูกค้าเลื่อนเวลางานได้เองโดยไม่ต้อง deploy รูปแบบบนจอกันคนตั้ง cron ผิด และงานระบบไม่ถูกเปลี่ยนรอบจนกติกาของแพ็กเจ้าของเพี้ยน
- **ถ้าผิด:** แก้ทีหลังได้ — ย้ายรอบระหว่างโค้ดกับตารางได้ ไม่กระทบข้อมูลธุรกิจ
- **ถามเมื่อ:** เอกสารลูกค้าระบุว่ารอบเวลาตายตัว หรือระบบมีแต่งานจากแพ็กอื่น
- **ตัวเลือกอื่น:** b) รอบเวลาอยู่ในโค้ดหรือ config เปลี่ยนด้วย deploy บนจอมีแค่สวิตช์เปิดปิด c) แก้ cron เป็นข้อความบนจอ สำหรับผู้ดูแลที่เป็นช่าง

### JOB-D04: รอบเวลาใช้เขตเวลาอะไร
- **คำตอบ:** เขตเวลาของระบบ `{system_time_zone}` เขตเดียวทั้งระบบ ไม่ใช้เขตเวลาของ server เวลาเริ่มและจบเก็บเป็น UTC แสดงตามเขตเวลาของระบบ เขตที่มีเวลาออมแสง รอบไม่หายและไม่ซ้ำในวันเปลี่ยนเวลา
- **เหตุผล:** ลูกค้าตั้ง "ตีสอง" หมายถึงตีสองของเขา ถ้าใช้ UTC งานจะไปรันตอนเก้าโมงเช้า
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนเขตแล้วรอบเดิมคิดตามเขตใหม่ทันที
- **ถามเมื่อ:** ผู้ใช้หรือสาขาอยู่ต่างเขตเวลา และงานต้องตรงเวลาของแต่ละเขต
- **ตัวเลือกอื่น:** b) เขตเวลาแยกต่องาน เก็บใน `job_definition` c) รันตาม UTC และบอกเวลา UTC บนจอ

### JOB-D05: งานเดียวกันรันซ้อนกันได้ไหม
- **คำตอบ:** ไม่ได้ แม้มี API หลาย container ฐานข้อมูลเป็นตัวตัดสิน ไม่ใช่ตัวแปรในเครื่อง: งานหนึ่ง (และ `subject_key` หนึ่งของงานครั้งเดียว) มีแถว Queued หรือ Running ได้แถวเดียว และรอบเวลาหนึ่งเริ่มได้ครั้งเดียว รอบตามเวลาที่ชนรอบที่รันอยู่ข้ามไปเงียบๆ ไม่มีแถวใหม่ คนสั่งรันที่ชนได้ 409 `JOB_RUNNING` งานครั้งเดียวที่เข้าคิวซ้ำได้รอบเดิมกลับไป งานต่างรหัสรันพร้อมกันได้ไม่เกิน `jobs.worker_count` งานต่อเครื่อง
- **เหตุผล:** กติกาอยู่ที่ฐานข้อมูลจึงไม่ขึ้นกับจำนวนเครื่อง และคนกดซ้ำไม่ทำให้งานทำซ้ำ
- **ถ้าผิด:** แก้ยาก — งานที่รันซ้อนทำข้อมูลซ้ำหรือส่งซ้ำ ไล่แก้ย้อนหลังยาก
- **ถามเมื่อ:** ไม่ถาม

### JOB-D06: งานต้องรันซ้ำได้ปลอดภัยไหม
- **คำตอบ:** ต้อง ทุกงานเขียนให้รันซ้ำแล้วผลเหมือนเดิม งานหลายรายการทำทีละรายการในการบันทึกของตัวเอง รายการที่ทำแล้วข้าม รายการที่ล้มไม่หยุดรายการอื่น รอบจบเป็น Failed พร้อมจำนวน ส่วนที่สำเร็จคงอยู่ งานที่เรียกระบบภายนอกส่งรหัสกันซ้ำเมื่อระบบนั้นรับได้ งานที่ลบของนอกฐานข้อมูลลบของก่อนแล้วลบแถว
- **เหตุผล:** งานถูกรันซ้ำอยู่แล้วจากการลองใหม่ การ restart และการกดด้วยมือ งานหนึ่งรายการที่พังไม่ควรทำให้ทั้งรอบเสีย
- **ถ้าผิด:** แก้ยาก — ผลซ้ำที่ส่งไปแล้ว เช่นอีเมลหรือข้อมูลในระบบอื่น เรียกคืนไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### JOB-D07: ลองใหม่กี่ครั้ง ห่างเท่าไร อะไรเป็น Failed
- **คำตอบ:** งานครั้งเดียวลองใหม่ตามช่วง `jobs.retry_delays_seconds` (ค่าเริ่มต้นลองใหม่ 2 ครั้ง รวมลอง 3 ครั้ง) ครบแล้วเป็น Failed พร้อม error ล่าสุด งานตามรอบเวลาไม่ลองใหม่ รอบถัดไปคือการลองใหม่ของมัน งานแยก error สองแบบ: ชั่วคราว (ระบบอื่นไม่ตอบ, 5xx, ฐานข้อมูลหลุด, หมดเวลา) ลองใหม่ได้ ต้องแก้ก่อน (ข้อมูลผิด, 400 403 422 จากระบบอื่น) เป็น Failed ทันที error ที่ไม่รู้จักถือว่าชั่วคราว งานที่รายการมีการลองใหม่ของตัวเองอยู่แล้ว เช่นตัวส่งอีเมล ใช้ของรายการ ไม่ซ้อนอีกชั้น
- **เหตุผล:** ความผิดพลาดชั่วคราวหายเองเมื่อรอสักครู่ แต่ข้อมูลผิดลองกี่ครั้งก็ผิด และการลองสองชั้นทำให้จำนวนครั้งคูณกัน
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนตัวเลขหรือแยกชนิด error ในงานนั้น
- **ถามเมื่อ:** งานเรียกระบบภายนอกที่กันการทำซ้ำไม่ได้ เช่นตัดเงิน
- **ตัวเลือกอื่น:** b) งานนั้นไม่ลองใหม่อัตโนมัติ เป็น Failed ทันที ให้คนตรวจแล้วกดลองใหม่ c) ก่อนลองใหม่ถามระบบภายนอกก่อนว่าครั้งก่อนสำเร็จหรือไม่

### JOB-D08: งานรันนานเกินไปทำอย่างไร
- **คำตอบ:** ทุกงานมีเวลาสูงสุดใน catalog ไม่ระบุใช้ `jobs.timeout_minutes` นาที ครบเวลาแล้วระบบสั่งหยุด งานหยุดหลังจบรายการปัจจุบัน รอบเป็น Failed ด้วย `JOB_TIMEOUT` ส่วนที่ทำแล้วคงอยู่ นับเป็นความผิดพลาดชั่วคราว งานครั้งเดียวจึงลองใหม่ได้ ไม่มีงานที่ไม่จำกัดเวลา
- **เหตุผล:** งานที่ค้างไม่จบถือสิทธิ์ "กำลังรัน" ไว้จนรอบถัดไปเริ่มไม่ได้ทั้งหมด
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับเวลาใน catalog
- **ถามเมื่อ:** ไม่ถาม

### JOB-D09: process ตายระหว่างงานทำอย่างไร
- **คำตอบ:** รอบที่รันอยู่ต่ออายุทุกหนึ่งในสามของ `jobs.lease_seconds` วินาที เครื่องที่รับงานทุกเครื่องตรวจรอบ Running ที่หมดอายุแล้วปิดเป็น Interrupted งานครั้งเดียวกลับเข้าคิวโดยนับเป็นการลองหนึ่งครั้ง หรือเป็น Failed เมื่อครบ งานตามรอบเวลารอรอบถัดไป ไม่ปิดรอบของเครื่องอื่นเพียงเพราะเครื่องตัวเอง start ใหม่
- **เหตุผล:** ปิดทุกรอบที่ค้างตอน start ใช้ได้เฉพาะระบบเครื่องเดียว เมื่อมีหลายเครื่องจะไปปิดรอบที่เครื่องอื่นกำลังทำงานอยู่
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับอายุ lease ส่วนรอบที่ค้างปิดได้ด้วย script
- **ถามเมื่อ:** ไม่ถาม

### JOB-D10: รอบหนึ่งบันทึกอะไร
- **คำตอบ:** แถว `job_run` ต่อรอบ: งาน ใครหรืออะไรเริ่ม เวลาเริ่มและจบ สถานะ จำนวนรายการ (ทั้งหมด สำเร็จ ล้ม ข้าม) รหัส error และข้อความที่อ่านได้ ไม่เกิน `jobs.error_max` ตัวอักษร ไม่มีความลับ รหัสผ่าน โทเค็น connection string เนื้อข้อมูล หรือ stack trace (stack trace อยู่ใน log พร้อมรหัสรอบ) งานที่รอบถี่กว่าทุก `jobs.frequent_minutes` นาทีและไม่มีงานในรอบนั้นไม่เขียนแถว แค่ปรับเวลาตรวจล่าสุดบน `job_definition`
- **เหตุผล:** ดูผลงานได้โดยไม่ต้องเข้า server หน้าจอไม่กลายเป็นที่รั่วของความลับ และตัวส่งอีเมลรายนาทีไม่สร้างพันแถวต่อวันโดยไม่มีข้อมูล
- **ถ้าผิด:** แก้ยาก — สิ่งที่ไม่ได้เก็บตอนรันย้อนเก็บไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### JOB-D11: เก็บประวัติรอบนานแค่ไหน
- **คำตอบ:** `jobs.run_retention_days` วันนับจากเวลาจบ แล้วงานล้างรายวันลบจริง ไม่ลง Activity Log `job_run` เป็นตารางชั่วคราวตาม AUDIT-D07 รอบที่ยัง Queued หรือ Running ไม่ถูกลบ
- **เหตุผล:** ประวัติรอบไม่ใช่ข้อมูลธุรกิจ ถ้าไม่ล้างตารางโตไม่หยุด
- **ถ้าผิด:** แก้ยาก — ประวัติที่ล้างแล้วเอาคืนไม่ได้
- **ถามเมื่อ:** เอกสารลูกค้ากำหนดอายุเก็บประวัติงาน
- **ตัวเลือกอื่น:** b) เก็บตามจำนวนวันที่ลูกค้ากำหนด c) เก็บตลอดไป

### JOB-D12: ดูงานได้ที่ไหน ใครใช้ได้
- **คำตอบ:** จองานของแพ็กนี้ ผู้ถือ `{job_view_key}` ดูงาน รอบล่าสุด รอบถัดไป ประวัติ และ error ผู้ถือ `{job_manage_key}` สั่งรัน แก้รอบเวลา และเปิดปิด จอที่มากับ library ของงาน เช่น dashboard ของ Hangfire ไม่เปิดให้ผู้ใช้เข้า เพราะไม่ผ่านกติกาสิทธิ์ของระบบ
- **เหตุผล:** ผู้ดูแลรู้ว่างานล้มหรือไม่โดยไม่ต้องเปิด log และสิทธิ์อยู่ในกติกาเดียวกับหน้าจออื่น
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหน้าจอจาก `job_run` ที่มีอยู่แล้วได้
- **ถามเมื่อ:** ระบบมีแต่งานจากแพ็กอื่น และไม่มีผู้ดูแลที่จะเปิดจอนี้
- **ตัวเลือกอื่น:** b) ไม่มีจอ ดูจาก log และอีเมลเตือน สั่งรันด้วย script

### JOB-D13: สั่งรันด้วยมือได้ไหม
- **คำตอบ:** ได้ ผู้ถือ `{job_manage_key}` สั่งรันงานตามรอบเวลาได้ทั้งตอนรอบเปิดและปิด และลองใหม่งานครั้งเดียวที่เป็น Failed ได้ เป็นแถวใหม่ที่อ้างรอบเดิม กล่องยืนยันบอกผลของงาน ตอบ 202 พร้อมรอบใหม่ทันที ชนรอบที่รันอยู่ตอบ 409 `JOB_RUNNING`
- **เหตุผล:** แก้สาเหตุแล้วไม่ต้องรอรอบถัดไป และไม่ต้องเข้า server
- **ถ้าผิด:** แก้ทีหลังได้ — ตัดปุ่มหรือจำกัดรายงานได้ใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### JOB-D14: เตือนใครเมื่อไร เมื่องานล้มซ้ำ
- **คำตอบ:** งานล้มติดกันครบ `jobs.alert_after_failures` รอบ (Failed หรือ Interrupted จาก process ตาย ไม่นับการปิดระบบ) เข้าคิวอีเมลผ่านแพ็กอีเมลถึงรายชื่อ `jobs.alert_emails` ครั้งเดียวต่อหนึ่งช่วงที่ล้ม รอบที่สำเร็จล้างตัวนับ จองานมีแถบเตือนเสมอ ไม่มีแพ็กอีเมลหรือรายชื่อว่าง แจ้งบนจออย่างเดียว ถ้าตัวส่งอีเมลล้มเอง อีเมลเตือนไม่ออก แต่จอยังเตือน
- **เหตุผล:** งานเบื้องหลังล้มเงียบได้นาน แต่ล้มครั้งเดียวจากระบบอื่นสะดุดไม่ควรปลุกใคร และเตือนซ้ำทุกรอบทำให้คนเลิกอ่าน
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนจำนวนหรือช่องทาง
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) เตือนบนจออย่างเดียว c) ส่งผ่านช่องทางอื่นที่ลูกค้าใช้ เช่นแชตหรือระบบเฝ้าระวัง

### JOB-D15: ใครเป็นผู้ทำของสิ่งที่งานแก้
- **คำตอบ:** `SYSTEM` ตาม AUDIT-D02 ไม่ว่างานเริ่มจากรอบเวลาหรือคนสั่ง คนที่สั่งเก็บใน `job_run.requested_by` และเป็นผู้ทำของการบันทึกที่เริ่มงาน งานเห็นข้อมูลทุกขอบเขต ยกเว้นระบบที่แยกข้อมูลรายองค์กร งานรันในองค์กรที่งานนั้นเป็นของ
- **เหตุผล:** Activity Log แยกได้ว่าระบบทำหรือคนทำ และคนที่กดยังตามหาได้จากรอบ
- **ถ้าผิด:** แก้ยาก — Activity Log ที่บันทึกผู้ทำผิดแก้ย้อนไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### JOB-D16: งานลง Activity Log อะไรบ้าง
- **คำตอบ:** แถว `job_run` และการปรับ `job_definition` ที่ตัวงานทำไม่ลงรายการของตัวเอง (AUDIT-D13) คนสั่งรันหรือสั่งลองใหม่ลงหนึ่งรายการ `ManualTrigger` คนแก้รอบหรือเปิดปิดลงหนึ่งรายการ `SaveSchedule` พร้อมค่าเก่าและใหม่ บันทึกโดยไม่เปลี่ยนไม่ลง ข้อมูลธุรกิจที่งานแก้ลงตามปกติด้วยผู้ทำ `SYSTEM` งานล้างข้อมูลไม่ลง
- **เหตุผล:** แถวรอบงานเป็นหลักฐานอยู่แล้ว ส่วนการกระทำของคนต้องตามหาได้
- **ถ้าผิด:** แก้ทีหลังได้ — log ใหม่ใช้กติกาใหม่ log เก่าคงเดิม
- **ถามเมื่อ:** ไม่ถาม

### JOB-D17: ปิดงานโดยไม่ deploy ได้ไหม
- **คำตอบ:** ได้ ต่องาน ด้วยสวิตช์บนจอซึ่งเก็บใน `job_definition` มีผลรอบถัดไป ไม่ต้อง restart รอบที่รันอยู่จบตามปกติ ปิดแล้วตัวจับเวลาไม่เริ่มงานนั้น งานครั้งเดียวในคิวรอจนเปิด ไม่หาย การสั่งรันด้วยมือยังทำได้ กล่องยืนยันบอกผลของการปิดงานนั้น หยุดทุกงานของเครื่องใดเครื่องหนึ่งใช้ `jobs.runner` แล้ว restart
- **เหตุผล:** ระบบปลายทางมีปัญหาหรืองานพังต้องหยุดได้ทันที และเปิดกลับได้เอง
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือตัดสวิตช์ได้
- **ถามเมื่อ:** ไม่ถาม

### JOB-D18: งานใน test รันอย่างไร
- **คำตอบ:** `jobs.mode` เป็น `Inline`: งานครั้งเดียวรันทันทีหลังการบันทึก ไม่ลองใหม่ ไม่มีตัวจับเวลา รอบตามเวลาไม่เริ่มเอง test เรียกงานตรงๆ และเลื่อนนาฬิกาของระบบเพื่อทดสอบเวลา แถว `job_run` ยังเขียนเหมือนจริง production ห้ามใช้ `Inline`
- **เหตุผล:** ตัวจับเวลาจริงที่ยิงกลาง test ทำผลไม่แน่นอน เกิดแถวเกินมาหรือไปถือสิทธิ์ "กำลังรัน" ของ test
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนวิธีรันใน test เท่านั้น
- **ถามเมื่อ:** ไม่ถาม

### JOB-D19: ตอน start ทำอะไร รอบที่พลาดทำอย่างไร
- **คำตอบ:** เพิ่มงานใหม่ของ catalog ลง `job_definition` โดยไม่เขียนทับรอบและสวิตช์ที่เก็บไว้ งานที่หายจาก catalog ซ่อนและไม่รัน แถวและประวัติคงอยู่ ไม่ทำงานหนักก่อนเปิดรับ request รอบที่พลาดระหว่างระบบดับชดเชยหนึ่งรอบต่องาน ไม่ไล่ทุกรอบ
- **เหตุผล:** deploy ใหม่ไม่ทำลายค่าที่ลูกค้าตั้ง API พร้อมรับคำขอเร็ว และงานตามเวลาไม่หายเงียบๆ
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนการชดเชยต่องานได้
- **ถามเมื่อ:** มีงานที่ผลไปถึงลูกค้าหรือคู่ค้า และไม่ควรเกิดนอกเวลา เช่นอีเมลแจ้งเตือนรายวัน
- **ตัวเลือกอื่น:** b) งานนั้นไม่ชดเชย รอรอบถัดไป c) ชดเชยทุกรอบที่พลาดตามลำดับเวลา

### JOB-D20: ตอนปิดระบบทำอย่างไร
- **คำตอบ:** หยุดรับงานใหม่ทันที สั่งงานที่รันอยู่ให้หยุดหลังจบรายการปัจจุบัน ภายใน `jobs.shutdown_seconds` วินาที รอบที่หยุดก่อนจบเป็น Interrupted งานครั้งเดียวกลับเข้าคิวโดยไม่นับเป็นการลอง และไม่นับเป็นงานล้ม ตัว container ต้องให้เวลาหยุดนานกว่าค่านี้
- **เหตุผล:** deploy ไม่ทิ้งงานค้างครึ่งรายการ และไม่ทำให้จองานขึ้นเตือนทุกครั้งที่ deploy
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับเวลา หรือรอบที่ค้างก็ถูกปิดตาม JOB-D09
- **ถามเมื่อ:** ไม่ถาม

### JOB-D21: รันงานใน API หรือแยก worker
