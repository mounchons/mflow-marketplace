# ข้อตัดสินใจของแพ็ก audit

### AUDIT-D01: ชื่อคอลัมน์ผู้ทำและเวลา และใครเป็นคนตั้งค่า
- **คำตอบ:** ทุกตารางธุรกิจมี `created_at`, `created_by`, `updated_at`, `updated_by` เวลาเก็บเป็น UTC แสดงตามเขตเวลาของระบบ ระบบตั้งค่าเองตอนบันทึกจากผู้ทำปัจจุบัน ค่าที่โค้ดใส่มาเองถูกเขียนทับ
- **เหตุผล:** ท้าย `_at` บอกว่าเป็นวันเวลา `_by` บอกว่าเป็นผู้ทำ ตั้งที่จุดบันทึกจุดเดียวจึงไม่มี Service ไหนลืมหรือปลอมผู้ทำได้
- **ถ้าผิด:** แก้ยาก — เปลี่ยนชื่อคอลัมน์ทุกตารางและ migration ทั้งชุด
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D02: ผู้ทำที่เป็น "ระบบ" เก็บอย่างไร
- **คำตอบ:** มีผู้ทำ `SYSTEM` หนึ่งแถวตั้งแต่ migration แรก ไม่มีรหัสผ่านและเข้าระบบไม่ได้ เป็นผู้ทำของทุกการบันทึกที่ไม่มีผู้ใช้เข้าระบบอยู่ (งานตามเวลา seed migration งานล้างข้อมูล) ส่วนการสั่งรันด้วยมือบันทึกเป็นชื่อคนที่กด และการตั้งรหัสผ่านผ่านลิงก์บันทึกเป็นเจ้าของลิงก์
- **เหตุผล:** `created_by` บังคับไม่ว่างได้ทุกตาราง Service ที่ลืมตั้งผู้ทำ error ทันที และแยก "ระบบทำ" ออกจาก "ไม่รู้ว่าใครทำ" ได้
- **ถ้าผิด:** แก้ยาก — คอลัมน์ผู้ทำทุกตารางต้องเปลี่ยนเป็นยอมให้ว่าง และ log เก่าตีความใหม่
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D03: คอลัมน์ผู้ทำชี้ไปที่ไหน เมื่อบัญชีมีหลายตาราง
- **คำตอบ:** ตารางกลางบาง `actor` (`id`, `kind`) ทุกคอลัมน์ผู้ทำและ `activity_log.actor_id` มี FK ชี้ตารางนี้ ตารางบัญชีของแต่ละพอร์ทัลใช้ `id` เดียวกับแถวใน `actor` แถวใน `actor` ไม่ถูกแก้หรือลบ
- **เหตุผล:** แยกตารางบัญชีตามพอร์ทัลได้โดยไม่เสีย FK ของคอลัมน์ผู้ทำ และกลไกรหัสผ่านกับเซสชันยังมีชุดเดียว ใช้ได้ทั้งระบบที่มีพอร์ทัลเดียวและหลายพอร์ทัล
- **ถ้าผิด:** แก้ยาก — FK ของคอลัมน์ผู้ทำทุกตารางและตารางเซสชันต้องเปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D04: เก็บประวัติการแก้ไขอย่างไร นอกจากผู้แก้ล่าสุด
- **คำตอบ:** Activity Log ตารางเดียว ทุกการบันทึกเขียนค่าเก่าและค่าใหม่ของทุกฟิลด์ที่เปลี่ยนใน transaction เดียวกับงาน ถ้าเขียน log ไม่ได้ งานก็ไม่ถูกบันทึก ไม่มีตารางประวัติแยกต่อตาราง
- **เหตุผล:** ตอบ "ใครแก้อะไรเมื่อไร" ได้ที่เดียว ไม่มีตารางเพิ่ม และไม่มีงานที่บันทึกแล้วแต่ไม่มีร่องรอย
- **ถ้าผิด:** แก้ยาก — ประวัติที่ไม่ได้เก็บตั้งแต่แรกย้อนเก็บไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D05: ลบข้อมูลธุรกิจอย่างไร
- **คำตอบ:** soft delete ทุกตารางธุรกิจ คอลัมน์ `is_deleted`, `deleted_at`, `deleted_by`, `deleted_reason` (ไม่เกิน `audit.deleted_reason_max` ตัวอักษร) ตั้งพร้อมกันในการบันทึกเดียว ฐานข้อมูลปฏิเสธแถวที่ `is_deleted` กับ `deleted_at` ไม่ตรงกัน
- **เหตุผล:** แถวยังอยู่ให้ log และเอกสารเก่าอ้างถึงได้ `is_deleted` ทำให้เงื่อนไขและ index ง่าย ส่วน CHECK กันสองค่าขัดกัน
- **ถ้าผิด:** แก้ยาก — ทุกตารางและทุก query ที่ซ่อนแถวที่ลบ
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D06: แถวที่ลบแล้วซ่อนอย่างไร และค่าที่ห้ามซ้ำใช้ซ้ำได้ไหม
- **คำตอบ:** ทุก query ซ่อนแถวที่ลบด้วย filter ชื่อ `SoftDelete` ตัวเดียว เฉพาะมุมมองประวัติปิด filter นี้ได้ โดย filter อื่น (เช่นขอบเขตข้อมูล) ยังทำงาน กฎห้ามซ้ำของตารางที่ลบได้ไม่นับแถวที่ลบ จึงใช้ค่าเดิมสร้างแถวใหม่ได้
- **เหตุผล:** จุดเดียวที่ปิดได้ ตรวจได้ง่าย และผู้ใช้ไม่ติดค่าซ้ำจากแถวที่ลบไปแล้ว
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยน unique index เป็นแบบมีเงื่อนไขใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D07: ตารางไหนลบจริงได้
- **คำตอบ:** เฉพาะตารางชั่วคราวทางเทคนิค (เซสชัน การเข้าผิด โทเค็นรหัสผ่าน ไฟล์ที่รออัปโหลด ข้อมูลรอนำเข้า log การเรียกระบบภายนอก) ลบด้วยงานล้างตามอายุ โดยไม่ลง Activity Log ตารางอื่นลบแถวไม่ได้ และ architecture test หา bulk delete หรือ SQL `DELETE` นอกตารางเหล่านี้
- **เหตุผล:** ตารางชั่วคราวไม่ใช่ข้อมูลธุรกิจ ถ้าไม่ล้างจะโตไม่หยุด และการลบโทเค็นกับเซสชันที่หมดอายุช่วยด้านความปลอดภัย
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือลดรายชื่อตารางชั่วคราวใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D08: ชนิดคีย์หลัก
- **คำตอบ:** uuid v7 ทุกตาราง ยกเว้น `activity_log` ที่ใช้เลขรัน ตาราง catalog ที่ใช้ natural key และตารางบัญชีที่ใช้ `id` เดียวกับ `actor`
- **เหตุผล:** เดา id ใน URL ไม่ได้ เรียงตามเวลาสร้าง index ไม่แตก และเป็นกติกาเดียวที่ทุกคนจำได้
- **ถ้าผิด:** แก้ยาก — ชนิดคีย์และ FK ทุกตาราง
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D09: ตาราง master ที่ระบบอื่นอ้างด้วยรหัส ใช้รหัสเป็นคีย์หลักไหม
- **คำตอบ:** ใช้รหัสเป็นคีย์หลัก เมื่อรหัสไม่เปลี่ยนตลอดอายุแถว และระบบภายนอกอ้างแถวด้วยรหัสนั้น
- **เหตุผล:** FK และไฟล์ที่ส่งไปมาอ่านออกเอง ไม่ต้องแปลงรหัสกับ uuid ทุกครั้งที่เชื่อมระบบ
- **ถ้าผิด:** แก้ยาก — FK ของทุกตารางที่อ้างตาราง master นั้น
- **ถามเมื่อ:** มีตาราง master ที่ระบบภายนอกอ้างด้วยรหัส หรือรหัสนั้นเปลี่ยนได้
- **ตัวเลือกอื่น:** b) `id` เป็น uuid v7 และรหัสเป็น unique ทุกตารางอ้างด้วย `id`

### AUDIT-D10: หลายคนแก้แถวเดียวกันพร้อมกัน
- **คำตอบ:** ตารางที่หลายคนแก้ตรวจการแก้ซ้อน (optimistic concurrency) คนที่บันทึกทีหลังจากข้อมูลเก่าได้ข้อผิดพลาด ไม่เขียนทับของคนแรก
- **เหตุผล:** ไม่มีการแก้ที่หายไปเงียบๆ
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มคอลัมน์ตรวจรุ่นในตารางที่ขาด
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D11: ชื่อการกระทำใน log
- **คำตอบ:** ใช้ชื่อที่ Service ตั้ง (เช่น `Approve`, `Revoke`) ถ้าไม่ได้ตั้งเป็น `Create`, `Edit` หรือ `Delete`
- **เหตุผล:** อ่าน log แล้วรู้เจตนา ไม่ใช่แค่ว่าแถวเปลี่ยน
- **ถ้าผิด:** แก้ทีหลังได้ — log ใหม่ใช้ชื่อใหม่ log เก่าคงเดิม
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D12: ฟิลด์ลับใน log
- **คำตอบ:** ฟิลด์ที่ทำเครื่องหมายว่าลับ (hash รหัสผ่าน โทเค็น กุญแจ) บันทึกแค่ว่าเปลี่ยน ไม่มีค่าเก่าและค่าใหม่
- **เหตุผล:** log อ่านได้หลายคนและเก็บนาน ต้องไม่กลายเป็นที่รั่วของความลับ
- **ถ้าผิด:** แก้ยาก — ความลับที่ลง log ไปแล้วลบออกไม่ได้เพราะ log แก้ไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D13: แถวที่เป็นบันทึกในตัวเอง (คิวงาน log การส่ง log การซิงก์) ลง Activity Log ไหม
- **คำตอบ:** ไม่ลงรายการของตัวเอง มีแค่คอลัมน์ผู้ทำและเวลา การกระทำที่ทำให้เกิดแถวนั้น (เช่นการอนุมัติที่เข้าคิวอีเมล หรือคนที่สั่งรันด้วยมือ) ลงหนึ่งรายการ
- **เหตุผล:** แถวเหล่านี้เป็นหลักฐานอยู่แล้ว ลงซ้ำทำให้ log บวมโดยไม่ได้ข้อมูลเพิ่ม
- **ถ้าผิด:** แก้ทีหลังได้ — เปิดการลง log ของตารางนั้นใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D14: แก้ ลบ หรือเขียนทับ Activity Log ได้ไหม
- **คำตอบ:** ไม่ได้ role ของแอปในฐานข้อมูลไม่มีสิทธิ์ UPDATE หรือ DELETE บน `activity_log` และ API ไม่มีคำสั่งแก้หรือลบรายการ
- **เหตุผล:** log ที่แก้ได้ใช้เป็นหลักฐานไม่ได้
- **ถ้าผิด:** แก้ยาก — รายการที่ถูกแก้ไปแล้วพิสูจน์ย้อนไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D15: export Activity Log ได้ไหม
- **คำตอบ:** ไม่มีปุ่มหรือ API export จอแสดงอย่างเดียว
- **เหตุผล:** log มีข้อมูลส่วนบุคคลและค่าก่อนแก้ ไฟล์ที่ export ออกไปควบคุมไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม export ใน change ถัดไป
- **ถามเมื่อ:** เอกสารลูกค้าขอ export หรือผู้ตรวจสอบต้องได้ไฟล์
- **ตัวเลือกอื่น:** b) export CSV ตามตัวกรองเฉพาะผู้ถือ `{log_view_all_key}` และการ export ลง log หนึ่งรายการ

### AUDIT-D16: เก็บ Activity Log นานแค่ไหน
- **คำตอบ:** อย่างน้อย `audit.log_retention_months` เดือน และไม่มีงานล้าง log ในรุ่นแรก
- **เหตุผล:** กฎหมายและผู้ตรวจสอบของแต่ละลูกค้ากำหนดต่างกัน ค่าต่ำสุดต้องมาจากลูกค้า
- **ถ้าผิด:** แก้ยาก — log ที่ล้างไปแล้วเอาคืนไม่ได้
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) เก็บตามจำนวนเดือนที่ลูกค้ากำหนด แล้วย้ายไปที่เก็บถาวรก่อนล้าง c) เก็บตลอดไป

### AUDIT-D17: ใครเห็นแถวไหนของ Activity Log
- **คำตอบ:** ผู้ถือ `{log_view_all_key}` เห็นทุกแถว ผู้ถือแค่ `{log_view_key}` เห็นเฉพาะแถวที่ตัวเองทำ ไม่ว่ากรองอะไร ขอดูของคนอื่นได้หน้าว่าง ไม่ใช่ error ขอบเขตข้อมูลไม่จำกัดแถวของ log
- **เหตุผล:** กติกาสองชั้นอธิบายง่าย และคนทั่วไปตรวจงานของตัวเองได้
- **ถ้าผิด:** แก้ยาก — เป็นเรื่องสิทธิ์และการมองเห็นข้อมูล
- **ถามเมื่อ:** เอกสารลูกค้าให้หัวหน้าเห็น log ของลูกทีม หรือให้ขอบเขตข้อมูลจำกัด log
- **ตัวเลือกอื่น:** b) หัวหน้าเห็นแถวของคนในกลุ่มเดียวกัน c) ใช้ขอบเขตข้อมูลของผู้ดูกับเอกสารในแต่ละรายการ

### AUDIT-D18: แถวหลายแถวจากการบันทึกครั้งเดียวแสดงอย่างไร
- **คำตอบ:** หนึ่งการบันทึกเป็นหนึ่งรายการ (ผู้ทำ เวลา การกระทำ ชนิดเอกสาร และ id เอกสารเดียวกัน) การแบ่งหน้าและจำนวนนับเป็นรายการ ไม่ใช่แถว
- **เหตุผล:** ผู้ใช้คิดเป็น "กดอนุมัติหนึ่งครั้ง" ไม่ใช่จำนวนแถวที่ฐานข้อมูลเขียน
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการจัดกลุ่มตอนอ่าน ข้อมูลที่เก็บไม่เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D19: บทบาทของผู้ทำที่แสดงในรายการ
- **คำตอบ:** บทบาทที่เขียนพร้อมรายการ ณ เวลานั้น (ชื่อกลุ่มตอนทำ ชนิดบัญชี หรือ System) ไม่ใช่กลุ่มปัจจุบันของผู้ทำ
- **เหตุผล:** ผู้ตรวจต้องรู้ว่าทำในฐานะอะไรตอนนั้น
- **ถ้าผิด:** แก้ยาก — บทบาทในอดีตที่ไม่ได้เขียนไว้ย้อนหาไม่ได้
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D20: ตัวกรองและแท็บของจอ Activity Log
- **คำตอบ:** กรองด้วย ผู้ใช้ (รวม System) กลุ่มการกระทำ ชนิดเอกสาร และช่วงวันที่ พร้อมกันได้ เรียงใหม่สุดก่อนเสมอ ไม่มีการเรียงแบบอื่น แท็บ All, Access & authorization, Content, Documents แต่ละแท็บมีจำนวนตามตัวกรอง จอเปิดมาที่ `audit.default_range_days` วันล่าสุด และตัวกรองอยู่ใน address
- **เหตุผล:** ตอบคำถามที่ผู้ตรวจถามบ่อยที่สุด (ใคร ทำอะไร กับเอกสารไหน ช่วงไหน) และแชร์ลิงก์หน้าที่เห็นได้
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มตัวกรองหรือย้ายกลุ่มการกระทำโดยไม่เปลี่ยนข้อมูล
- **ถามเมื่อ:** ไม่ถาม

### AUDIT-D21: ชื่อผู้ทำที่แสดง
