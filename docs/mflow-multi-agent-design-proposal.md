# ข้อเสนอ: ให้ AI หลายตัวช่วยวิเคราะห์และออกแบบนอกเหนือจาก discuss

วันที่: 2026-10-03 · Revision: 0.2 · สถานะ: ข้อเสนอ ยังไม่ได้เพิ่มคำสั่งใน plugin

> ความคืบหน้า (2026-10-04): ผู้ใช้สั่งให้เริ่มแล้ว กำลังสร้างตามลำดับในหัวข้อ 8 โดยใช้ pipeline ร่วม `plugins/mflow/skills/delegate/references/consultation.md` และ `scripts/consult.mjs` ทำแล้ว: `/mflow:analyze` ยังไม่ได้ทำ: `/mflow:design`, `/mflow:challenge` ส่วนการรันเครื่องมือภายนอกอัตโนมัติ (หัวข้อ 7 ส่วนต่อยอด) ยังไม่ทำ เพราะ requirement §13 ระบุว่า mflow ไม่รัน AI tool อื่นเอง เนื้อหาด้านล่างคงไว้ตามข้อเสนอ

## 1. แนวทางที่แนะนำ

เพิ่ม **`/mflow:analyze`, `/mflow:design` และ `/mflow:challenge` เป็นคำสั่งเสริมแบบ optional ทั้งหมด** ผู้ใช้เลือกเรียกเมื่อต้องการความเห็นเพิ่มเติมจาก AI อื่น และเลือกไม่เรียกเลยได้

ทั้งสามใช้กลไกส่ง brief, รับรายงาน และตรวจหลักฐานร่วมกัน ไม่ควรทำระบบส่งงานใหม่สามชุด ส่วน `discuss` ยังคงเป็นที่คุยและยืนยันข้อตัดสินใจกับผู้ใช้ เมื่อผลวิเคราะห์มีตัวเลือกที่ต้องตัดสินใจจึงส่งประเด็นนั้นเข้า discuss ได้ โดยไม่บังคับให้ทุกงานต้องเริ่มจาก discussion document

### ข้อกำหนดที่ผู้ใช้ยืนยัน: optional และไม่ขวาง workflow หลัก

- เรียกเมื่อผู้ใช้สั่งเท่านั้น; skill ใหม่ตั้ง `disable-model-invocation: true` และ hooks/คำสั่งอื่นไม่เรียกทั้งสามคำสั่งให้อัตโนมัติ
- Workflow เดิมตั้งแต่ init, capture, theme, screen, hotspot ไปจนถึง OpenSpec propose/apply/review/archive ทำต่อได้โดยไม่ผ่านคำสั่งใหม่ และไม่ต้องมีไฟล์รายงานจากคำสั่งเหล่านี้
- เรียกแต่ละคำสั่งแยกกันได้: design ไม่ต้องผ่าน analyze; challenge รับแบบที่มีอยู่แล้วได้โดยไม่ต้องสร้างด้วย design
- AI แนะนำให้ใช้ได้เมื่อเกี่ยวข้อง โดยระบุว่าเป็นทางเลือก ไม่เพิ่มเป็น prerequisite, readiness gate, acceptance criterion หรือ task บังคับเพียงเพราะมีคำสั่งใหม่นี้
- หากเริ่มขอความเห็นแล้วมีรายงานค้าง ผู้ใช้ทำงานหลักต่อได้ สถานะ pending เป็นข้อมูลประกอบ ไม่ทำให้ project/task ถูกตั้ง blocked โดยอัตโนมัติ
- ผลจาก AI เป็นคำแนะนำที่ต้องตรวจหลักฐานก่อนนำไปใช้ ผู้ใช้เลือกใช้บางข้อ พักไว้ หรือไม่ใช้ได้ การเลือกไม่เรียกคำสั่งไม่ยกเลิกข้อกำหนดและการตรวจคุณภาพเดิมของงานหลัก
- แสดงงานปรึกษาใน briefing เป็นส่วน optional และไม่แทนที่ next action ของงานหลัก เว้นแต่ผู้ใช้เลือกให้งานปรึกษานั้นเป็นงานที่กำลังทำ

ข้อกำหนดนี้มาจากคำยืนยันของผู้ใช้ในวันที่ 2026-10-03; รายละเอียด implementation ส่วนอื่นยังเป็นข้อเสนอ

## 2. ความสามารถเดิมที่ต่อยอดได้

ปัจจุบัน [delegate skill](../plugins/mflow/skills/delegate/SKILL.md) รองรับหัวข้ออิสระและ `--mode analyze` อยู่แล้ว จึงใช้รูปแบบนี้ได้ทันที:

```text
/mflow:delegate "วิเคราะห์ภาพรวมระบบและเสนอจุดปรับปรุง" --mode analyze --to any
```

ระบบสร้าง brief และคำสั่งสำหรับเครื่องมือที่รองรับ ผู้ใช้เป็นคนรัน AI ภายนอก จากนั้นใช้ `/mflow:assess @docs/ai-inbox/<report>.md` ตรวจรายงานแต่ละฉบับ

สิ่งที่ยังควรเพิ่มเพื่อให้ได้ประสบการณ์ตามความต้องการ:

- ขอบเขตและรูปแบบผลลัพธ์เฉพาะงานวิเคราะห์ระบบกับงานออกแบบ
- การจัดกลุ่มหลายรายงานให้อยู่ในงานเดียวกัน มีรอบและ revision ที่ชัดเจน
- การเทียบข้อเสนอ ตรวจประเด็นที่ขัดกัน และสรุปคำแนะนำร่วม
- การติดตามว่า agent ใดตอบแล้ว ติดขัด หรืออ้าง source คนละฉบับ
- การนำข้อเสนอที่เลือกเข้าสู่ discuss, hotspot, Backlog หรือ OpenSpec อย่างตรวจย้อนกลับได้

คำสั่งใหม่ด้านล่างทั้งหมดเป็น syntax ที่เสนอ ไม่ใช่คำสั่งที่มีอยู่ในรุ่นปัจจุบัน

## 3. คำสั่งที่เสนอ

| คำสั่ง | คำถามที่ตอบ | ผลลัพธ์หลัก | เหมาะกับ |
|---|---|---|---|
| `/mflow:analyze <scope>` | ระบบตอนนี้ทำอะไร มีอะไรขาดหรือควรปรับ | ภาพรวมปัจจุบัน, ปัญหาที่มีหลักฐาน, gaps, ลำดับปรับปรุง | เริ่มรับช่วงระบบ, ตรวจ requirement, วิเคราะห์ legacy, หา bottleneck/ความเสี่ยง |
| `/mflow:design <topic>` | ควรสร้างหรือเปลี่ยนระบบอย่างไร | แบบเสนอ, ทางเลือก, trade-offs, contracts, diagrams ที่จำเป็น, migration/test plan | ออกแบบระบบใหม่หรือปรับ module/API/data/workflow |
| `/mflow:challenge @artifact` | ถ้าใช้แบบนี้ อะไรจะผิดพลาดหรือยังตอบไม่ได้ | counterexamples, failure scenarios, สมมติฐานที่อ่อน, การทดลองที่ใช้ตัดสิน | ตรวจแบบก่อนสร้างจริง หรือก่อนรับการเปลี่ยนแปลงที่มีผลกว้าง |

### 3.1 `/mflow:analyze` — วิเคราะห์สภาพจริงและเสนอสิ่งที่ควรทำ

ตัวอย่าง:

```text
/mflow:analyze system --to codex,gemini
/mflow:analyze "ระบบรับงานและจัดรถ" --focus workflow,data,permissions --to any
/mflow:analyze @docs/requirement.md --focus gaps,edge-cases
```

Output contract:

1. Understanding และ Files read ตาม contract เดิม
2. พฤติกรรมปัจจุบันพร้อมหลักฐาน; แยกจากสิ่งที่เอกสารระบุว่าควรเป็น
3. Findings ที่มี ID, ข้อกล่าวอ้าง, หลักฐาน, ผลกระทบ และ confidence
4. ข้อเสนอปรับปรุง พร้อมเหตุผลและลำดับความสำคัญ
5. สิ่งที่ยังตรวจไม่ได้ และข้อมูลหรือการทดลองที่จะช่วยตอบ

งานนี้จบได้ด้วยรายงาน ไม่จำเป็นต้องสร้างแบบใหม่หรือแก้ implementation ทุก finding ที่รับไว้ต้องแยกว่า “ยืนยันว่าพบจริง” กับ “อนุมัติให้ลงมือแก้”

### 3.2 `/mflow:design` — เสนอแบบและเปรียบเทียบทางเลือก

ตัวอย่าง:

```text
/mflow:design "ระบบสิทธิ์หลายบริษัท" --to codex,gemini
/mflow:design "โครงสร้างข้อมูลใบงานและค่าใช้จ่าย" --from @docs/analysis/AN-001/summary.md
/mflow:design "API สำหรับนำเข้าข้อมูล" --focus api,data,failure-recovery
```

Output contract:

1. ปัญหา เป้าหมาย constraints และสิ่งที่ไม่รวม
2. แบบที่แนะนำ และทางเลือกที่มีเหตุผลจริง โดยอาจคงโครงสร้างเดิมเป็นทางเลือกหนึ่ง
3. Business flow, module boundaries, data model หรือ API contract ตามขอบเขตที่ออกแบบ
4. การจัดการสิทธิ์, failure/retry, concurrency และข้อจำกัดที่เกี่ยวข้อง
5. Trade-offs ด้านความซับซ้อน ต้นทุนดำเนินงาน และการเปลี่ยนภายหลัง พร้อมสมมติฐานของการประเมิน
6. แผนเปลี่ยนจากระบบปัจจุบัน รวม compatibility/data migration เมื่อจำเป็น
7. Acceptance scenarios และวิธีพิสูจน์ว่าแบบใช้ได้
8. ข้อตัดสินใจที่ผู้ใช้ต้องเลือก; ใช้ `[เสนอ]`/`[อนุมาน]` แยกจากข้อเท็จจริง

ไม่บังคับให้ทุกงานมี diagram ครบทุกชนิด เช่นออกแบบ API หนึ่งชุดไม่จำเป็นต้องสร้าง sitemap ทั้งระบบ ข้อเสนอที่รับเลือกยังไม่แก้ `openspec/specs/` โดยตรง แต่ส่งต่อเป็น OpenSpec change หรือปลายทางของข้อเท็จจริงตาม workflow เดิม

### 3.3 `/mflow:challenge` — ตรวจแบบด้วยกรณีที่ทำให้แบบนั้นล้มเหลว

ตัวอย่าง:

```text
/mflow:challenge @docs/design/DS-001/proposal.md --to codex,gemini
/mflow:challenge @docs/design/DS-001/proposal.md --focus permissions,concurrency,recovery
```

ให้ agent ตรวจจากแบบและ source จริง โดยรายงานแต่ละข้อเป็น:

`Claim → Scenario/input → Expected → Failure or uncertainty → Evidence → Suggested test/fix`

ตัวอย่าง: “ผู้ใช้บริษัท A ส่ง ID ของบริษัท B ตรงเข้า API แล้วผลควรเป็นอย่างไร” หรือ “รับรายการสำเร็จแต่ network หลุดก่อนส่ง response เมื่อ retry จะสร้างซ้ำหรือไม่”

ข้อทักท้วงต้องมี scenario หรือหลักฐาน ไม่ต้องบังคับให้ agent หา defect ให้ครบจำนวน หากไม่พบให้ระบุขอบเขตที่ตรวจและข้อจำกัดได้ คำสั่งนี้ตรวจแบบได้ก่อนมี code diff จึงต่างจาก `/mflow:review` ที่มีอยู่

## 4. วิธีให้หลาย agent ทำงานร่วมกัน

เมื่อผู้ใช้เลือกเรียกคำสั่งใดคำสั่งหนึ่ง จึงใช้ workflow เสริมต่อไปนี้ร่วมกัน ทั้งสามคำสั่งไม่ได้เป็นขั้นตอนบังคับต่อเนื่องกัน:

```text
Scope + source snapshot
        ↓
Brief กลาง + คำถามเฉพาะบทบาท (ถ้ามี)
        ↓
รอบแรก: แต่ละ agent วิเคราะห์เอง
        ↓
ตรวจรายงานและหลักฐานราย finding
        ↓
รวมประเด็นซ้ำ + ตารางความเห็นต่าง + แบบที่เสนอ
        ↓
รอบสองเฉพาะประเด็นที่ยังขัดกัน (ถ้าจำเป็น)
        ↓
สรุปคำแนะนำ / ข้อตัดสินใจ / งานถัดไป
```

มีรูปแบบการแบ่งงานให้เลือกสองแบบ:

| รูปแบบ | การใช้ | ข้อจำกัด |
|---|---|---|
| วิเคราะห์อิสระในขอบเขตเดียวกัน | เปรียบเทียบทางเลือกหรือช่วยจับความเข้าใจผิด | ใช้เวลาและ context ซ้ำกัน แต่เปรียบเทียบคำตอบได้ตรงกว่า |
| แบ่งตามมุมมอง เช่น business/data/security | ระบบใหญ่หรือโจทย์หลายส่วน | ต้องมี agent ผู้รวบรวมตรวจข้อต่อระหว่างส่วน ไม่ถือว่าแต่ละส่วนถูกแล้วทั้งระบบจะเข้ากัน |

ให้ผู้ใช้หรือ brief กำหนดบทบาทตามโจทย์ ไม่ hardcode ว่าโมเดลยี่ห้อหนึ่งต้องถนัดด้านใดเสมอ รอบแรกไม่ส่งคำตอบของ agent อื่นให้ดู ส่วนรอบสองระบุชัดว่าเป็นการตอบข้อทักท้วงและอ้าง finding ID เดิม

**การรวมผลต้องไม่ใช้เสียงส่วนใหญ่แทนหลักฐาน:** ถ้า AI สามตัวเห็นด้วยแต่ไม่มี source รองรับ ต้องยังเป็นข้อเสนอหรือสมมติฐาน ส่วนความเห็นต่างต้องคงผู้เสนอ เหตุผล และวิธีตัดสิน ไม่ลบทิ้งเพื่อให้ summary ดูลงตัว

แนะนำเริ่มสอง agent ต่อโจทย์และไม่เกินสองรอบเป็นค่าเริ่มต้นที่ปรับได้ งานที่ไม่มีข้อขัดแย้งสำคัญจบได้ตั้งแต่รอบแรก

## 5. การจัดเก็บและสถานะ

โครงสร้างที่เสนอในโปรเจกต์ผู้ใช้ mflow:

```text
.mflow/consultations/<id>/session.json   metadata, revision, participants, snapshot
.mflow/briefs/<id>-r1-<role>.md        brief ตามกลไกเดิม
docs/ai-inbox/<id>-r1-<tool>.md        รายงานต้นฉบับตามกลไกเดิม
docs/ai-inbox/<id>-r1-<tool>.assessment.md
docs/analysis/AN-001/summary.md        ผลรวมงาน analyze
docs/design/DS-001/proposal.md         แบบเสนอของ design
docs/design/DS-001/comparison.md       เปรียบเทียบทางเลือกเมื่อจำเป็น
```

ผล challenge เก็บเป็นรายงานที่อ้าง path/hash/revision ของ artifact เป้าหมาย และลิงก์จากงานต้นทาง ไม่มีสำเนา proposal อีกชุดเพื่อเป็นแหล่งความจริงแข่งกัน

ข้อมูลสำคัญใน session record: ID, intent (`analyze/design/challenge`), scope, source snapshot, round, participants, expected report paths, per-agent status, report hashes และ next action ชื่อ `consultations` เป็นชื่อกลไกภายใน ไม่จำเป็นต้องเพิ่ม `/mflow:consult` อีกคำสั่งให้ผู้ใช้จำ

สถานะงานรวมที่เสนอ: `prepared → awaiting-reports → assessing → summarized` พร้อมผล completeness `complete/partial` แยกต่างหาก ส่วน decision status เป็น `proposed/selected/superseded` และไม่เปลี่ยนเป็น selected เพราะหลาย agent เห็นด้วยเอง

หาก agent บางตัวไม่ได้รันหรือ timeout ให้สรุปจากรายงานที่มีโดยติด partial และระบุส่วนที่ขาดได้ ผู้ใช้สามารถเพิ่มรายงานภายหลังเพื่อสร้าง summary revision ใหม่ แต่ผลลัพธ์เก่าที่ถูกเลือกแล้วต้องไม่ถูกเปลี่ยนโดยเงียบ ๆ

## 6. การต่อกับคำสั่งเดิม

| ผลที่ได้ | ส่งไปที่ไหน |
|---|---|
| ข้อเท็จจริงปัจจุบันและ gap ที่ตรวจแล้ว | analysis summary; งานแก้ไขส่ง Backlog ตามคำสั่งผู้ใช้ |
| ทางเลือกที่ต้องถามผู้ใช้ | `/mflow:discuss <topic>` พร้อม evidence/comparison ที่มีแล้ว |
| กฎธุรกิจยังไม่ชัดและต้องมีตัวอย่าง | `/mflow:hotspot <topic>` |
| แบบที่เลือกแล้วและเปลี่ยนพฤติกรรมระบบ | `/opsx:propose <change>` อ้าง design revision |
| งานเกิน baseline ที่อนุมัติไว้ | `/mflow:change-request <request>` |
| ต้องทดลองเพื่อเลือกทางออก | spike ticket ที่มีสมมติฐานและเกณฑ์ตัดสิน |
| งานที่ยังไม่คุ้มทำ | backlog ที่ระบุเหตุผล/เงื่อนไขกลับมาพิจารณา |

`delegate` รับผิดชอบส่งงาน, `assess` ตรวจความถูกต้องของรายงาน, `analyze/design/challenge` กำหนดเป้าหมายและรูปแบบผลรวม ส่วน `discuss` รับผิดชอบการตกลงกับผู้ใช้ บทบาทจึงต่อกันได้โดยไม่ทับซ้อนกันทั้งหมด

ควรเพิ่มการ assess ทั้ง session ภายใน workflow โดย reuse logic เดิม ไม่จำเป็นต้องเปิดคำสั่ง `/mflow:synthesize` ในรุ่นแรก การสรุปผลเป็นขั้นจบของ analyze/design/challenge ได้อยู่แล้ว

## 7. รูปแบบการเรียก agent

**ช่วงแรก: ผู้ใช้รันเครื่องมือภายนอกเองตามแบบปัจจุบัน** คำสั่งใหม่สร้าง briefs/commands/context packs และรวบรวมผล เหมาะกับการใช้ AI ต่างยี่ห้อโดยยังรักษาขอบเขตของ plugin ตาม requirement §13

**ส่วนต่อยอด: ให้ host เรียก subagent หรือ external runner อัตโนมัติ** ทำได้เป็นงานออกแบบแยก โดยต้องกำหนด host capability, tool permissions, งบเวลา/ค่าใช้จ่าย, cancel/retry, read-only workspace และสถานะ child process อย่าใช้ `applySubagent` เป็นสวิตช์เดียวกัน เพราะค่านั้นควบคุม `mflow:dev` สำหรับเขียนโค้ดระหว่าง apply

`design` และ `challenge` เป็น intent ของงาน แต่การเรียก `delegate-cmd.mjs` ในช่วงแรกใช้ execution mode `analyze` ที่มีอยู่ได้ พร้อม output contract เฉพาะ ไม่จำเป็นต้องทำให้ AI CLI ภายนอกรู้จัก mode ใหม่

การออกแบบให้รองรับหลาย agent ไม่ได้แปลว่ารันเครื่องมือเหล่านั้นอัตโนมัติแล้ว ต้องแสดงให้ผู้ใช้เห็นเสมอว่าอยู่ในโหมดสร้างคำสั่งหรือโหมดรันจริง

## 8. ลำดับพัฒนาและเกณฑ์รับ

1. เพิ่ม `/mflow:analyze` ก่อน: scope/snapshot, หลาย report, ตรวจหลักฐาน, รวม findings และส่ง next action
2. เพิ่ม `/mflow:design`: reuse pipeline เดิม เพิ่ม design contract และ comparison ของทางเลือก
3. เพิ่ม `/mflow:challenge`: ใช้เมื่อมีแบบให้ตรวจ และเชื่อมข้อทักท้วงกลับไป revision ต้นทาง
4. พิจารณา automatic execution หลัง pipeline แบบผู้ใช้รันเองใช้งานได้ครบวงจร

เกณฑ์รับร่วม:

- โปรเจกต์ที่ไม่เคยเรียกทั้งสามคำสั่งยังทำ workflow เดิมได้ครบ โดยไม่มี missing-report warning ที่ขวางงานหรือการบังคับให้สร้าง consultation
- เรียก design โดยไม่มี analyze และเรียก challenge กับเอกสารที่สร้างด้วยวิธีอื่นได้
- hooks และคำสั่งหลักไม่เรียกคำสั่งเสริมอัตโนมัติ; รายงานปรึกษาค้างไม่ block งานหลัก
- สอง agent ได้ source snapshot เดียวกันและ output paths ไม่ชนกัน
- findings ทุกข้อใน summary ตามกลับไปถึง report และ evidence ได้ รวมข้อที่ถูกปฏิเสธ
- source เปลี่ยนแล้วรายงานเก่าถูกระบุ stale; rerun ไม่สร้างงานซ้ำ
- ผลออกแบบแยก fact/proposal/assumption และรักษาความเห็นต่าง
- agent ขาดไปหนึ่งตัวไม่ทำสถานะงานหาย และผู้ใช้เลือกสรุป partial ได้
- ไม่มี production code หรือ spec หลักถูกแก้เพียงเพราะ AI เสนอให้แก้
- ผู้ใช้เลือกแบบหรือสั่งดำเนินการแล้ว ส่งต่อขอบเขตที่เลือกได้โดยไม่ขออนุมัติเรื่องเดิมซ้ำ

อ่านคู่กับ [รายงานวิเคราะห์หลัก](mflow-plugin-design-review.md) โดยเฉพาะ F03/F04 เรื่องการส่งบริบทและคำสั่ง, F07 เรื่องการทำต่อหลังล้มเหลว และ F08 เรื่อง snapshot/provenance
