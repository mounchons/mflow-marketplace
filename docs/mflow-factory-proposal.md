# ข้อเสนอ: mflow Software Factory

สถานะ: พักไว้ รอผู้ใช้อ่านรายละเอียดก่อน อาจมีการปรับเปลี่ยน ยังไม่สร้างจนกว่าผู้ใช้จะสั่ง ยังไม่มีการแก้ plugin (2026-11-09)
ที่มา: คำขอของผู้ใช้ 2026-11-09 ให้แสดงงานเป็นกล่องแบบกระดาน มี agent ประจำกล่องมากวาดงานเอง
ผลวิเคราะห์แบบ: ข้อ 12 (2026-11-10) ข้อ 1–11 ปรับตามผลนั้นแล้วเมื่อ 2026-11-10 (รายการในข้อ 12.6) เรื่องในข้อ 12.3 ผู้ใช้ตอบแล้ว: a

## 1. เป้าหมาย

- ใบงานเดินเป็นกล่อง: Requirement → Discuss → จัดคิว → Build → QA → Review → E2E → Done (merge)
- หลัง Discuss อนุมัติ agent จัดลำดับงานให้เดินต่อเนื่องหรือทำพร้อมกันได้
- ทุกกล่อง ถ้าติดหรือต้องตัดสินใจ ส่งมากล่อง Human
- ผู้ใช้กำหนด test case และ scenario เองได้ QA และ E2E ต้องตรวจและเพิ่มที่ยังไม่มี
- ให้ AI ตัวอื่นเช่น Codex มาทำบางกล่องได้ เช่น Claude build แล้ว Codex ทำ test

## 2. หลักการออกแบบ

1. **กระดานคือมุมมองของไฟล์** สถานะส่วนใหญ่มีอยู่แล้วในไฟล์ของ mflow ไม่สร้างฐานข้อมูลใหม่
2. **ต่อยอด `/mflow:apply-all`** สายงานเพิ่มคำสั่งเดียว `/mflow:factory` ส่วน Monitor แยกจากสายงาน วิธีเรียกยังไม่กำหนด ของเดิมเปลี่ยนเฉพาะที่อยู่ในตารางใต้หลักการ ที่เหลือไม่เปลี่ยน (ปรับ 2026-11-10 ตามข้อ 12.4)
3. **Foreman คือ session ของ Claude Code** Claude Code ไม่มี background process ที่รันค้างเอง Foreman วนกวาดกระดาน ส่ง subagent หรือ Codex ไปทำแต่ละกล่อง และหยุดเมื่อไม่มีงานเดินได้ ระหว่างรัน โฟลเดอร์ของโปรเจกต์เป็นของ Foreman ผู้เดียว เหมือน `apply-all` ผู้ใช้คุยต่อในช่วงที่ factory ไม่รัน (คำตอบข้อ 12.3)
4. **Gate อ่านจากไฟล์** การ merge ตัดสินจากหลักฐานในไฟล์ ไม่ใช่จากคำบอกของ agent
5. **คนตรวจไม่ใช่คนเขียน** QA และ Review แยกจาก Build เท่าที่ทำได้ กล่อง Review เขียนรายงานอย่างเดียว การแก้เป็นงานของ Build (ข้อ 4)

รุ่นแรกสายงานรับเฉพาะ change ที่มาจากเอกสาร discuss ที่อนุมัติ งานต้นแบบ hotspot และ CR แสดงบน Monitor อย่างเดียว (ปรับ 2026-11-10 ตามข้อ 12.4)

## 4. กติกาการเดินงาน

**กวาดงาน** Foreman ไล่จากกล่องขวาไปซ้าย เพื่อให้งานใกล้เสร็จออกก่อน กล่องไหนมีที่ว่างก็หยิบใบที่พร้อม

| กล่อง | จำนวนพร้อมกัน |
|---|---|
| Build | 2 |
| QA, Review, E2E, Merge | 1 |

**ไม่ผ่าน** QA, Review หรือ E2E ส่งกลับ Build พร้อมข้อที่พบ กล่อง Review เขียนรายงานอย่างเดียว ไม่ทำหัวข้อ 4 (Fix) ของ `/mflow:review` เอง แบบเดียวกับที่ `/mflow:night` แยกการแก้ออกจาก review (`skills/night/SKILL.md:56`) รอบนับแยกตามกล่องเหมือน apply-all: แต่ละกล่องส่งกลับได้สูงสุด 3 รอบ (`rounds`) เกินนั้นส่ง Human ใบที่มีกล่อง E2E จึงวนได้ถึง 9 รอบ ทั้งสองเรื่องเป็นค่าเริ่มต้น ผู้ใช้แก้ได้ (ปรับ 2026-11-10 ตามข้อ 12.4)

**ข้าม E2E** รุ่นแรกเปิดกล่องนี้เฉพาะใบที่มี case ระดับ e2e ของผู้ใช้ (ข้อ 7) ใบอื่นข้าม เพราะใบที่มีจอคือแทบทุกใบ จอของใบที่ข้ามรอ `/mflow:e2e` ที่ผู้ใช้สั่งเองตามเดิม E2E จำกัด browser ตาม `e2eMaxWorkers` เดิม (ปรับ 2026-11-10 ตามข้อ 12.4)

## 5. การจัดลำดับ

Planner อ่าน `order` จาก `packs.mjs selected`, `sources:` ของเอกสาร, "ควรคุยก่อน" ใน AGENDA และสิ่งที่แต่ละใบจะแตะ (ตาราง route จอ ไฟล์ร่วม) แล้วส่งแผนให้ผู้ใช้ตอบครั้งเดียว

| กรณี | การเดินงาน |
|---|---|
| ใบหนึ่งใช้ตารางหรือ endpoint ของอีกใบ, pack `requires` | ทำต่อกัน ใบหลังรอใบแรก merge |
| มี migration ทั้งสองใบ | ทำต่อกัน เพราะ model snapshot ชนกัน |
| ไม่พึ่งกัน ไฟล์ไม่ทับ migration ไม่เกินหนึ่งใบ | Build พร้อมกันได้ ไม่เกิน 2 ใบ ใบละ worktree |
| QA, E2E, Merge | ทีละใบเสมอ เพราะใช้ฐานข้อมูล port และ browser ร่วมกัน |
| `main` ขยับระหว่างที่ใบหยุดรอ (รอ Human หรือรอใบอื่น) | ดึง `main` เข้า branch ทันทีที่ใบกลับมาเดินต่อ ก่อน test และ review ที่เหลือ review หลังจากนั้นเป็นแบบเต็มของ branch (`git diff main...<branch>`) ไม่ใช่ `--short` gate ไม่ผ่านถ้า branch ไม่มี `main` ล่าสุด (ข้อ 9) |
| conflict ใน `docs/reviews/pending.md` หรือ `STATUS.md` ตอนดึง `main` | Foreman แก้เองตามกฎตายตัว: `pending.md` เก็บแถวของทั้งสองฝั่ง `STATUS.md` เขียน `## Now` ใหม่ conflict ในไฟล์อื่นส่ง Human |
| ใบที่ผ่าน review แล้ว `main` ขยับ (เกิดเมื่อทำพร้อมกัน) | review ซ้ำผ่านสคริปต์ยังไม่ได้ ต้องแก้ก่อนเปิดขั้นที่ 7 (ข้อ 9) |

สามแถวท้ายปรับ 2026-11-10 ตามข้อ 12.2 เดิมเขียนว่าดึง `main` แล้ว test อีกรอบก่อน merge

Worktree อยู่ที่ `.mflow/wt/<n>` ในโปรเจกต์ (เพิ่มใน `.gitignore`) ชื่อสั้นเพราะเครื่องจำกัด path 260 ตัวอักษร ใบหนึ่งมี worktree เดียว ทุกกล่องของใบนั้นทำในนั้น เพราะ branch หนึ่งเปิดได้ worktree เดียว (ผลทดลองข้อ 12.2)

## 6. กล่อง Human

| ประเภท | ตัวอย่าง |
|---|---|
| ต้องเลือก | spec ไม่ได้บอกสิทธิ์หรือกฎธุรกิจ agent ห้ามเดา |
| เครื่องมือติด | Docker ไม่ทำงาน, stack ไม่ขึ้น, ไม่มีสิทธิ์ |
| แก้ไม่ผ่านครบรอบ | ครบ 3 รอบแล้วยังไม่ผ่าน พร้อมรายงาน |
| ยืนยันแผน | แผนคิว, merge conflict ที่ agent ไม่ควรตัดสินเอง |

ทุกเรื่องมีเลขข้อ ตัวเลือก a) b) c) และคำแนะนำ ตอบรวมครั้งเดียวได้ เช่น `1 a, 2 b`

ตอบแล้ว Foreman เขียนคำตอบลงเอกสารของใบก่อน แล้วใบจึงกลับกล่องเดิม: เรื่องของ change นั้นเองลง `proposal.md` ของ change พร้อมวันที่ตอบ เรื่องที่ใบอื่นต้องใช้ด้วยไปที่เอกสาร discuss ผ่าน `/mflow:discuss` เหมือน apply-all ไฟล์ `human.md` อยู่ใน `.git/` จึงเป็นคิวคำถาม ไม่ใช่ที่เก็บคำตอบ ใบที่ archive แล้วเขียนคำตอบที่ไหน กำหนดตอนสร้าง (ปรับ 2026-11-10 ตามข้อ 12.4)

ต่างจาก apply-all ที่ใบแรกที่ติดหยุดทั้งรอบ ที่นี่หยุดเฉพาะใบนั้นและใบที่พึ่งมัน ใบที่กลับมาเดินต่อดึง `main` เข้า branch ก่อน (ข้อ 5)

## 7. Test case ของผู้ใช้

ไฟล์ `docs/test-cases/<NN>-<slug>.md` ตั้งชื่อตามเอกสาร discuss ที่ case นั้นเป็นของ เพราะชื่อ change เกิดตอนวางแผน หลังผู้ใช้เริ่มเพิ่ม case ได้แล้ว change อ่าน case ของเอกสารที่แผนผูกไว้ (`<change>=<NN>`) (ปรับ 2026-11-10 ตามข้อ 12.4 เดิมตั้งชื่อตาม change)
ไฟล์ใช้รูปแบบ `## Cases` ของ mtest (`Case, Path, Kind, Expect, Level, Test`) เพิ่มคอลัมน์ `From` ค่าเป็น `user`, `spec` หรือ `agent`
mflow ยังไม่มี `flows.mjs` ต้องมีตัวตรวจของตัวเอง เพราะโปรเจกต์ที่ใช้ mflow อาจไม่ได้ติดตั้ง mtest

- ผู้ใช้เพิ่มได้ตั้งแต่ Discuss และเมื่อไรก็ได้ก่อน merge โดยแก้ไฟล์นี้ในช่วงที่ factory ไม่รัน (คำตอบข้อ 12.3) Monitor อ่านอย่างเดียว จึงไม่มีการเพิ่มผ่านกระดาน
- Scenario ใน spec นับเป็น case `spec` ให้เอง
- QA ตรวจระดับ unit และ integration, E2E ตรวจระดับ e2e ถ้ายังไม่มี test ให้เขียนแล้วรัน
- case `user` ที่ไม่มี test E2E นับเป็นช่องโหว่ ต่างจากกติกา mtest ที่รอคำสั่ง
- agent ลบหรือแก้ผลที่คาดของ case `user` ไม่ได้ ถ้าทำตามไม่ได้ส่ง Human
- Merge ไม่ผ่านถ้ารายงาน review ไม่ได้ยืนยัน case `user` ครบทุกข้อ กล่อง Review ไล่ทีละข้อว่า test ในช่อง `Test` มีอยู่จริง ไม่ถูก skip และตรวจผลตามช่อง `Expect` แล้วเขียนผลต่อข้อในรายงาน gate อ่านผลจากรายงานนั้น เพราะ record ของ `/mflow:test` เก็บแค่ยอดต่อ part กับรายการที่ fail จึงบอกไม่ได้ว่า test ชื่อใดผ่าน (ปรับ 2026-11-10 ตามข้อ 12.4)
- เพิ่ม case หลังผ่านกล่องที่ต้องตรวจไปแล้ว ใบย้อนกลับกล่องนั้น

## 8. ให้ Codex มาช่วย

```json
"factory": {
  "route": { "build": "claude", "qa": "codex", "review": "claude", "e2e": "claude" },
  "slots": { "build": 2, "qa": 1, "review": 1, "e2e": 1 },
  "rounds": 3
}
```

- ใช้ registry ใน `.mflow/config.json` และ `delegate-cmd.mjs` ที่มีอยู่
- Codex ทำใน worktree ของใบนั้น ซึ่งมีอันเดียวต่อใบ (ข้อ 5) sandbox `workspace-write` อาจต่อเน็ตไม่ได้ เช่น NuGet restore
- ต้องพิสูจน์ก่อนเปิดกล่องนี้: Codex รัน integration test ใน sandbox ได้หรือไม่ ถ้าไม่ได้ `qa: codex` หมายถึง Codex เขียน test และ Claude รันแล้วเขียน record (ปรับ 2026-11-10 ตามข้อ 12.4)
- Review ของ Codex บนโค้ดของตัวเองไม่นับเป็นเงื่อนไข merge (FR-220)
- E2E ต้องเป็น Claude เพราะ hook `e2e-guard` อยู่ใน Claude Code (FR-221)
- ผลนับจาก record `By: codex` ที่รันจริง
- brief ต้องอยู่นอก branch เพราะ gate 0.44.2 ไม่นับไฟล์ที่สั่ง AI เป็นเอกสาร

**คำตอบของผู้ใช้ 2026-11-09: a)** `/mflow:factory` รัน Codex เองได้ เมื่อ `route` ของโปรเจกต์ระบุไว้ คำสั่งอื่นยังเป็นไปตาม FR-101 เมื่อสร้างกล่องนี้ต้องแก้ FR-101 และ FR-180 ใน `docs/requirement.md` ให้ตรงกัน

**ข้อขัดแย้งที่ตัดสินแล้ว:** FR-101 บอกว่า mflow ไม่รัน AI tool อื่นเอง (ตั้งใจ) และ FR-180 ให้ผู้ใช้รันเครื่องมือภายนอกเอง

| ตัวเลือก | ผล |

ที่มาของแต่ละข้อ: **ทดลอง** คือรันจริงใน repo ชั่วคราว, **โค้ด** คืออ่านจากโค้ดหรือ skill ยังไม่ได้รัน, **รอพิสูจน์** คือต้องดูตอนใช้จริง

### 12.1 สรุป

ต้องปรับ จุดใหญ่มีข้อเดียว: `apply-all` ออกแบบบนเงื่อนไขว่าใบงานไม่ซ้อนเวลากัน แต่ข้อ 6 (หยุดเฉพาะใบที่ติด ใบอื่นเดินต่อ) ทำให้ใบงานซ้อนกันตั้งแต่ขั้นที่ 4 ของข้อ 10 ไม่ใช่ขั้นที่ 7 เรื่องที่เหลือเป็นข้อรอง แก้เมื่อถึงขั้นนั้นได้ (ข้อ 12.4)

### 12.2 จุดใหญ่: ใบงานซ้อนเวลากัน

สิ่งที่ของเดิมอาศัย (โค้ด):

| ของเดิม | ที่อยู่ | ใช้ได้เพราะ |
|---|---|---|
| ใบแรกที่ติดหยุดทั้งรอบ | `skills/apply-all/SKILL.md:44` | `main` ไม่ขยับใต้ branch ที่ค้าง |
| ต้องอยู่บน `main` และ tree สะอาด | `apply-all.mjs:63-78` | โฟลเดอร์เป็นของ run ผู้เดียว |
| gate นับโค้ดทุกไฟล์หลัง commit ที่ review | `apply-all.mjs:306` | branch มีแต่งานของใบนั้น |
| `pending.md` และ `STATUS.md` ถูกแก้บน branch ของทุกใบ (`status-guard.mjs:19` ยกเว้นเฉพาะ `fix/*-review`, `fix/night-*` และ `e2e/night-*`) | `skills/apply-all/SKILL.md:57-65` | มีผู้เขียนทีละใบ |

ลำดับที่ข้อ 6 สร้าง: ใบ A ติดรอผู้ใช้ → ใบ B ผ่านและ merge → ผู้ใช้ตอบ → A เดินต่อบน `main` ตัวเก่า

**ผลทดลองชุดแรก: สองใบซ้อนกัน** ใน repo ชั่วคราว ด้วย `pending.mjs` และ `apply-all.mjs gate` ตัวจริง สองใบแตกจาก `main` เดียวกัน A ผ่าน test และ review แล้ว B merge ก่อน:

| ทดลอง | ผล |
|---|---|
| gate ของ A ก่อน `main` ขยับ | `ready: true` ซึ่งถูกต้อง |
| gate ของ A หลัง B merge เข้า `main` | `ready: true` ทั้งที่ A ไม่เคย test ร่วมกับ B |
| `git merge main` เข้า branch ของ A | conflict ใน `docs/reviews/pending.md` และ `STATUS.md` |
| gate ของ A หลังรวม `main` และ whole suite ผ่านอีกรอบ | `ready: false` ด้วยเหตุ `code changed after the review at …` เพราะไฟล์โค้ดของ B อยู่ในส่วนต่าง |
| เปิด worktree ที่สองบน branch ที่เปิดอยู่แล้ว | git ปฏิเสธ: `already used by worktree` |

ข้อจำกัดของผลทดลอง:
- `pending.md` ชนเมื่อแถวของทั้งสองใบอยู่ใต้ `## Done` ถ้าอยู่คนละตาราง git รวมได้เอง
- conflict ของ `STATUS.md` มาจากการจำลองการเขียน `## Now` ตามที่ skill สั่ง ไม่ใช่จากสคริปต์จริง
- สภาพที่ทดลองคือใบที่ผ่าน review แล้ว ใบที่ติดจะมาถึงสภาพนี้เมื่อเดินต่อจนผ่านโดยไม่ดึง `main` เข้ามาก่อน
- วิธีทำซ้ำ: แต่ละใบมีโฟลเดอร์ archive ของ change, ไฟล์โค้ดหนึ่งไฟล์, `pending.mjs add`, record `Scope: whole suite` ที่ผ่าน, `tick-test`, รายงานที่มี `Reviewed: … at <commit>`, `tick-review --verdict approve`, แก้บรรทัดใต้ `## Now` แล้ว commit

**ผลทดลองชุดที่สอง: กล่อง E2E หลัง Review** ใบเดียว ใช้ `pending.mjs` และ gate ตัวจริง ส่วน record และรายงานเขียนด้วยมือ ยังไม่ได้รัน `/mflow:review --short` จริง:

| B. ยังไม่ tick จนกว่า review ปิดท้ายหลัง E2E ผ่าน | ยังอยู่ | สำเร็จ แถวย้ายไป Done | `ready: true` |
