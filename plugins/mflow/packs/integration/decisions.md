# integration: ข้อที่ตอบไว้แล้ว

### INTG-D01: โค้ดธุรกิจเรียกระบบภายนอกอย่างไร
- **คำตอบ:** ผ่าน port หนึ่งตัวต่อ `{external_system}` เท่านั้น port มีหนึ่ง method ต่อ `{operation}` รับและคืนค่าเป็นชนิดของระบบเรา โค้ดธุรกิจไม่รู้จัก HTTP, URL, token หรือรูปแบบ JSON ของอีกฝั่ง ตัว implement มีสองตัว (ของจริงกับของปลอม) เลือกด้วย env และมี architecture test ห้ามเรียก HTTP นอกโฟลเดอร์ของ port
- **เหตุผล:** กติกา timeout การลองใหม่ และ log อยู่ที่เดียว เปลี่ยนรุ่น API หรือเปลี่ยนผู้ให้บริการได้โดยโค้ดธุรกิจไม่รู้ตัว และทดสอบโดยไม่ต้องมีระบบจริง
- **ถ้าผิด:** แก้ยาก — ถ้าโค้ดธุรกิจเรียก HTTP เองกระจายไปแล้ว ต้องไล่รื้อทุกจุด
- **ถามเมื่อ:** ไม่ถาม

### INTG-D02: คุยกับระบบไหนบ้าง ทิศไหน ใครเริ่ม ใครเป็นเจ้าของข้อมูล
- **คำตอบ:** ตารางเดียวในเอกสาร discuss หนึ่งแถวต่อ `{operation}`: `{external_system}`, ทิศทาง (ดึงเข้า ส่งออก รับเข้า), ตัวกระตุ้น (ตามรอบ เหตุการณ์ในระบบ ปุ่มของผู้ใช้ webhook), ความถี่หรือเหตุการณ์ที่กระตุ้น, เจ้าของข้อมูล ระบบที่เป็นเจ้าของคือคนตัดสินเมื่อค่าไม่ตรงกัน อีกฝั่งเก็บเป็นสำเนา และ port ไม่มี method ที่ไม่อยู่ในตาราง
- **เหตุผล:** ถ้าไม่ตกลงว่าใครเป็นเจ้าของ ข้อมูลสองฝั่งจะเขียนทับกันเงียบๆ ส่วนรายชื่อเส้นบอกงานทดสอบและของปลอมได้ครบ
- **ถ้าผิด:** แก้ยาก — ข้อมูลที่ถูกเขียนทับจากผิดฝั่งแล้วแยกไม่ออกว่าค่าไหนถูก
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ระบบนี้เป็นเจ้าของทุกอย่าง อีกฝั่งอ่านอย่างเดียว c) ทั้งสองฝั่งแก้ได้ และกำหนดกติกาชนกันเป็นรายฟิลด์

### INTG-D03: address ผู้ใช้ และความลับ อยู่ที่ไหน
- **คำตอบ:** บนหน้าตั้งค่าระบบ แท็บละหนึ่งระบบ ตาม SET-D03 ความลับใช้ชนิดความลับของแพ็ก settings (SET-D08, SET-D09) ค่ายังไม่ครบ API ยัง start ได้ งานเขียนรอในคิวโดยไม่นับเป็นการลอง คำขอที่ต้องใช้ตอบ 503 และจอติดตามบอกว่ายังไม่ได้ตั้ง
- **เหตุผล:** ผู้ดูแลเปลี่ยนรหัสตามรอบของอีกฝั่งได้เองโดยไม่ต้องรอคน deploy และระบบขึ้นก่อนแล้วค่อยตั้งได้โดยไม่มีงานหาย
- **ถ้าผิด:** แก้ทีหลังได้ — ย้ายค่าระหว่าง env กับจอได้ด้วยกติกาค่าตั้งต้นครั้งแรก (SET-D07)
- **ถามเมื่อ:** เอกสารลูกค้าหรือฝ่ายความปลอดภัยห้ามเก็บรหัสผ่านของระบบอื่นในฐานข้อมูล หรือบังคับใช้ secret store
- **ตัวเลือกอื่น:** b) address และความลับอยู่ใน env หรือ secret store เปลี่ยนแล้ว restart c) address อยู่บนจอ ความลับอยู่ใน env

### INTG-D04: กันเครื่องทดสอบเรียกระบบจริงอย่างไร
- **คำตอบ:** env `INTEGRATION_ALLOWED_HOSTS` บอก host ที่เครื่องนี้เรียกได้ address บนจอที่ host ไม่อยู่ในรายการบันทึกไม่ได้ และถูกปฏิเสธอีกครั้งตอนเรียก โหมด live แล้วรายการว่าง API ไม่ start นอก Development และ Prototype ใช้ https เท่านั้น และไม่ตาม redirect
- **เหตุผล:** ฐานข้อมูล Production ที่คัดลอกมาลงเครื่องทดสอบพา address และความลับของจริงมาด้วย ส่วนรายการ host ใน env อยู่กับเครื่อง จึงเรียกของจริงไม่ได้ และ URL ที่ตั้งบนจอไม่กลายเป็นทางยิงเข้าเครือข่ายภายใน
- **ถ้าผิด:** แก้ยาก — ข้อมูลทดสอบถูกเขียนลงระบบจริงของลูกค้า
- **ถามเมื่อ:** ลูกค้าต้องย้าย host ของระบบภายนอกเองโดยไม่ผ่านคน deploy
- **ตัวเลือกอื่น:** b) ไม่มีรายการ host ขั้นตอน restore ฐานข้อมูลต้องล้างค่าเชื่อมต่อทุกครั้ง c) address อยู่ใน env ทั้งหมด

### INTG-D05: รอนานแค่ไหน
- **คำตอบ:** ทุกการเรียกมีเวลารอ ไม่มีการเรียกที่รอไม่จำกัด: เชื่อมต่อ `integration.connect_timeout_seconds` วินาที ในคำขอของผู้ใช้ `integration.request_timeout_seconds` วินาทีต่อครั้งและ `integration.request_total_seconds` วินาทีรวม ในงานเบื้องหลัง `integration.job_timeout_seconds` วินาทีต่อครั้ง ไฟล์ `integration.file_timeout_seconds` วินาที การยกเลิกจากผู้ใช้หรือการหยุดระบบยกเลิกการเรียกด้วย
- **เหตุผล:** อีกฝั่งที่ค้างต้องไม่ทำให้หน้าจอหรือ thread ของเราค้างตาม ส่วนงานเบื้องหลังรอได้นานกว่าคนที่ยืนรอหน้าจอ
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับค่าได้โดยไม่กระทบข้อมูล
- **ถามเมื่อ:** ไม่ถาม

### INTG-D06: ลองใหม่เมื่อไร และห้ามลองใหม่เมื่อไร
- **คำตอบ:** ตัดสินจากตารางเดียวใน port: 2xx ถือว่าสำเร็จ (ค้นแล้วไม่พบคือผลว่าง ไม่ใช่ error) · 400 403 422 และ 4xx อื่นต้องมีคนแก้ ไม่ลองเอง · 401 ขอ token ใหม่แล้วส่งซ้ำหนึ่งครั้ง ครั้งที่สองคือ Unauthorized · 404 และ 409 เป็น Review ไม่ส่งซ้ำ ยกเว้นการลบที่ได้ 404 ถือว่าลบแล้ว · 408 429 และ 5xx ลองใหม่ ถ้ามี `Retry-After` รอตามนั้น · 503 คือระบบไม่พร้อม · ไม่มีคำตอบภายในเวลาคือผลไม่แน่ชัด งานอ่านลองในการเรียกเดียวรวม `integration.read_attempts` ครั้ง เว้นช่วงยาวขึ้น งานเขียนไม่ลองในการเรียกเดียว แต่กลับเข้าคิวตาม `integration.outbox_retry_minutes` จนสำเร็จ
- **เหตุผล:** รหัส 4xx ส่งกี่ครั้งก็ได้ผลเดิม ส่วนงานเขียนที่ลองซ้ำอัตโนมัติอาจบันทึกซ้ำ เช่นอีกฝั่งบันทึกแล้วแต่ตอบ 500 คลิกเดียวจึงกลายเป็นหลายแถว
- **ถ้าผิด:** แก้ยาก — งานเขียนที่เกิดซ้ำบนระบบของลูกค้าตามลบทีหลังยาก
- **ถามเมื่อ:** ไม่ถาม

### INTG-D07: กันงานเขียนเกิดซ้ำอย่างไร
- **คำตอบ:** ทุกงานเขียนมีคีย์กันซ้ำหนึ่งค่าที่สร้างครั้งเดียว ส่งเหมือนเดิมทุกครั้งที่ลอง ใน header `Idempotency-Key` เมื่ออีกฝั่งรับ อีกฝั่งไม่รับ เมื่อผลไม่แน่ชัด (หมดเวลา) อ่านจากอีกฝั่งก่อนว่างานนี้เกิดแล้วหรือยัง อ่านแล้วบอกไม่ได้เป็น Review ให้คนตัดสิน ไม่ส่งซ้ำเอง
- **เหตุผล:** การหมดเวลาไม่ได้แปลว่าอีกฝั่งไม่ได้ทำ คีย์กันซ้ำหรือการอ่านก่อนส่งคือสองวิธีที่รู้ได้จริง
- **ถ้าผิด:** แก้ยาก — ใบแจ้งหนี้หรือรายการจ่ายเงินซ้ำบนระบบของลูกค้า
- **ถามเมื่อ:** อีกฝั่งไม่มีทั้งคีย์กันซ้ำและเส้นอ่านผล หรือเอกสารของอีกฝั่งยังไม่บอก
- **ตัวเลือกอื่น:** b) ไม่ส่งซ้ำเมื่อผลไม่แน่ชัด ทุกรายการเป็น Review c) ยอมให้ส่งซ้ำได้ เพราะอีกฝั่งเขียนทับค่าเดิมอยู่แล้ว (เช่นอัปเดตสถานะ)

### INTG-D08: งานเขียนออกไปอย่างไรเมื่อต้องอยู่รอดถ้าระบบล้ม
- **คำตอบ:** งานธุรกิจเขียนแถวลง `integration_outbox` ใน transaction เดียวกับงานนั้น แล้วตัวส่งซึ่งเป็นงานเบื้องหลังหยิบไปส่งเรียงตามเวลา งานที่ rollback ไม่มีอะไรออก หนึ่งรายการล้มไม่หยุดรายการอื่น แถวไม่ถูกลบ เนื้อหาถูกล้างเมื่อส่งแล้วครบ `audit.call_log_days` วัน มีกติกาเดียวกับคิวอีเมล
- **เหตุผล:** งานที่บันทึกแล้วไม่หาย และอีกฝั่งช้าหรือล่มไม่ทำให้หน้าจอค้าง
- **ถ้าผิด:** แก้ยาก — ทุกจุดที่เขียนออกต้องเปลี่ยน และงานที่บันทึกแล้วแต่ไม่ได้ส่งย้อนหายาก
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ปุ่มเรียกอีกฝั่งก่อนบันทึก ถ้าสำเร็จจึงบันทึก (ผู้ใช้เห็นผลทันที แต่อีกฝั่งสำเร็จแล้วเราบันทึกไม่ได้ต้องมีงานซ่อม) c) เรียกตรงในคำขอ ล้มก็บอกผู้ใช้ให้กดใหม่ ไม่มีคิว (เฉพาะงานที่หายได้)

### INTG-D09: ดึงข้อมูลเข้าจากจุดไหน
- **คำตอบ:** ตาราง `integration_cursor` หนึ่งแถวต่อ `{operation}` ขาเข้า เก็บเวลาสิ้นสุดของการดึงครั้งล่าสุดที่อ่านจนหน้าสุดท้าย รอบใหม่อ่านตั้งแต่เวลานั้นลบ `integration.cursor_overlap_minutes` นาที จนถึงตอนนี้ รอบที่หยุดกลางทางไม่ขยับจุดนี้ รอบแรกไม่มีขอบล่าง การนำเข้าต้องทำซ้ำรายการเดิมแล้วผลเหมือนเดิม
- **เหตุผล:** ช่วงซ้อนกันรายการที่อีกฝั่งบันทึกช้า และไม่เสียข้อมูลเมื่อระบบล้มกลางรอบ
- **ถ้าผิด:** แก้ทีหลังได้ — ดึงย้อนหลังใหม่ได้เพราะการนำเข้าทำซ้ำได้
- **ถามเมื่อ:** อีกฝั่งไม่มีเวลาแก้ไขล่าสุดให้กรอง หรือรอบแรกมีข้อมูลเก่ามากจนต้องจำกัด
- **ตัวเลือกอื่น:** b) ใช้ token หรือเลขลำดับที่อีกฝั่งให้มาแทนเวลา c) รอบแรกดึงย้อนหลังตามจำนวนวันที่กำหนด

### INTG-D10: บันทึกอะไรต่อการเรียกหนึ่งครั้ง
- **คำตอบ:** `integration_call_log` หนึ่งแถวต่อการเรียกจริงหนึ่งครั้ง รวมการขอ token: เวลา ระบบ `{operation}` ผู้เรียก (รอบงาน แถวในคิว หรือบัญชีของคำขอ) รหัสตอบกลับ ผล ระยะเวลาที่วัดได้ ข้อความจากอีกฝั่ง request id และ body ที่ปิดบังความลับและตัดที่ `integration.body_log_bytes` ไบต์ header ไม่ถูกเก็บ การเรียกที่ล้มมีรหัสอ้างอิงซึ่งแสดงให้ผู้ใช้เห็นในข้อความผิด
- **เหตุผล:** ผู้ใช้อ้างรหัสเดียวแล้วทีมหาการเรียกนั้นเจอ และ log อ่านได้หลายคนจึงต้องไม่มีความลับ
- **ถ้าผิด:** แก้ยาก — ความลับที่ลง log ไปแล้วถือว่ารั่ว
- **ถามเมื่อ:** ไม่ถาม

### INTG-D11: เก็บ log การเรียกนานแค่ไหน
- **คำตอบ:** `audit.call_log_days` วัน แล้วงานล้างลบจริง ตารางชั่วคราวตาม AUDIT-D07 ไม่ลง Activity Log (AUDIT-D13) เส้นอ่านหรือดาวน์โหลดปริมาณมากที่สำเร็จไม่เก็บทีละแถว แต่นับรวมต่อชั่วโมงใน `integration_call_hourly` ที่อายุเท่ากัน การเรียกที่ล้มเก็บทีละแถวเสมอ
- **เหตุผล:** log ไม่โตไม่หยุด และจอติดตามยังนับเส้นดาวน์โหลดหลายพันครั้งต่อวันได้โดยไม่เก็บซ้ำทุกครั้ง
- **ถ้าผิด:** แก้ยาก — log ที่ล้างไปแล้วเอาคืนไม่ได้
- **ถามเมื่อ:** เอกสารลูกค้ากำหนดอายุ log การเชื่อมต่อ หรือต้องเก็บทุกการเรียกเป็นหลักฐาน
- **ตัวเลือกอื่น:** b) เก็บทุกการเรียกทีละแถว รวมการอ่านที่สำเร็จ แบ่ง partition รายเดือน c) เก็บเฉพาะการเรียกที่ล้ม

### INTG-D12: ระบบภายนอกล่มแล้วเกิดอะไร
- **คำตอบ:** ผู้ใช้: หน้าที่ไม่ต้องใช้อีกฝั่งทำงานปกติ ข้อมูลที่ดึงไว้แล้วยังแสดงพร้อมเวลาที่ดึง คำขอที่ต้องใช้อีกฝั่งตอบ 503 `<SYSTEM>_UNAVAILABLE` พร้อมรหัสอ้างอิง งานเขียน: รออยู่ในคิว รอบดึงเข้า: เจอ 503 หรือเชื่อมต่อไม่ได้แล้วหยุดทั้งรอบ เป็นรอบที่ล้ม รายการที่ทำแล้วคงอยู่ และรอบใหม่เริ่มใน `integration.down_rerun_minutes` นาที ไม่ขยับ cursor
- **เหตุผล:** ระบบเราไม่ควรล่มตามอีกฝั่ง และงานเขียนหลายร้อยรายการไม่ควรยิงซ้ำใส่ระบบที่กำลังล่ม
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนสิ่งที่ผู้ใช้เห็นและรอบที่ลองใหม่ได้
- **ถามเมื่อ:** งานที่ผู้ใช้กดต้องรู้ผลจาก `{external_system}` ทันที เช่นตรวจเครดิตก่อนยืนยัน
- **ตัวเลือกอื่น:** b) งานนั้นทำต่อไม่ได้ ขึ้นแถบแจ้งทั้งหน้าจนอีกฝั่งกลับมา c) ใช้ค่าล่าสุดที่ดึงไว้พร้อมบอกเวลา แล้วตรวจซ้ำเมื่ออีกฝั่งกลับมา

### INTG-D13: มี circuit breaker ไหม
- **คำตอบ:** ไม่มีตัวตัดวงจรที่ต้องดูแลเอง ใช้ของมาตรฐานใน library การเรียก HTTP ตามค่าปกติ ซึ่งแทบไม่ทำงานในระบบปริมาณต่ำ การตัดวงจรจริงคือกฎหยุดทั้งรอบของ INTG-D12 และเวลารอของ INTG-D05
- **เหตุผล:** ระบบองค์กรส่วนใหญ่เรียกกันไม่กี่ครั้งต่อนาที ตัวตัดวงจรที่ปรับเองจะเปิดผิดจังหวะมากกว่าจะช่วย
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มได้ที่ port โดยโค้ดธุรกิจไม่เปลี่ยน
- **ถามเมื่อ:** มีการเรียกจำนวนมาก (เกิน 100 ครั้งใน 30 วินาที) หรืออีกฝั่งคิดเงินหรือจำกัดโควตาต่อครั้ง
- **ตัวเลือกอื่น:** b) ตัดวงจรตามอัตราความล้มเหลวต่อ `{external_system}` c) ปุ่มหยุดและเปิดการเรียกด้วยมือบนจอติดตาม

### INTG-D14: จอติดตามแสดงอะไร
- **คำตอบ:** จอเดียวต่อทั้งระบบ เปิดมาที่ `integration.monitor_hours` ชั่วโมงล่าสุด: ตารางต่อระบบและ `{operation}` (ครั้ง สำเร็จ เตือน ล้ม ผลล่าสุด เวลาเฉลี่ย cursor ล่าสุด) รายการล้มพร้อมรหัสอ้างอิง คิวงานเขียนที่รอ (ค้างเกิน `integration.late_hours` ชั่วโมงเป็นสีแดง) และรอบงานล่าสุดจากแพ็ก jobs ค่าที่ยังไม่ได้ตั้งหรือโหมดปลอมแสดงเป็นป้าย
- **เหตุผล:** เห็นในจอเดียวว่าเส้นไหนเสียและอะไรค้าง ก่อนผู้ใช้จะโทรมาบอก
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการแสดงผล ข้อมูลที่เก็บไม่เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### INTG-D15: ใครใช้จอติดตามได้
- **คำตอบ:** จอนี้อยู่ในตารางสิทธิ์ มีช่อง View และ Manage `{superadmin}` ถือทั้งสองช่องตั้งแต่ seed ผู้ถือ View เห็นตารางและตัวเลขรวม แถวที่ระบุเอกสารรายฉบับเห็นเฉพาะผู้ที่ขอบเขตข้อมูลเป็นทั้งหมด นอกนั้นเห็นจำนวนแทน
- **เหตุผล:** log มีชื่อเอกสารและคู่ค้า ถ้าไม่จำกัดจะเป็นทางอ้อมขอบเขตข้อมูล ส่วนการส่งซ้ำเขียนลงระบบอื่น คนกดจึงควรน้อย
- **ถ้าผิด:** แก้ยาก — เป็นเรื่องการมองเห็นข้อมูลและสิทธิ์
- **ถามเมื่อ:** เอกสารลูกค้าให้หลายกลุ่มดูจอนี้ และขอบเขตข้อมูลของกลุ่มเหล่านั้นไม่เหมือนกัน
- **ตัวเลือกอื่น:** b) กรองแถวตามขอบเขตของแต่ละคน c) ผู้ถือ View เห็นทุกแถว

### INTG-D16: ส่งซ้ำและดึงซ้ำด้วยมืออย่างไร
- **คำตอบ:** ผู้ถือ `{integration_manage_key}` กดส่งซ้ำแถวในคิวที่ Failed หรือ Review ได้ทีละแถว ใช้คีย์กันซ้ำเดิม เหตุผลต้องกรอก ดึงซ้ำคือสั่งรอบของงานดึงเข้าตามแพ็ก jobs จากจุด cursor หรือจากเวลาที่เลือกย้อนได้ไม่เกิน `integration.repull_max_days` วัน การดึงย้อนหลังไม่ขยับ cursor การกดทุกครั้งลง Activity Log
- **เหตุผล:** รายการที่ต้องแก้ก่อนส่งต้องมีคนสั่ง และดึงย้อนหลังเพื่อซ่อมต้องไม่ทำให้รอบปกติข้ามข้อมูล
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มการส่งซ้ำเป็นชุดภายหลังได้
- **ถามเมื่อ:** ไม่ถาม

### INTG-D17: แจ้งเตือนใครเมื่อล้มซ้ำ
- **คำตอบ:** รอบงานที่ล้มติดกันเตือนตามแพ็ก jobs แพ็กนี้เตือนเพิ่มสองอย่างที่รอบงานไม่เห็น: ระบบหนึ่งตอบล้มติดกัน `integration.alert_failures` ครั้ง นับจากทุกผู้เรียก และมีแถวในคิวค้างเกิน `integration.late_hours` ชั่วโมง ส่งถึงผู้รับเดียวกับการเตือนของแพ็ก jobs ผ่านคิวอีเมล ไม่ส่งซ้ำเรื่องเดิมภายใน `integration.alert_repeat_minutes` นาที และส่งหนึ่งฉบับเมื่อกลับมาปกติ ไม่มีข้อมูลธุรกิจหรือความลับในอีเมล
- **เหตุผล:** การเรียกจากปุ่มและคำขอของผู้ใช้ไม่อยู่ในรอบงาน และแถวที่ค้างนานไม่ทำให้รอบล้ม ส่วนรายชื่อผู้รับชุดเดียวดูแลง่ายกว่า
- **ถ้าผิด:** แก้ทีหลังได้ — ปรับเงื่อนไขและผู้รับได้
- **ถามเมื่อ:** ผู้รับการเตือนการเชื่อมต่อเป็นคนละกลุ่มกับงานเบื้องหลัง หรือโปรเจกต์ไม่เลือกแพ็ก mail
- **ตัวเลือกอื่น:** b) รายชื่อผู้รับแยกของการเชื่อมต่อ c) แสดงบนจอติดตามอย่างเดียว ไม่ส่งอีเมล

### INTG-D18: เครื่องพัฒนาคุยกับใคร
- **คำตอบ:** ของปลอมในโค้ดหนึ่งตัวต่อ `{external_system}` เปิดด้วย env `<SYSTEM>_MODE=fake` ตอบรูปแบบเดียวกับของจริง Development และ Prototype ใช้ของปลอมเป็นค่าเริ่มต้น Staging ต่อเครื่องทดสอบของอีกฝั่ง Production ต่อของจริงเท่านั้น โหมดปลอมใน Staging หรือ Production ทำให้ API ไม่ start ตัวสั่งให้ของปลอมตอบรหัสที่เลือก N ครั้งมีเฉพาะโหมดปลอม โหมด live คำขอไปที่ตัวสั่งได้ 404
- **เหตุผล:** พัฒนาและทดสอบกรณีล้มได้โดยไม่แตะระบบของคนอื่น และไม่มีสวิตช์ทำให้ล้มอยู่ในโค้ดที่ต่อของจริง
- **ถ้าผิด:** แก้ยาก — ถ้าหลุดไป Production ทุกอย่างดูเหมือนสำเร็จแต่ไม่มีอะไรไปถึงอีกฝั่ง
- **ถามเมื่อ:** อีกฝั่งไม่มีเครื่องทดสอบให้ Staging ต่อ
- **ตัวเลือกอื่น:** b) Staging ใช้ของปลอม และป้ายบนทุกหน้าบอกว่าไม่ได้ต่อของจริง c) Staging ต่อของจริงโดยจำกัดด้วย allow-list ข้อมูลทดสอบ

### INTG-D19: ทดสอบการเชื่อมต่ออย่างไร
- **คำตอบ:** แต่ละแท็บระบบบนหน้าตั้งค่ามีปุ่ม Test connection ใช้ค่าที่บันทึกแล้วเรียกเส้นอ่านที่เบาที่สุดของระบบนั้นในคำขอนั้น ไม่ผ่านคิว รอไม่เกิน `integration.test_timeout_seconds` วินาที แล้วแสดงผลพร้อมรหัสตอบกลับและเวลา ไม่มีค่าตั้งใดๆ ในคำตอบ ไม่เขียนข้อมูลธุรกิจ ทุกครั้งลง `integration_call_log` และ Activity Log กดได้เฉพาะผู้ที่แก้ค่าตั้งได้
- **เหตุผล:** ผู้ดูแลรู้ทันทีว่าค่าที่เพิ่งแก้ใช้ได้ ไม่ต้องรอให้รอบถัดไปล้ม
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นปุ่มเดียวที่ไม่กระทบคิว
- **ถามเมื่อ:** ไม่ถาม

### INTG-D20: รู้ได้อย่างไรว่าของปลอมตรงกับของจริง
- **คำตอบ:** ชุดทดสอบสัญญาที่คนสั่งรันเอง เรียกเครื่องทดสอบของอีกฝั่งด้วยค่าจาก env ไม่อยู่ใน CI อ่านอย่างเดียว ไม่แก้และไม่ลบข้อมูลของอีกฝั่ง เก็บคำตอบจริงหนึ่งตัวอย่างต่อเส้นในโปรเจกต์ โดยไม่มีความลับหรือข้อมูลจริง แล้ว unit test ตรวจว่าของปลอมตอบรูปเดียวกัน ไม่มีค่าใน env แล้วข้าม ไม่นับว่าล้ม
- **เหตุผล:** ถ้าของปลอมเดาผิด ทุกอย่างผ่านในเครื่องแล้วไปพังตอนต่อของจริง
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มชุดทดสอบได้ทุกเมื่อ
- **ถามเมื่อ:** อีกฝั่งไม่มีเครื่องทดสอบ หรือไม่อนุญาตให้เรียกจากเครื่องพัฒนา
- **ตัวเลือกอื่น:** b) อีกฝั่งส่งตัวอย่างคำตอบเป็นไฟล์ แล้วเทียบกับไฟล์นั้น c) ไม่มีชุดทดสอบ ตรวจด้วยมือก่อนขึ้นระบบ

### INTG-D21: รับคำขอที่อีกฝั่งยิงเข้ามาอย่างไร
- **คำตอบ:** route แยกต่อ `{external_system}` ไม่ใช้ session ตรวจลายเซ็น HMAC-SHA256 ของ body ดิบด้วย `integration.webhook_secret` เทียบแบบเวลาคงที่ และเวลาในลายเซ็นต้องอยู่ใน `integration.webhook_tolerance_seconds` วินาที ไม่ผ่านตอบ 401 ไม่บอกเหตุผล ผ่านแล้วเขียนแถวใน `integration_inbox` โดย event id ห้ามซ้ำ แล้วตอบ 200 ทันที งานเบื้องหลังทำงานธุรกิจภายหลัง event id ซ้ำตอบ 200 และไม่ทำอะไร `integration_inbox` เป็นตารางชั่วคราวตาม AUDIT-D07 อายุ `audit.call_log_days` วัน
- **เหตุผล:** อีกฝั่งส่งซ้ำได้เสมอ ต้องไม่ทำงานธุรกิจซ้ำ ลายเซ็นกันคนอื่นปลอมคำขอ และการตอบเร็วไม่ทำให้อีกฝั่งหมดเวลาแล้วส่งซ้ำ
- **ถ้าผิด:** แก้ยาก — คำขอปลอมหรือการทำงานธุรกิจซ้ำ
- **ถามเมื่อ:** มี `{external_system}` ที่ยิงเข้าระบบนี้ หรืออีกฝั่งกำหนดวิธีลงลายเซ็นของตัวเอง
- **ตัวเลือกอื่น:** b) ใช้ API key ใน header แทนลายเซ็น พร้อมจำกัด IP ต้นทาง c) ไม่รับ webhook ใช้การดึงเข้าตามรอบแทน

### INTG-D22: รุ่นของ API อีกฝั่งและการแปลงฟิลด์อยู่ที่ไหน
- **คำตอบ:** ใน port ของระบบนั้นที่เดียว: รุ่นของ API อีกฝั่งเป็นค่าคงที่ที่เดียว การแปลงฟิลด์และรหัส (ของเรา ↔ ของอีกฝั่ง) เป็นตารางในโค้ดหนึ่งที่ต่อ `{operation}` ค่าที่แปลงไม่ได้ทำให้รายการนั้นเป็น Review ไม่ใส่ค่าเดา
- **เหตุผล:** อีกฝั่งเปลี่ยนรุ่นหรือชื่อฟิลด์แล้วแก้ที่เดียว และไม่มีข้อมูลเพี้ยนเงียบๆ เพราะค่าที่ไม่รู้จัก
- **ถ้าผิด:** แก้ทีหลังได้ — ตารางแปลงรวมอยู่ที่เดียว
- **ถามเมื่อ:** ไม่ถาม

### INTG-D23: ไฟล์ที่ส่งผ่านระบบภายนอกทำอย่างไร
- **คำตอบ:** ไฟล์ขึ้นระบบตามแพ็ก upload ก่อนเสมอ ตัวส่งส่งจากที่เก็บของเราไปอีกฝั่งเป็นงานใน `integration_outbox` อ้างไฟล์ด้วย key ไม่ใส่เนื้อไฟล์ใน payload เวลารอใช้ `integration.file_timeout_seconds` log ไม่เก็บเนื้อไฟล์ ไฟล์ขาเข้าถูกตรวจชนิดและเก็บตามแพ็ก upload เหมือนไฟล์ที่ผู้ใช้อัปโหลด ไม่มี URL ของอีกฝั่งถึง browser
- **เหตุผล:** ไฟล์ไม่หายเมื่ออีกฝั่งล่ม และตารางคิวไม่บวม และไฟล์จากภายนอกเป็นทางเข้าของมัลแวร์เหมือนกัน
- **ถ้าผิด:** แก้ยาก — เปลี่ยนที่เก็บไฟล์หลังใช้งานจริงต้องย้ายทั้งหมด
- **ถามเมื่อ:** ไฟล์เก็บอยู่ที่อีกฝั่งเป็นหลัก และระบบนี้ไม่เก็บสำเนา
- **ตัวเลือกอื่น:** b) เก็บไว้อีกฝั่งอย่างเดียว ดาวน์โหลดผ่าน API ของเราเพื่อคุมสิทธิ์ c) ส่งไฟล์ตรงในคำขอของผู้ใช้ ไม่มีคิว

### INTG-D24: ข้อมูลที่ออกนอกระบบต้องทำอะไร
- **คำตอบ:** ตารางระบบของ INTG-D02 ระบุว่าแต่ละเส้นส่งข้อมูลส่วนบุคคลอะไรออก ส่งเฉพาะฟิลด์ที่จำเป็น ฟิลด์ข้อมูลส่วนบุคคลถูกเพิ่มใน `integration.masked_fields` จึงไม่ลง log การส่งข้ามองค์กรหรือข้ามประเทศต้องมีเหตุผลทางกฎหมายที่ลูกค้าระบุ เป็นเรื่องที่ลูกค้าต้องตกลงก่อนเปิดส่งจริง
- **เหตุผล:** PDPA ใช้กับการส่งข้อมูลออกนอกองค์กรด้วย และ log เป็นที่เก็บข้อมูลส่วนบุคคลอีกที่หนึ่งที่มักถูกลืม
- **ถ้าผิด:** แก้ยาก — ข้อมูลที่ออกไปแล้วเรียกคืนไม่ได้
- **ถามเมื่อ:** มีการส่งข้อมูลส่วนบุคคลออกนอกองค์กร หรือไปยังผู้ให้บริการนอกประเทศ
- **ตัวเลือกอื่น:** b) ส่งเฉพาะรหัส ไม่ส่งชื่อหรือข้อมูลติดต่อ c) ทำให้เป็นข้อมูลนิรนามก่อนส่ง
