# ข้อตัดสินใจของแพ็ก permission

### PERM-D01: สิทธิ์ให้กับใคร
- **คำตอบ:** ให้กับ role เท่านั้น ไม่มีสิทธิ์รายคน ผู้ใช้ได้สิทธิ์จาก role ที่สังกัด
- **เหตุผล:** ตรวจและเปลี่ยนสิทธิ์ทีละ role ได้ ไม่มีสิทธิ์ตกค้างรายคนที่ไม่มีใครเห็น
- **ถ้าผิด:** แก้ยาก — ตารางสิทธิ์ จอจัดการ role และการคำนวณคีย์ตอนเข้าระบบเปลี่ยนทั้งหมด
- **ถามเมื่อ:** ไม่ถาม

### PERM-D02: ผู้ใช้หนึ่งคนอยู่ได้กี่ role
- **คำตอบ:** หนึ่ง role ต่อบัญชี
- **เหตุผล:** สิทธิ์และขอบเขตของแต่ละคนอ่านได้จาก role เดียว ไม่ต้องรวมสิทธิ์หลาย role และไม่มีคำถามว่าขอบเขตไหนชนะ
- **ถ้าผิด:** แก้ยาก — คอลัมน์ role ของบัญชีกลายเป็นตารางกลาง และการรวมขอบเขตต้องคิดใหม่
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) หลาย role สิทธิ์และขอบเขตรวมกัน (union) c) role หลักหนึ่ง role บวก role เสริมที่ให้สิทธิ์เพิ่มอย่างเดียว

### PERM-D03: หน่วยของสิทธิ์ที่โค้ดตรวจ
- **คำตอบ:** แต่ละหน้าจอมีช่องสิทธิ์ (View และช่องอื่นตาม PERM-D04) แต่ละช่องครอบคำสั่งละเอียด `<SCREEN>.<Action>` ทุกปุ่มและทุก endpoint ผูกกับคำสั่งละเอียดตั้งแต่วันแรก ไม่ผูกกับชื่อช่อง catalog เก็บในตารางและเปลี่ยนผ่าน migration เท่านั้น ตาราง role กับ catalog เชื่อมแบบ many-to-many
- **เหตุผล:** แยกช่องภายหลังเป็นงานข้อมูลที่ทดสอบได้ ไม่ต้องไล่แก้โค้ดทุกปุ่ม จึงไม่มี endpoint ตกหล่น
- **ถ้าผิด:** แก้ยาก — ถ้าโค้ดเช็กชื่อช่อง การแยกช่องต้องแก้ทุกปุ่มและ endpoint และพลาดแล้วเป็นช่องโหว่
- **ถามเมื่อ:** ไม่ถาม

### PERM-D04: แต่ละหน้าจอมีช่องอะไรบ้างตั้งแต่ต้น
- **คำตอบ:** ชุดช่องมาตรฐานห้าช่อง แต่ละหน้าจอมีเฉพาะช่องที่หน้านั้นมี action จริง: View (ดู) ครอบการเปิดหน้าจอ อ่าน preview และดาวน์โหลดไฟล์แนบของระเบียน, Manage (จัดการ) ครอบสร้าง แก้ ลบ และคำสั่งเขียนอื่นที่ไม่อยู่ในช่องอื่น, Approve (อนุมัติ-ไม่อนุมัติ) ครอบทั้งการอนุมัติและการตีกลับหรือไม่อนุมัติ, Import (นำเข้า) ครอบการนำเข้าไฟล์ของหน้านั้นทุกขั้น, Export (ส่งออก) ครอบการดาวน์โหลดรายการหรือรายงานเป็นไฟล์ ตารางของจอจัดการ role มีคอลัมน์ตามลำดับนี้ หน้าที่ไม่มี action ของช่องนั้นแสดง "—" ช่องอื่น (เช่น Delete แยกจาก Manage หรือ Publish) แยกเพิ่มเมื่อเอกสารลูกค้าหรือการใช้งานจริงขอ
- **เหตุผล:** ผู้ดูแลอ่านตารางแล้วรู้ทันทีว่า role ทำอะไรได้ในแต่ละหน้า ห้าช่องนี้ตรงกับคำถามที่ลูกค้าถามบ่อยที่สุด (ใครดู ใครแก้ ใครอนุมัติ ใครนำเข้า ใครดึงข้อมูลออก) และ PERM-D03 ทำให้แยกช่องเพิ่มทีหลังได้โดยไม่แก้โค้ด
- **ถ้าผิด:** แก้ทีหลังได้ — รวมหรือแยกช่องด้วย migration ตาม PERM-D06
- **ถามเมื่อ:** เอกสารลูกค้ากำหนดสิทธิ์รายปุ่มที่ไม่ลงห้าช่องนี้ เช่น ลบแยกจากแก้ไข หรืออนุมัติกับไม่อนุมัติแยกคนกัน
- **ตัวเลือกอื่น:** b) View กับ Manage เท่านั้น แยกช่องเมื่อเอกสารลูกค้าขอ c) View, Create, Edit, Delete ทุกหน้าจอ

### PERM-D05: ช่องสิทธิ์ของหน้าจอเดียวกันพากันอย่างไร
- **คำตอบ:** ติ๊กช่องใดก็ได้นอกจาก View ได้ View ของหน้าจอนั้นด้วย ช่องอื่นไม่พากันเอง (Approve, Import หรือ Export ไม่พา Manage) เอา View ออกแล้วช่องอื่นของหน้าจอนั้นออกทั้งหมด
- **เหตุผล:** ไม่มี role ที่กดปุ่มได้แต่เปิดหน้าจอไม่ได้ และการให้อนุมัติหรือส่งออกไม่แอบให้แก้ข้อมูล
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นกติกาของจอและ aggregate ไม่เปลี่ยนตาราง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D06: แยกปุ่มออกจากช่องเดิมภายหลังอย่างไร
- **คำตอบ:** release ที่มี migration ย้ายคำสั่งไปช่องใหม่ของหน้าจอเดิม และติ๊กช่องใหม่ให้ทุก role ที่ถือช่องเดิมใน migration เดียวกัน แต่ละสิทธิ์ที่เพิ่มลง Activity Log โดยผู้ทำคือระบบ ฐานข้อมูลที่ยังไม่มี role ไม่ได้อะไรจากขั้นนี้ ไม่มีจอให้ผู้ดูแลย้ายคำสั่งเอง
- **เหตุผล:** ไม่มีใครเสียปุ่มที่ใช้อยู่ในวันที่แยก และการแยกผ่านการทดสอบเหมือน release ปกติ
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มจอย้ายคำสั่งได้ภายหลังโดยไม่เปลี่ยนตาราง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D07: สิทธิ์ที่เปลี่ยนมีผลเมื่อไร
- **คำตอบ:** การเปลี่ยนสิทธิ์หรือขอบเขตของ role มีผลเมื่อสมาชิกเข้าระบบรอบถัดไป เซสชันที่เปิดอยู่ใช้สิทธิ์เดิมจนออกหรือจนครบอายุสูงสุดของเซสชัน ส่วนการเปลี่ยนผู้ใช้ไป role อื่น และการถอนเมนูออกจาก org role ของ `{org_portal}` จบเซสชันของบัญชีที่เกี่ยวข้องทันที
- **เหตุผล:** คีย์คำนวณครั้งเดียวตอนเข้าระบบ ไม่ต้องอ่านสิทธิ์ทุก request ส่วนกรณีที่คนหนึ่งเปลี่ยนสังกัดหรือเสียเมนูต้องมีผลทันที
- **ถ้าผิด:** แก้ยาก — เปลี่ยนเป็นมีผลทันทีต้องโหลดสิทธิ์ทุก request หรือจบเซสชันของทั้ง role และกระทบความปลอดภัย
- **ถามเมื่อ:** เอกสารลูกค้าต้องการให้การถอนสิทธิ์มีผลทันที
- **ตัวเลือกอื่น:** b) ทุกการเปลี่ยนสิทธิ์หรือขอบเขตจบเซสชันของสมาชิกทั้ง role ทันที c) รอบเข้าถัดไปทุกกรณี รวมการเปลี่ยน role

### PERM-D08: ตรวจสิทธิ์ฝั่ง server อย่างไร
- **คำตอบ:** ทุก endpoint ประกาศคีย์ที่ต้องมี (หรือเมนูสำหรับ `{org_portal}`, หรือแค่ต้องเข้าระบบ, หรือ public) ไม่มีคีย์ตอบ 403 `ACCESS_DENIED` ไม่คืนข้อมูล และลง Activity Log architecture test ล้มเมื่อมี endpoint ที่ไม่ประกาศ หรือประกาศคีย์ที่ไม่มีใน catalog
- **เหตุผล:** การซ่อนปุ่มไม่ใช่การกันสิทธิ์ และ endpoint ที่ลืมประกาศถูกจับตั้งแต่ build
- **ถ้าผิด:** แก้ยาก — endpoint ที่ไม่ได้ตรวจคือช่องโหว่ที่ใครก็เรียกได้
- **ถามเมื่อ:** ไม่ถาม

### PERM-D09: หน้าจอแสดงเมนูและปุ่มอย่างไร
- **คำตอบ:** แสดงเมนูเมื่อมี View ของหน้าจอนั้น ซ่อนหัวกลุ่มเมนูที่ไม่เหลือรายการ ปุ่มแสดงเมื่อมีคีย์ของปุ่ม มีคีย์แต่สถานะของระเบียนไม่ให้ทำ แสดงปุ่มแบบ disabled พร้อมเหตุผล เปิดหน้าจอด้วย URL โดยไม่มี View เห็นแผง no-access ไม่มีข้อมูล เมนูที่มีช่องเขียน (ทุกช่องนอกจาก View และ Export) แต่ role ไม่ถือช่องเขียนใดเลย ติดป้าย "· view"
- **เหตุผล:** ผู้ใช้เห็นเฉพาะสิ่งที่ทำได้ และรู้ว่าทำไมปุ่มกดไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการแสดงผล server ยังตรวจตาม PERM-D08
- **ถามเมื่อ:** ไม่ถาม

### PERM-D10: `GET /me` ส่งอะไรให้หน้าจอ
- **คำตอบ:** พอร์ทัล ชื่อที่แสดง role หรือ org role คำสั่งละเอียดที่ role ถือ (ไม่ส่งชื่อช่องแทน) เมนูของบัญชี `{org_portal}` หน้าแรก และสิ่งที่ยังค้างของการเข้าครั้งแรก ระหว่างที่ค้างไม่ส่งคีย์และเมนู ไม่ส่งรหัสผ่าน โทเค็น หรือความลับใด
- **เหตุผล:** หน้าจอตัดสินจากคำสั่งละเอียดเหมือน server จึงไม่ต้องแก้หน้าจอเมื่อแยกช่อง
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือตัดฟิลด์ใน response ได้
- **ถามเมื่อ:** ไม่ถาม

### PERM-D11: Activity Log บันทึก role ของผู้ทำอย่างไร
- **คำตอบ:** บันทึก role ณ เวลาที่ทำ: ชื่อ role ของบัญชีพนักงาน ชื่อประเภทของบัญชี `{org_portal}` และ `System` สำหรับงานที่ไม่มีบัญชีเข้าระบบ เปลี่ยน role ภายหลังไม่แก้ log เดิม
- **เหตุผล:** log ต้องบอกว่าตอนนั้นทำในฐานะอะไร ไม่ใช่สังกัดปัจจุบัน
- **ถ้าผิด:** แก้ยาก — log ที่เขียนไปแล้วไม่มี role ย้อนหลัง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D12: มีขอบเขตข้อมูลไหม และแบ่งตามอะไร
- **คำตอบ:** มี ขอบเขตต่อ role ต่อเมนู แบ่งตามมิติ `{scope}` แต่ละเมนูที่มีขอบเขตตั้งแยกกัน
- **เหตุผล:** role เดียวกันมักดูแลข้อมูลคนละชุดในแต่ละงาน
- **ถ้าผิด:** แก้ยาก — ทุก query ของข้อมูลที่มีเจ้าของ และจอจัดการ role เปลี่ยน
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ไม่มีขอบเขต ทุก role เห็นทุกแถวของหน้าจอที่มีสิทธิ์ c) ขอบเขตเดียวต่อ role ใช้กับทุกเมนู

### PERM-D13: เก็บขอบเขตของแต่ละเมนูในรูปไหน
- **คำตอบ:** ต่อ (role, เมนู): "ทั้งหมด" หรือ "รายการรหัส" ของ `{scope}` เมนูที่ไม่ได้ตั้งหมายถึงไม่เห็นเลย role ใหม่เริ่มโดยไม่มีขอบเขต รายการว่างบันทึกไม่ได้
- **เหตุผล:** ตรงกับวิธีที่ผู้ดูแลอธิบายงาน และล้มแบบปิด (fail closed) เมื่อยังไม่ได้ตั้ง
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มโหมดแบ่งตามคุณสมบัติเป็นโหมดที่สามได้โดยไม่เปลี่ยนโครง
- **ถามเมื่อ:** ลูกค้าแบ่งความรับผิดชอบตามคุณสมบัติของ `{scope}` (ภูมิภาค โรงงาน ประเภท) มากกว่าตามรายชื่อ
- **ตัวเลือกอื่น:** b) ตามคุณสมบัติของ `{scope}` c) มีทั้งรายชื่อและคุณสมบัติ

### PERM-D14: บังคับขอบเขตในโค้ดอย่างไร
- **คำตอบ:** filter เดียวระดับการเข้าถึงข้อมูลที่อ่านขอบเขตของ request (เช่น global query filter) ใช้กับข้อมูลทุกชนิดที่มีเจ้าของ ไม่มีเส้นทางใดปิด filter นี้ได้ ห้าม raw SQL นอก migration และ seed มี architecture test ตรวจทั้งสองข้อ ตารางของ `{scope}` เองไม่ติด filter แต่ทุกการอ่านที่ผู้ใช้เห็นต้องระบุว่าใช้ขอบเขตของเมนูไหน
- **เหตุผล:** ลืมใส่เงื่อนไขไม่ได้ และมุมมองประวัติที่ปิด filter soft delete ยังคงขอบเขต
- **ถ้าผิด:** แก้ยาก — query ที่หลุด filter รั่วข้อมูลข้ามขอบเขต
- **ถามเมื่อ:** ไม่ถาม

### PERM-D15: role เริ่มต้นมีอะไร และได้สิทธิ์อะไร
- **คำตอบ:** มาจากตารางบทบาทในเอกสารลูกค้า มี `{superadmin}` เสมอ แต่ละ role ได้ View ของหน้าจอที่ตารางเปิดให้ และช่อง Manage, Approve, Import หรือ Export ที่ครอบคำสั่งที่ตารางให้ role นั้นทำได้ ข้อมูล prototype ใช้กติกาเดียวกัน
- **เหตุผล:** สิทธิ์เริ่มต้นตรงกับเอกสารที่ลูกค้าอนุมัติ ตรวจกับเอกสารได้ทีละช่อง
- **ถ้าผิด:** แก้ทีหลังได้ — แก้ seed หรือให้ `{superadmin}` แก้บนจอ
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) seed มีแค่ `{superadmin}` ลูกค้าสร้าง role อื่นเองบนจอ c) seed ตามที่ทีมเสนอ แล้วให้ลูกค้าตรวจตอนทดสอบใช้งาน

### PERM-D16: role seed เห็นข้อมูลของใคร
- **คำตอบ:** ทุก role seed ได้ "ทั้งหมด" ทุกเมนูที่มีขอบเขต ฐานข้อมูลที่มี role seed อยู่ก่อนมีขอบเขตได้ "ทั้งหมด" ครั้งเดียว role ที่ถูกเอาขอบเขตออกโดยตั้งใจไม่ได้คืน
- **เหตุผล:** เปิดใช้ขอบเขตแล้วไม่มีใครเห็นข้อมูลน้อยลงจากวันก่อน
- **ถ้าผิด:** แก้ทีหลังได้ — ผู้ดูแลแคบขอบเขตบนจอได้
- **ถามเมื่อ:** ไม่ถาม

### PERM-D17: ระเบียนนอกขอบเขตตอบอะไร
- **คำตอบ:** 404 `NOT_FOUND` เหมือนระเบียนที่ไม่มีอยู่ ไม่คืนส่วนใดของระเบียน และลง Activity Log `AccessDenied` พร้อมชนิดเอกสารและรหัส
- **เหตุผล:** ผู้ใช้เดาไม่ได้ว่ารหัสไหนมีอยู่จริง แต่ผู้ดูแลยังเห็นความพยายามใน log
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนรหัสตอบกลับได้โดยไม่เปลี่ยนตาราง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D18: ขอบเขตของผู้เรียกแต่ละแบบ
- **คำตอบ:** บัญชีพนักงานได้ขอบเขตของ role รายเมนู บัญชี `{org_portal}` ได้เฉพาะ `{org}` ของตัวเองทุกเมนู และรหัสไม่มาจาก request งานของระบบ (migration, seed, job) ได้ "ทั้งหมด" เฉพาะเมื่องานนั้นประกาศเอง ผู้ที่ยังไม่เข้าระบบไม่เห็นอะไร คำขอเข้าระบบหรือลืมรหัสของ `{org_portal}` ได้ `{org}` ของบัญชีที่อีเมลหรือลิงก์ระบุ ไม่ใช่ของเซสชันที่ค้างอยู่ใน browser
- **เหตุผล:** ทุกเส้นทางล้มแบบปิด และไม่มี request ใดได้ "ทั้งหมด" โดยบังเอิญ
- **ถ้าผิด:** แก้ยาก — ผิดแล้วรั่วข้อมูลข้าม `{org}`
- **ถามเมื่อ:** ไม่ถาม

### PERM-D19: role ใหม่เริ่มด้วยอะไร
- **คำตอบ:** View ของหน้าแรกอย่างเดียว และไม่มีขอบเขต สมาชิกเข้าแล้วเห็นหน้าแรกกับ Help
- **เหตุผล:** role ใหม่ไม่ได้สิทธิ์หรือข้อมูลเกินที่ผู้ดูแลตั้งใจให้
- **ถ้าผิด:** แก้ทีหลังได้ — ผู้ดูแลติ๊กสิทธิ์เพิ่มบนจอ
- **ถามเมื่อ:** ไม่ถาม

### PERM-D20: ผู้แก้ขอบเขตให้ role อื่นได้แค่ไหน
- **คำตอบ:** เพิ่มรหัสได้เฉพาะที่อยู่ในขอบเขตของผู้แก้สำหรับเมนูนั้น ตั้ง "ทั้งหมด" ได้เมื่อผู้แก้มี "ทั้งหมด" ของเมนูนั้น รหัสเดิมที่อยู่นอกขอบเขตของผู้แก้คงไว้และแสดงเป็นรหัส
- **เหตุผล:** ผู้แก้ส่งต่อสิทธิ์ที่ตัวเองไม่มีไม่ได้
- **ถ้าผิด:** แก้ยาก — ผิดแล้วผู้แก้ขยายการมองเห็นเกินของตัวเอง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D21: ใครจัดการ role ได้
- **คำตอบ:** ใน seed มีแค่ `{superadmin}` ที่ถือสิทธิ์ของจอจัดการ role ส่วน role อื่นเข้าได้เมื่อ `{superadmin}` ให้ ทุกการสร้าง เปลี่ยนชื่อ เปลี่ยนสิทธิ์ และเปลี่ยนขอบเขต ถามยืนยันก่อนบันทึก และลง Activity Log ค่าเก่าและค่าใหม่ใน transaction เดียว ชื่อ role ห้ามซ้ำโดยไม่สนตัวพิมพ์ ไม่นับ role ที่ลบแล้ว
- **เหตุผล:** สิทธิ์เป็นเรื่องที่ต้องตรวจย้อนได้เสมอ
- **ถ้าผิด:** แก้ทีหลังได้ — ให้สิทธิ์ role อื่นบนจอได้
- **ถามเมื่อ:** ไม่ถาม

### PERM-D22: เปลี่ยน role ของผู้ใช้ที่ไหน
- **คำตอบ:** ที่จอจัดการผู้ใช้ (แพ็ก `users`) หน้าของ role มีตารางผู้ใช้ใน role นั้นแบบอ่านอย่างเดียว อยู่หน้าเดียวกับตารางสิทธิ์ นับเฉพาะบัญชีที่ไม่ถูกลบ
- **เหตุผล:** ทางเข้า role มีทางเดียว log และการจบเซสชันตอนเปลี่ยน role เกิดที่เดียว ส่วนผู้ดูแลยังเห็นสิทธิ์และคนที่ได้สิทธิ์นั้นในหน้าเดียว
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มปุ่มเพิ่มหรือเอาผู้ใช้ออกบนหน้าของ role ได้ภายหลัง
- **ถามเมื่อ:** ไม่ถาม

### PERM-D23: role ของบัญชี `{org_portal}` เก็บที่ไหน
- **คำตอบ:** ตาราง org role แยกจาก role ของพนักงาน แต่ละ org role เปิดเมนูของ `{org_portal}` ได้หนึ่งเมนูขึ้นไป บัญชีถือ org role เดียว org role ใช้ร่วมกันทุก `{org}`
- **เหตุผล:** บัญชีภายนอกไม่ควรอยู่ในโครงเดียวกับ role ของพนักงาน และ org role เป็นชุดเมนู ไม่ใช่สิทธิ์รายหน้าจอ
- **ถ้าผิด:** แก้ยาก — ตาราง org role และการคำนวณเมนูตอนเข้าระบบเปลี่ยน
- **ถามเมื่อ:** ระบบมีพอร์ทัลขององค์กรภายนอก
- **ตัวเลือกอื่น:** b) ใช้ตาราง role เดียวกับพนักงาน แยกด้วยประเภทของ role c) org role ตายตัวจาก migration ไม่มีการแก้บนจอ

### PERM-D24: role ผู้ดูแลของ `{org}`
- **คำตอบ:** `{org_admin}` เปิดทุกเมนูรวมเมนูจัดการบัญชีขององค์กร ถูกล็อก แก้และลบไม่ได้ (409 `ORG_ROLE_LOCKED`) org role อื่นเปิดเมนูจัดการบัญชีไม่ได้
- **เหตุผล:** ทุก `{org}` มีคนจัดการบัญชีของตัวเองได้เสมอ และไม่มีใครตัดทางนี้โดยไม่ตั้งใจ
- **ถ้าผิด:** แก้ทีหลังได้ — ปลดล็อกเป็นการเปลี่ยนกติกา ไม่เปลี่ยนตาราง
- **ถามเมื่อ:** ระบบมีพอร์ทัลขององค์กรภายนอก
- **ตัวเลือกอื่น:** b) ไม่มี org role ล็อก ผู้ดูแลฝั่งพนักงานจัดการบัญชีภายนอกแทน

### PERM-D25: มีจอจัดการ org role ของ `{org_portal}` บน `{staff_portal}` ไหม
- **คำตอบ:** ไม่แสดงจอ เพราะทุกบัญชีภายนอกถือ `{org_admin}` แต่ API ของ org role (รายการ สร้าง แก้ ลบ) คงไว้พร้อมคีย์ เปิดจอได้ภายหลังโดยไม่แก้ server
- **เหตุผล:** เมื่อทุกคนเป็นผู้ดูแลขององค์กร จอนี้ไม่มีงานให้ทำ
- **ถ้าผิด:** แก้ทีหลังได้ — เปิดจอเรียก API ที่มีอยู่
- **ถามเมื่อ:** ระบบมีพอร์ทัลขององค์กรภายนอก
- **ตัวเลือกอื่น:** b) แสดงจอให้ `{superadmin}` สร้าง แก้ และลบ org role ตั้งแต่ต้น

### PERM-D26: ตัวสลับผู้ใช้ของ prototype
- **คำตอบ:** มีเฉพาะบน `{staff_portal}` เมื่อเปิดโหมด prototype ต้องเข้าระบบก่อน รายชื่อเฉพาะบัญชีพนักงานที่ Active และไม่ถูกลบ การสลับจบเซสชันเดิมและเปิดเซสชันของบัญชีที่เลือกโดยไม่ถามรหัส นับเป็นการเข้าระบบใหม่และลง Activity Log `{org_portal}` ไม่มีตัวสลับ ปิดโหมด prototype แล้ว endpoint ของตัวสลับไม่มีอยู่
- **เหตุผล:** ผู้ตรวจดูเมนูและข้อมูลของแต่ละ role ได้เร็ว โดยไม่เปิดทางเข้าระบบแบบไม่มีรหัสบนระบบจริง
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นเครื่องมือของ prototype ไม่ไปถึงระบบจริง
- **ถามเมื่อ:** ไม่ถาม
