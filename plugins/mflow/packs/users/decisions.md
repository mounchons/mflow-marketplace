# ข้อตัดสินใจของแพ็ก users

### USERS-D01: ใครจัดการบัญชีพนักงานได้
- **คำตอบ:** ผู้ที่กลุ่มถือสิทธิ์ของจอ Manage Users ซึ่งแยกต่อปุ่ม (USERS-D12) ใน seed มีเฉพาะกลุ่ม SuperAdmin ที่ถือทุกปุ่ม
- **เหตุผล:** ลูกค้าแต่ละรายมอบงานดูแลบัญชีต่างกัน แต่กลไกเดียวกัน (สิทธิ์ต่อปุ่ม) รองรับได้ทุกแบบโดยไม่ต้องแก้โค้ด
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนกลุ่มที่ถือสิทธิ์บนจอสิทธิ์ ไม่ต้องแก้โค้ด
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) SuperAdmin และหัวหน้าฝ่ายดูแลบัญชีในฝ่ายตัวเอง c) ฝ่าย IT กลุ่มเดียว

### USERS-D02: บัญชีพนักงานใหม่ได้รหัสผ่านแรกอย่างไร
- **คำตอบ:** ฟอร์มสร้างไม่มีช่องรหัสผ่าน บัญชีเป็น Invited และส่งลิงก์ตั้งรหัส (`account.password_link`) ไปที่อีเมลในการบันทึกเดียวกัน บัญชีเป็น Active เมื่อเข้าครั้งแรกและยอมรับข้อกำหนด
- **เหตุผล:** ไม่มีใครรู้รหัสของคนอื่น ไม่ต้องมีเทมเพลตรหัสเริ่มต้นเพิ่ม และใช้ลิงก์ชุดเดียวกับลืมรหัส
- **ถ้าผิด:** แก้ยาก — อีเมลที่ส่งถึงผู้ใช้และสถานะเริ่มต้นของบัญชีเปลี่ยน
- **ถามเมื่อ:** เอกสารลูกค้าสั่งให้ผู้ดูแลตั้งรหัสเอง หรือส่งรหัสเริ่มต้นทางอีเมล
- **ตัวเลือกอื่น:** b) รหัสเริ่มต้นแบบสุ่มในอีเมลแล้วบังคับเปลี่ยนตอนเข้าครั้งแรก c) ผู้ดูแลพิมพ์รหัสแรกเอง

### USERS-D03: เก็บชื่อผู้ใช้ (username) ไหม เมื่อเข้าระบบด้วยอีเมล
- **คำตอบ:** เก็บเป็นชื่อสั้นที่ห้ามซ้ำ (ไม่สนตัวพิมพ์ ในบัญชีที่ยังไม่ถูกลบ) แสดงในรายการ ในเมนูผู้ใช้ และใน Activity Log แต่ใช้เข้าระบบไม่ได้
- **เหตุผล:** คนในองค์กรเรียกกันด้วยรหัสสั้น อ่าน log ง่ายกว่าอีเมลยาว
- **ถ้าผิด:** แก้ทีหลังได้ — เลิกแสดงคอลัมน์ได้ใน change ถัดไป
- **ถามเมื่อ:** เอกสารลูกค้าไม่มีชื่อผู้ใช้เลย
- **ตัวเลือกอื่น:** b) ไม่มี username แสดงอีเมลแทนทุกที่

### USERS-D04: บัญชีพนักงานอยู่ได้กี่กลุ่ม
- **คำตอบ:** หนึ่งบัญชีหนึ่งกลุ่ม ฟอร์มไม่มีทางเพิ่มกลุ่มที่สอง ย้ายกลุ่มได้
- **เหตุผล:** สิทธิ์และขอบเขตข้อมูลของคนหนึ่งคนอ่านได้จากกลุ่มเดียว ไม่ต้องรวมสิทธิ์ข้ามกลุ่ม
- **ถ้าผิด:** แก้ยาก — ตารางความสัมพันธ์บัญชีกับกลุ่ม และวิธีคำนวณสิทธิ์และขอบเขตเปลี่ยน
- **ถามเมื่อ:** เอกสารลูกค้าให้คนหนึ่งคนมีหลายบทบาทพร้อมกัน
- **ตัวเลือกอื่น:** b) หลายกลุ่ม สิทธิ์เป็นผลรวม ขอบเขตเป็นผลรวม

### USERS-D05: ผู้แก้ให้บัญชีอยู่กลุ่มไหนได้บ้าง
- **คำตอบ:** เฉพาะ "กลุ่มที่อยู่ในมือผู้แก้": ทุกสิทธิ์ที่กลุ่มให้ ผู้แก้ถืออยู่ และขอบเขตข้อมูลของกลุ่มทุกเมนูอยู่ในขอบเขตของผู้แก้ ใช้กับการสร้าง การย้ายกลุ่ม (ทั้งกลุ่มเดิมและกลุ่มใหม่) และการเปลี่ยนอีเมลของบัญชีอื่น กลุ่มของตัวเองอยู่ในมือเสมอ
- **เหตุผล:** กันคนที่ได้สิทธิ์จอนี้ยกสิทธิ์ตัวเอง หรือยึดบัญชีที่ใหญ่กว่าด้วยการเปลี่ยนอีเมลแล้วกดลืมรหัส
- **ถ้าผิด:** แก้ยาก — เป็นช่องยกระดับสิทธิ์
- **ถามเมื่อ:** ไม่ถาม

### USERS-D06: แก้หรือลบบัญชีของตัวเองได้แค่ไหน
- **คำตอบ:** เปลี่ยนสถานะและกลุ่มของตัวเองไม่ได้ ลบตัวเองไม่ได้ ส่วนชื่อและอีเมลของตัวเองแก้ได้
- **เหตุผล:** กันผู้ดูแลล็อกตัวเองออกจนไม่มีใครดูแลระบบ
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือลดเงื่อนไขในฟอร์ม
- **ถามเมื่อ:** ไม่ถาม

### USERS-D07: ผู้ดูแลเลือกสถานะอะไรได้
- **คำตอบ:** Active, Inactive และ Disabled ส่วน Invited ระบบตั้งเอง เลือก Active ให้บัญชีที่ยังไม่ยอมรับข้อกำหนด บัญชียังเป็น Invited จนเข้าครั้งแรก
- **เหตุผล:** Invited หมายถึง "ยังไม่เคยเข้า" ซึ่งผู้ดูแลกำหนดแทนไม่ได้ ชื่อของสถานะที่ไม่ใช่ Active ใช้ตามคำของลูกค้าได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นรายการตัวเลือกบนจอ
- **ถามเมื่อ:** ไม่ถาม

### USERS-D08: การแก้บัญชีมีผลกับเซสชันที่เปิดอยู่อย่างไร
- **คำตอบ:** เปลี่ยนสถานะออกจาก Active เปลี่ยนอีเมล หรือย้ายกลุ่มหรือ role ทำให้เซสชันของบัญชีนั้นจบทันที ส่วนชื่อและเบอร์มีผลรอบเข้าถัดไปโดยไม่ตัดเซสชัน
- **เหตุผล:** สิทธิ์คำนวณตอนเข้าระบบ การตัดเซสชันทำให้สิทธิ์ใหม่มีผลทันทีโดยไม่ต้องตรวจสิทธิ์ใหม่ทุก request
- **ถ้าผิด:** แก้ยาก — คนที่ถูกปิดบัญชีหรือลดสิทธิ์ยังใช้งานต่อได้
- **ถามเมื่อ:** ไม่ถาม

### USERS-D09: ผู้ดูแลรีเซ็ตรหัสให้ผู้ใช้อย่างไร
- **คำตอบ:** ยืนยันก่อน แล้วส่งลิงก์ตั้งรหัสใหม่ (`account.password_link`) ไม่มีรหัสชั่วคราว รหัสเดิมยังใช้ได้จนกว่าจะใช้ลิงก์ ลิงก์ใหม่ยกเลิกลิงก์เก่า จำกัด `{users.reset_links_per_hour}` ลิงก์ต่อชั่วโมงต่อบัญชี และลง Activity Log
- **เหตุผล:** ผู้ดูแลไม่เคยเห็นรหัส และการกดรีเซ็ตโดยไม่ตั้งใจไม่ทำให้ผู้ใช้เข้าระบบไม่ได้
- **ถ้าผิด:** แก้ยาก — อีเมลที่ส่งถึงผู้ใช้และพฤติกรรมของรหัสเดิมเปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### USERS-D10: ลบบัญชีแล้วเกิดอะไร
- **คำตอบ:** ยืนยันแบบย้อนไม่ได้ แล้วลบแบบ soft delete จบเซสชัน ยกเลิกลิงก์ที่ยังไม่ใช้ ลง Activity Log บัญชีที่ลบออกจากรายการและเข้าระบบไม่ได้อีก ชื่อผู้ใช้และอีเมลของบัญชีที่ลบนำไปใช้กับบัญชีใหม่ได้
- **เหตุผล:** ประวัติยังอ้างถึงผู้ทำได้ และคนที่กลับมาทำงานใหม่ใช้อีเมลเดิมได้
- **ถ้าผิด:** แก้ยาก — ข้อมูลที่ลบจริงแล้วกู้ไม่ได้ และประวัติจะอ้างบัญชีที่ไม่มีอยู่
- **ถามเมื่อ:** ไม่ถาม

### USERS-D11: ฟอร์มของบัญชีแสดงประวัติอะไร
- **คำตอบ:** รายการ Activity Log ของบัญชีนั้น ใหม่สุดก่อน แบ่งหน้า: การสร้าง ทุกการแก้ การย้ายกลุ่ม การเปลี่ยนสถานะ ลิงก์รหัส การลบ และการเข้าระบบ พร้อมชื่อผู้ทำ
- **เหตุผล:** ตอบคำถาม "ใครเปลี่ยนอะไรกับบัญชีนี้" ได้จากจอเดียว
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือลดชนิดรายการที่แสดง
- **ถามเมื่อ:** ไม่ถาม

### USERS-D12: สิทธิ์ของจอ Manage Users แยกแค่ไหน
- **คำตอบ:** แยกต่อปุ่มและ endpoint: View (รายการ เปิด ประวัติ), Create, Edit, AssignGroup, ResetPassword, Delete ปุ่มที่ไม่มีสิทธิ์ไม่แสดง และ endpoint ตอบ 403 พร้อม Activity Log
- **เหตุผล:** ให้ผู้ช่วยแก้ชื่อหรือรีเซ็ตรหัสได้โดยไม่ต้องได้สิทธิ์ย้ายกลุ่ม
- **ถ้าผิด:** แก้ทีหลังได้ — รวมหรือแยกสิทธิ์ใน catalog
- **ถามเมื่อ:** ไม่ถาม

### USERS-D13: มีบัญชีของคนนอกที่สังกัดองค์กร (`{org}`) ไหม
- **คำตอบ:** มี เมื่อคนนอก (ลูกค้า ซัพพลายเออร์ ตัวแทน) ต้องเข้าระบบ บัญชีของ `{org}` แยกจากบัญชีพนักงาน เข้าที่ `{org_portal}` และเห็นเฉพาะข้อมูลขององค์กรตัวเอง
- **เหตุผล:** คนนอกมีข้อมูลประจำตัวต่างจากพนักงาน (องค์กร ผู้ติดต่อ) และต้องไม่เห็นเมนูของพนักงานเลย
- **ถ้าผิด:** แก้ยาก — โครงตารางบัญชี พอร์ทัล และขอบเขตข้อมูลเปลี่ยนทั้งหมด
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ไม่มีคนนอกเข้าระบบ ข้ามข้อ USERS-D14 ถึง USERS-D23 c) คนนอกใช้พอร์ทัลเดียวกับพนักงาน แยกด้วยกลุ่ม

### USERS-D14: อีเมลเดียวเป็นบัญชีของหลายองค์กรได้ไหม
- **คำตอบ:** ไม่ได้ หนึ่งอีเมลหนึ่งบัญชีทั่วทั้ง `{org_portal}` อีเมลที่ถูกใช้แล้วถูกปฏิเสธโดยไม่บอกว่าเป็นขององค์กรไหน อีเมลเดียวกันเป็นบัญชีพนักงานและบัญชีองค์กรพร้อมกันได้ เพราะแต่ละพอร์ทัลดูเฉพาะบัญชีของตัวเอง
- **เหตุผล:** ไม่ต้องมีหน้าเลือกองค์กร การล็อกและลืมรหัสนับต่อบัญชีเดียวชัดเจน
- **ถ้าผิด:** แก้ยาก — unique key การล็อก ลืมรหัส และขอบเขตข้อมูลต้องรู้จักองค์กรที่เลือก
- **ถามเมื่อ:** มีบริษัทในเครือที่คนเดียวทำงานให้หลายองค์กร
- **ตัวเลือกอื่น:** b) ได้ เข้าแล้วเลือกองค์กร

### USERS-D15: ในองค์กร ใครเพิ่มและแก้บัญชีขององค์กรได้
- **คำตอบ:** เฉพาะบัญชีที่ role เปิดเมนูบัญชีผู้ใช้ (role ผู้ดูแลขององค์กร) role ของ `{org_portal}` เก็บแยกจากกลุ่มของพนักงาน และฝ่ายพนักงานเป็นผู้กำหนดว่า role ไหนเปิดเมนูอะไร role ผู้ดูแลมีใน seed เปิดทุกเมนู และล็อกไม่ให้เปลี่ยนชื่อ เปลี่ยนเมนู หรือลบ
- **เหตุผล:** พนักงานคนไหนขององค์กรก็ลบบัญชีเพื่อนร่วมงานไม่ได้ ถ้าไม่ได้รับมอบ
- **ถ้าผิด:** แก้ยาก — สิทธิ์ของคนนอกเปลี่ยน
- **ถามเมื่อ:** ลูกค้าต้องการให้ทุกบัญชีจัดการกันเองได้ หรือมีบัญชีหลักคนเดียวที่จัดการ
- **ตัวเลือกอื่น:** b) ทุกบัญชีที่ Active ขององค์กร c) บัญชีหลักขององค์กรคนเดียว

### USERS-D16: บัญชีขององค์กรมี role ย่อยไหม
- **คำตอบ:** ไม่มี ทุกบัญชีขององค์กรถือ role ผู้ดูแลขององค์กร จนกว่าลูกค้าขอแบ่งหน้าที่ กลไกยังรองรับ role ย่อย: เมนูของบัญชีคือเมนูที่ role เปิด คำนวณตอนเข้าระบบ
- **เหตุผล:** องค์กรภายนอกมักมีผู้ใช้ไม่กี่คนที่ทำทุกอย่าง role ย่อยเพิ่มภาระตั้งค่าโดยไม่ได้ประโยชน์
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม role ย่อยบนจอ role ได้โดยไม่แก้ตาราง
- **ถามเมื่อ:** เอกสารลูกค้าแบ่งหน้าที่ของคนในองค์กร (เช่น ฝ่ายขาย ฝ่ายคุณภาพ)
- **ตัวเลือกอื่น:** b) role ย่อยที่ฝ่ายพนักงานตั้งบนจอ และผู้ดูแลขององค์กรเลือกให้แต่ละบัญชี

### USERS-D17: ฝ่ายพนักงานทำอะไรกับบัญชีขององค์กรได้
- **คำตอบ:** ดู เพิ่มบัญชี แก้อีเมล ผู้ติดต่อ role และสถานะ เชิญใหม่ และตั้งบัญชีหลัก เฉพาะองค์กรที่อยู่ในขอบเขตข้อมูลของผู้ทำ องค์กรนอกขอบเขตตอบ not found ทุกครั้งลง Activity Log
- **เหตุผล:** ต้องปิดบัญชีของคนที่ลาออกได้ทันที และกู้องค์กรที่ไม่เหลือใครจัดการบัญชีได้
- **ถ้าผิด:** แก้ยาก — สิทธิ์ของพนักงานต่อข้อมูลคนนอกเปลี่ยน
- **ถามเมื่อ:** ลูกค้าต้องการให้องค์กรดูแลบัญชีของตัวเองทั้งหมด
- **ตัวเลือกอื่น:** b) ดูอย่างเดียว c) ดู ตั้งสถานะ และเชิญใหม่

### USERS-D18: บัญชีแรกขององค์กรมาจากไหน
- **คำตอบ:** พนักงานเพิ่ม หรือมาจากการนำเข้าข้อมูลองค์กร บัญชีแรกถือ role ผู้ดูแลขององค์กร เป็น Invited และเป็นบัญชีหลักขององค์กรเมื่อองค์กรยังไม่มีบัญชีหลัก
- **เหตุผล:** องค์กรต้องมีคนหนึ่งคนที่เข้าระบบแล้วดูแลต่อได้ โดยไม่ต้องรอพนักงานทำทุกบัญชี
- **ถ้าผิด:** แก้ยาก — บัญชีและอีเมลเชิญที่ส่งถึงคนนอกเปลี่ยน
- **ถามเมื่อ:** ลูกค้าให้คนนอกสมัครเอง
- **ตัวเลือกอื่น:** b) สมัครเองแล้วพนักงานอนุมัติ

### USERS-D19: บัญชีขององค์กรได้รหัสผ่านแรกอย่างไร
- **คำตอบ:** รหัสเริ่มต้นแบบสุ่มยาว `{users.initial_password_length}` ตัวที่ผ่านนโยบายรหัส ส่งในอีเมลเชิญ (`account.invite`) ถึงอีเมลของบัญชีนั้นเท่านั้น ระบบเก็บเป็น hash ใน token เชิญที่หมดอายุใน `{users.invite_hours}` ชั่วโมง รหัสในคิวอีเมลเก็บแบบเข้ารหัสและล้างทิ้งหลัง `{users.queued_secret_hours}` ชั่วโมง เข้าครั้งแรกต้องตั้งรหัสใหม่และยอมรับข้อกำหนด
- **เหตุผล:** คนนอกเข้าระบบได้จากอีเมลฉบับเดียว และรหัสเริ่มต้นใช้ได้ครั้งเดียวก่อนถูกบังคับเปลี่ยน
- **ถ้าผิด:** แก้ยาก — อีเมลที่ส่งถึงคนนอกและการเข้าครั้งแรกเปลี่ยน
- **ถามเมื่อ:** ลูกค้าห้ามส่งรหัสผ่านทางอีเมล
- **ตัวเลือกอื่น:** b) ลิงก์ตั้งรหัสแบบบัญชีพนักงาน (USERS-D02)

### USERS-D20: เชิญใหม่ได้เมื่อไร
- **คำตอบ:** เฉพาะบัญชีที่ยังเป็น Invited ไม่ว่าการเชิญเดิมหมดอายุหรือยัง การเชิญใหม่ยกเลิก token เชิญเก่า บัญชี Active ที่ลืมรหัสใช้ลืมรหัสผ่าน องค์กรที่ไม่ Active ไม่ได้รับเชิญจนกว่าองค์กรกลับเป็น Active
- **เหตุผล:** การเชิญซ้ำบัญชีที่ใช้งานอยู่จะทำให้มีรหัสสองชุดที่ใช้ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นเงื่อนไขของปุ่ม
- **ถามเมื่อ:** ไม่ถาม

### USERS-D21: บัญชีหลักขององค์กรคืออะไร
- **คำตอบ:** ผู้ติดต่อขององค์กรที่รายการองค์กรแสดง ไม่ให้สิทธิ์จัดการเพิ่ม เลือกได้จากทุกบัญชีที่ยังไม่ถูกลบขององค์กรนั้น ไม่ว่าสถานะอะไร
- **เหตุผล:** พนักงานต้องรู้ว่าติดต่อใครในองค์กร โดยไม่ผูกกับสิทธิ์
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการแสดงผลและฟิลด์เดียว
- **ถามเมื่อ:** ไม่ถาม

### USERS-D22: องค์กรหนึ่งมีบัญชีได้กี่บัญชี
- **คำตอบ:** ไม่เกิน `{users.org_account_limit}` บัญชีที่ยังไม่ถูกลบ นับขณะล็อกแถวองค์กร เพื่อไม่ให้การเพิ่มพร้อมกันเกินจำนวน
- **เหตุผล:** ลูกค้ามักกำหนดจำนวนบัญชีต่อองค์กรเพื่อคุมคนที่เห็นข้อมูล
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้ง
- **ถามเมื่อ:** เอกสารลูกค้าไม่ระบุจำนวน
- **ตัวเลือกอื่น:** b) ไม่จำกัด

### USERS-D23: พนักงานเปลี่ยนอีเมลของบัญชีองค์กรแล้วเกิดอะไร
- **คำตอบ:** ถือว่าอาจเป็นคนใหม่: ยกเลิก token ที่ยังไม่ใช้ ล้างรหัสผ่านและการยอมรับข้อกำหนด จบเซสชัน บัญชีกลับเป็น Invited และส่งอีเมลเชิญไปอีเมลใหม่เท่านั้น ถ้าบัญชีหรือองค์กรไม่ Active ไม่ส่งเชิญ
- **เหตุผล:** อีเมลเดิมและรหัสเดิมต้องเข้าระบบไม่ได้อีก และเจ้าของอีเมลใหม่ต้องยอมรับข้อกำหนดเอง
- **ถ้าผิด:** แก้ยาก — คนที่ออกไปแล้วยังเข้าระบบด้วยรหัสเดิมได้
- **ถามเมื่อ:** ไม่ถาม

### USERS-D24: หน้า Profile มีที่พอร์ทัลไหน
- **คำตอบ:** `{org_portal}` มี Profile ส่วนพนักงานเปลี่ยนรหัสผ่านเมื่อรหัสหมดอายุ (หน้าเข้าครั้งแรก) หรือผ่านลืมรหัสผ่าน และผู้ดูแลแก้ข้อมูลให้บนจอ Manage Users
- **เหตุผล:** ข้อมูลของพนักงานมาจากผู้ดูแล ส่วนคนนอกดูแลข้อมูลติดต่อของตัวเอง
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหน้า Profile ให้ `{portal}` ใน change ถัดไป
- **ถามเมื่อ:** เอกสารลูกค้ามีหน้า Profile หรือเปลี่ยนรหัสผ่านของพนักงาน
- **ตัวเลือกอื่น:** b) ทุกพอร์ทัลมี Profile พร้อมเปลี่ยนรหัสผ่าน

### USERS-D25: เปลี่ยนอีเมลของตัวเองบน Profile ต้องทำอะไร
- **คำตอบ:** ต้องใส่รหัสผ่านปัจจุบันในการบันทึกเดียวกัน รหัสผิดนับเป็นความพยายามที่ผิดในการล็อก อีเมลใหม่ต้องไม่ซ้ำ บันทึกแล้วบัญชียัง Active ด้วยรหัสเดิม ใช้อีเมลใหม่เข้ารอบถัดไป และเซสชันอื่นของบัญชีจบ
- **เหตุผล:** อีเมลคือชื่อเข้าระบบ คนที่ใช้เครื่องที่ค้างเซสชันไว้จึงยึดบัญชีด้วยการเปลี่ยนอีเมลไม่ได้
- **ถ้าผิด:** แก้ยาก — เป็นช่องยึดบัญชี
- **ถามเมื่อ:** ไม่ถาม

### USERS-D26: เปลี่ยนรหัสผ่านบน Profile
- **คำตอบ:** รหัสปัจจุบัน รหัสใหม่ และยืนยัน ต้องผ่านนโยบายรหัสของแพ็ก auth รหัสปัจจุบันผิดนับในการล็อก บันทึกแล้วตั้งวันหมดอายุใหม่ จบเซสชันอื่นแต่คงเซสชันที่เปลี่ยน และลง Activity Log โดยไม่มีค่ารหัส
- **เหตุผล:** ผู้ใช้เปลี่ยนรหัสเองได้ทันทีเมื่อสงสัยว่ารหัสรั่ว และไม่ถูกดีดออกจากเครื่องที่ใช้อยู่
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นกติกาของจอเดียว
- **ถามเมื่อ:** ไม่ถาม

### USERS-D27: ใครเห็นรหัสผ่านได้บ้าง
- **คำตอบ:** ไม่มีใคร ไม่มี response จอ หรืออีเมลในคิวที่แสดงรหัส hash หรือ token แบบอ่านได้ Activity Log บันทึกว่าคอลัมน์รหัสเปลี่ยนโดยไม่มีค่า บัญชีแสดงเพียงวันที่ส่งเชิญและเชิญหมดอายุหรือยัง ข้อยกเว้นเดียวคือ mailbox ของ prototype ในแพ็ก mail
- **เหตุผล:** รหัสที่ไม่เคยออกจาก server รั่วจากจอหรือ log ไม่ได้
- **ถ้าผิด:** แก้ยาก — รหัสที่รั่วไปแล้วเรียกคืนไม่ได้
- **ถามเมื่อ:** ไม่ถาม
