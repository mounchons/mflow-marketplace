---
name: e2e
description: Write or update the E2E tests of one screen, or of one flow that crosses screens, people and webs (an invitation answered by a supplier, then collected, approved or sent back; a setting made on the admin web as the supplier web shows it), and run only them, when the user calls it once the screens have settled; nothing else in mflow writes or runs E2E tests.
disable-model-invocation: true
argument-hint: "[<screen> [what to cover] | flow <capability, scenario or setting>]"
---

E2E tests drive the real pages in a browser. Written while a screen still changes, they have to be rewritten after every change, and a whole run starts many browsers at once. So mflow writes and runs them only here, one screen at a time, when the user calls it. Tasks, `/opsx:apply`, `/mflow:screen` and the whole suite of `/mflow:test` prove behaviour with unit tests and the build. `/mflow:test e2e` runs every E2E test, also only on the user's call.

## 1. Pick the screen

- Read AGENTS.md `## Stack` (the E2E tests row) and `## Commands` (the E2E command and the build it needs). If `## Stack` is missing or its profile is `TODO`, ask first, as "Asking" in `${CLAUDE_PLUGIN_ROOT}/skills/init/references/stacks.md` describes, and write the section. No E2E framework in the project yet: say so and stop; setting one up is an `/opsx:propose` change.
- No argument: list the screens in `docs/ui/screens.md` with their E2E test files (or none), and when each test file and the screen's UI files last changed (`git log -1`), so the user sees which screens have no tests and which changed after their tests. Ask which one, and stop.
- `<screen>`: find its row in `docs/ui/screens.md` (route, roles, actions, rules) and what it must do: the scenarios in `openspec/specs/` and in open changes that cross it, the UAT or acceptance IDs AGENTS.md names, and its existing E2E test files (search the E2E folder for the route and the page's test ids).
- `flow <capability or scenario>`: the scenarios of that capability in `openspec/specs/` (and in open changes), or the one named, that cross several screens or several roles, such as set up a survey → invite suppliers → a supplier answers and attaches files → collect → send back or keep in the library → build a document from chosen files → approve, reject or withdraw → the supplier acknowledges. List its steps in order, each with its screen (from `docs/ui/screens.md`) and the role that acts, then every path the scenarios name (each send back, reject and withdraw), and show the list to the user before writing.
- The argument may also name a setting (`flow <setting>`), or a step of the flow may set one: something a role sets once on one screen or web (a system setting, a master list, a switch, a template, a required field, a limit) that changes what another role or web shows. Follow it into the capability whose screens show it, even when that is another capability or another web, and list for each setting where it is set, which web, screens and roles show it (the web from the screen's row in `docs/ui/screens.md`, or from the app folder its route lives in), each of its states (on and off, each value), whom it reaches (everyone, or some suppliers only), and when the spec says it takes effect (a Scenario, or a table of when each key applies).
- When the flow crosses more than one web app (an admin web and a supplier web, each with its own address or sign-in), find in AGENTS.md `## Commands` and the project's Playwright config each web's base URL, how it starts for E2E (the config's `webServer` list, or a stack command such as `docker compose … up -d`), and how each Playwright project reaches the API: mocked in the test (`page.route`, a mock server) or the real API. Missing: ask, as "Asking" in `${CLAUDE_PLUGIN_ROOT}/skills/init/references/stacks.md` describes, and write it under `## Commands`.
- **Where each part of a setting is proven.** When the projects of each web mock the API, a setting that crosses webs is proven in three parts, and each part has its own test: (1) the admin web sends it: that page's E2E asserts the request it sends, in each state; (2) the API joins it: an integration test that what is saved through the admin endpoint is what the receiver's endpoint answers, in each state, to whom it reaches and not to the others, and from when; (3) the receiver web shows it: that page's E2E draws each state from a mocked answer typed by the project's API contract (generated types or schema), with the same values as part 1 (one shared constant or fixture, so a change on one side breaks the other). List, for each setting, the test of each part or `missing`. A missing part 2 is reported with the integration test to add, in the change that builds the setting or one of its own; E2E does not stand in for it. A joined test (both webs on the real API) is one per setting, for its main path, in the project that runs the real API, and only when the project has one.

Done when: one screen or one flow is chosen and its scenarios and existing test files are listed, with, for a setting across webs, the test of each of its three parts or `missing`.

## 2. Write

- One test file per screen, or the files the project already has for it, in the project's E2E conventions: its folder, helpers, fixtures or API mocks, and the test names AGENTS.md asks for (such as the UAT Test ID).
- Cover: the page loads as each role in `Role(s)`, with only that role's rows and buttons; each action and each acceptance scenario that crosses this screen; the screenshots that §5 of `${CLAUDE_PLUGIN_ROOT}/skills/theme/references/responsive.md` names, when the project keeps them. For a flow: every path from its first step to its end, and the hand-offs, the second party, the webs and the settings below. "What to cover" in the argument narrows or adds to this.
- An existing test that fails because the screen changed on purpose (its spec or the user says so) is updated to the current behaviour. A test that fails because the screen breaks its spec keeps asserting the spec: report it as a defect in the screen, with the fix as the next step (`/opsx:apply` for a change in progress, `/mflow:screen <screen> …` for a prototype). This command changes test files only.

Done when: every scenario of the screen or the flow has a test, or the user narrowed the scope.

## A flow across screens, people and webs

One test per path, the people taking turns in it:
- **One browser context per role** in the same test (`browser.newContext()`, each logged in as its role, or from the project's saved login states; in prototype mode, the role switcher of each context). Contexts share the worker's one browser, so the cap on browsers still holds.
- **Links people get by mail** (an invitation, a notice): from the project's fake mailer, outbox table or test endpoint, as its integration tests read them, never from real mail. No such seam: say so; adding one is an `/opsx:propose` change.
- **What was set arrives as set:** keep the values the sender set in the test's own variables (questions, options, required files, deadline, message) and assert, on the receiver's page, each one shown as set, and that a setting that hides something hides it. The answers and files sent back reach the next role and the place they are kept (a library), and a document built from chosen files carries them.
- **Every decision shows on both sides:** after send back, reject, approve, withdraw or acknowledge, assert on each role's page the new state, the reason, and the actions now offered and the ones gone.
- **A second outside party:** a second account of the outside role (supplier B) opens supplier A's record by its direct URL, A's file download URL, its own list, search, counts and notifications: nothing of A's shows, and the direct links are refused. Check the API answer too when the page only hides it.
- **Files:** upload from the project's fixtures (`setInputFiles`); for a file or document the system builds, wait for the download and assert its name, type and size, and its text when the project can read it.
- **Background steps** (collecting answers, building a document, sending mail): wait for the state on the page or through the API, within the project's timeout. Never a fixed sleep.
- **Data:** each test makes its own records with unique names, unless the project's E2E tests are one ordered story on one database.
- **Several webs:** when the roles work on different web apps, open each role's context on its own web (`browser.newContext({ baseURL, storageState })` with that web's base URL and that web's login: a saved state, or the project's sign-in helper that signs in through the API and then opens the page), never every context on the one `use.baseURL`. Two webs on one host with different ports share their cookies, because cookies do not keep ports apart: a context per web keeps the sessions apart, and one context for both works only when the webs name their cookies differently. Both webs run before the test: from the Playwright config's `webServer` list, or the stack command in AGENTS.md `## Commands`; a stack that is not up is said so before the run, not left to fail. A link in a mail that leads to the other web is followed as it is, and the test asserts it opens on that web's address. Still one browser per worker.
- **Calls to the API from the test** (to arrange data, to check what a page only hides, to put things back) go through the project's helper that sends what the web sends (its session and CSRF token), or the API refuses them before they reach the check the test means to prove.
- **A setting that reaches another web:** for a value a role sets once for everyone or for a group (not a value of one record, which the hand-off above covers), test each state. In a project on the real API: set it on the admin web, then on the receiver's page, reloaded or opened again after the change, assert it shows exactly as set; turn it off or change it, and assert the page follows, that what was turned off is gone by its direct link too, and the API answer when the page only hides it. In a project that mocks the API, setting it on one page and looking at the other shows only the mock: write parts 1 and 3 of §1 instead, the same values in both. Wait for the new state within the project's timeout, never a fixed sleep. A page that does not follow is a defect, unless the spec says when the change takes effect (a cache's time, the next sign-in); then test that. A setting for some suppliers only is also asserted absent for supplier B outside it.
- **Data every test reads** (settings, groups' grants and scopes, templates, seed records, the test clock): a test that changes it changes what the other tests see while they run. Prefer a value scoped to records the test made (its own group or category). Otherwise the test goes in a file of tests that write (such as `*.writes.spec.ts`), run in a Playwright project of its own after the read-only ones: that project lists the read-only project in `dependencies` and has `workers: 1`, because serial mode alone keeps one file's tests in order but still runs files side by side. Each test puts back what it changed in a `finally` (or `afterEach`), never only at the end of the test body, where a failure midway leaves it changed for every later test and run. Records a test makes carry a run stamp in their names (`Date.now().toString(36)`), so a second run on the same database does not collide, and records the rules forbid deleting are cleaned up the way the rules allow (withdraw, then reject).

A scenario of the flow that the specs do not have (what the supplier sees of a setting in each state, whom a setting reaches, what another supplier sees) is not invented in the test: report it as missing from the spec, with the scenario to add, and test what the spec says.

## 3. Run

- Only this screen's or this flow's test files, in the foreground, after the build the E2E command needs (AGENTS.md `## Commands`), with at most 2 browsers at a time: `--workers=2` for Playwright Test. `e2eMaxWorkers` in `.mflow/config.json` raises the cap when the user wants more, and mflow's hook refuses a Playwright run above it or without `--workers`. Playwright's default is half the CPU threads, 10 on a 20-thread laptop; that many browsers at once has crashed a laptop's graphics driver and restarted the machine.
- Never the whole E2E suite here: that is `/mflow:test e2e`.
- When AGENTS.md marks the E2E command `(unverified)` and this run worked, remove the mark.

Done when: the files ran, with passed, failed and skipped counts and the first line of each failure.

## 4. Record

Write the run the way `/mflow:test` records one (its §3), with `Scope: e2e <screen>` or `Scope: e2e flow <name>`. A record of one screen or one flow never counts as the whole suite.

Tell the user the test files written or changed, the result, any defect found in the screen, and the next step: the fix for a defect, or the next screen with no tests or changed after its tests (`/mflow:e2e <screen>`), or the next flow (`/mflow:e2e flow <name>`); and any scenario found missing from the spec, as an `/opsx:propose` change. Write it into STATUS.md `## Now`.

Done when: the screen's test files exist and ran, the record exists, and the user has the result and the next command.
