# auth: ข้อที่ตอบไว้แล้ว

### AUTH-D01: ใช้อะไรเป็นชื่อเข้าระบบ
- **คำตอบ:** อีเมล เทียบแบบไม่สนตัวพิมพ์และตัดช่องว่างหัวท้าย ชื่อผู้ใช้ถ้ามีเก็บไว้เป็นชื่อที่แสดง ไม่ใช้เข้าระบบ
- **เหตุผล:** อีเมลใช้ส่ง OTP ลิงก์ตั้งรหัส และแจ้งเตือนได้ในตัว ผู้ใช้ไม่ต้องจำชื่ออีกชื่อ
- **ถ้าผิด:** แก้ยาก — คีย์ค้นบัญชี หน้าเข้าระบบ การล็อก และอีเมลเชิญเปลี่ยนทั้งหมด
- **ถามเมื่อ:** เอกสารลูกค้าระบุให้เข้าด้วยชื่อผู้ใช้ หรือมีผู้ใช้กลุ่มที่ไม่มีอีเมล
- **ตัวเลือกอื่น:** b) ชื่อผู้ใช้อย่างเดียว c) ช่องเดียวรับได้ทั้งอีเมลและชื่อผู้ใช้ (ล็อกต้องนับสองชื่อของบัญชีเดียวรวมกัน)

### AUTH-D02: ระบบที่มีหลายพอร์ทัลเก็บบัญชีอย่างไร
- **คำตอบ:** แต่ละพอร์ทัลมีตารางบัญชีของตัวเองเมื่อข้อมูลของบัญชีต่างกัน ทุกตารางบัญชีใช้ `id` ของแถวในทะเบียนผู้ทำ `actor` ของแพ็ก `audit` เป็นคีย์ ตารางรหัสผ่าน เซสชัน โทเค็น และการเข้าผิดมีชุดเดียวที่มีคอลัมน์พอร์ทัล บัญชีของพอร์ทัลหนึ่งเข้าอีกพอร์ทัลไม่ได้
- **เหตุผล:** ไม่มีคอลัมน์ว่างครึ่งตาราง กติกาของแต่ละฝั่งชัด แต่คอลัมน์ผู้ทำทุกตารางยังชี้ที่เดียว และกลไกรหัสผ่านเขียนครั้งเดียว
- **ถ้าผิด:** แก้ยาก — โครงตารางบัญชี foreign key ของคอลัมน์ผู้ทำ และโค้ดยืนยันตัวตนทั้งชุด
- **ถามเมื่อ:** ระบบมีมากกว่าหนึ่งพอร์ทัล หรือมีผู้ใช้หลายกลุ่มที่ข้อมูลบัญชีต่างกันมาก
- **ตัวเลือกอื่น:** b) ตารางบัญชีเดียวมีคอลัมน์พอร์ทัลและ CHECK ต่อพอร์ทัล c) ตารางฐานร่วม + ตารางส่วนขยายต่อพอร์ทัลแบบ 1:1

### AUTH-D03: อีเมลเดียวมีได้กี่บัญชี
- **คำตอบ:** หนึ่งอีเมลหนึ่งบัญชีต่อพอร์ทัล ในบัญชีที่ยังไม่ถูกลบ อีเมลเดียวกันอยู่คนละพอร์ทัลได้และเป็นคนละบัญชี
- **เหตุผล:** ไม่ต้องมีหน้าเลือกองค์กรหลังเข้าระบบ และลืมรหัส ล็อก OTP นับต่อบัญชีได้ตรงๆ
- **ถ้าผิด:** แก้ยาก — unique index การค้นบัญชีตอนเข้าระบบ และหน้าเลือกองค์กรที่ต้องเพิ่ม
- **ถามเมื่อ:** ผู้ใช้คนเดียวต้องมีหลายบัญชีในพอร์ทัลเดียว เช่น ทำงานให้หลายบริษัทคู่ค้า
- **ตัวเลือกอื่น:** b) อีเมลซ้ำได้ต่างองค์กร และมีหน้าเลือกองค์กรหลังรหัสผ่านถูก

### AUTH-D04: บัญชีที่สังกัดองค์กรเข้าได้เมื่อไร
- **คำตอบ:** บัญชีเข้าได้เมื่อทั้งบัญชีและ `{org}` ของบัญชีอยู่ในสถานะที่เข้าได้ องค์กรถูกระงับแล้วทุกบัญชีขององค์กรเข้าไม่ได้และเซสชันสิ้นสุด โดยข้อความไม่บอกว่าเป็นเพราะองค์กร
- **เหตุผล:** ระงับคู่ค้าทั้งรายได้ในครั้งเดียว ไม่ต้องไล่ปิดทีละบัญชี
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มเงื่อนไขในการตรวจสถานะ ไม่ต้องย้ายข้อมูล
- **ถามเมื่อ:** บัญชีของพอร์ทัลสังกัดองค์กร เช่น บริษัทคู่ค้า ลูกค้านิติบุคคล หรือสาขา
- **ตัวเลือกอื่น:** b) ดูสถานะของบัญชีอย่างเดียว ระงับองค์กรไม่กระทบการเข้าระบบ

### AUTH-D05: บัญชีมีสถานะอะไร และสถานะไหนเข้าได้
- **คำตอบ:** Active, Invited, Inactive, Disabled โดย Active และ Invited (ที่มีรหัสผ่านแล้ว) เข้าได้ Inactive และ Disabled เข้าไม่ได้ Invited เป็น Active เมื่อเข้าครั้งแรกสำเร็จ
- **เหตุผล:** แยกบัญชีที่ยังไม่เคยเข้า (Invited) จากบัญชีที่ปิดชั่วคราว (Inactive) และปิดถาวร (Disabled) ได้ชัด
- **ถ้าผิด:** แก้ยาก — ค่าที่เก็บในตาราง การตรวจตอนเข้าระบบ และจอจัดการผู้ใช้
- **ถามเมื่อ:** เอกสารลูกค้ากำหนดสถานะอื่น เช่น Suspended หรือ Locked ที่ผู้ดูแลตั้งเอง
- **ตัวเลือกอื่น:** b) ใช้ชื่อสถานะตามเอกสารลูกค้า แล้วจับคู่ว่าแต่ละสถานะเข้าได้หรือไม่

### AUTH-D06: เข้าไม่สำเร็จแล้วบอกอะไร
- **คำตอบ:** ไม่พบอีเมล รหัสผิด และบัญชีที่ยังไม่มีรหัส ได้ข้อความเดียวกันทุกตัวอักษร ส่วนรหัสถูกแต่สถานะเข้าไม่ได้ ได้ข้อความให้ติดต่อผู้ดูแลโดยไม่บอกสถานะ
- **เหตุผล:** คนนอกเดาไม่ได้ว่าอีเมลไหนมีบัญชี และไม่รู้ว่าบัญชีถูกปิด
- **ถ้าผิด:** แก้ทีหลังได้ — แก้ข้อความและเงื่อนไข ไม่มีข้อมูลเปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D07: ตรวจอะไรก่อนหลัง
- **คำตอบ:** ล็อก → อีเมลและรหัสผ่าน → สถานะ → รหัส OTP (เมื่อสวิตช์เปิดและ browser ไม่ถูกจำ) → การเข้าครั้งแรกที่ยังค้าง
- **เหตุผล:** ล็อกต้องมาก่อนเพื่อไม่ให้เดาต่อได้ และสถานะต้องตรวจหลังรหัสถูกเพื่อไม่บอกสถานะกับคนที่ไม่รู้รหัส
- **ถ้าผิด:** แก้ทีหลังได้ — สลับลำดับในโค้ดจุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D08: ล็อกเมื่อผิดซ้ำอย่างไร
- **คำตอบ:** ผิด `auth.lock_failures` ครั้งใน `auth.lock_window_minutes` นาทีต่อพอร์ทัลต่ออีเมลที่พิมพ์ ล็อก `auth.lock_minutes` นาที นับชื่อที่ไม่มีจริงด้วย ข้อความล็อกเหมือนกันทุกชื่อ ล็อกห้ามแค่การเข้าใหม่ เซสชันที่เปิดอยู่ยังใช้ได้ คำขอของชื่อเดียวกันตัดสินทีละครั้ง
- **เหตุผล:** กันการเดารหัสโดยไม่บอกว่าชื่อไหนมีจริง และกันสคริปต์ที่ส่งพร้อมกันหลายคำขอ
- **ถ้าผิด:** แก้ทีหลังได้ — ค่าตัวเลขปรับได้ และตารางการเข้าผิดมีอยู่แล้ว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D09: เซสชันเก็บที่ไหน
- **คำตอบ:** ทุกการเข้าระบบเปิดเซสชันหนึ่งแถวฝั่ง server ที่เก็บแค่ hash ส่วนวิธีที่ client ถือเซสชันขึ้นกับว่า client อยู่ที่ไหน: เว็บที่อยู่ origin เดียวกับ API (ค่าเริ่มต้นของแพ็ก `api` ทั้งเว็บที่ render ฝั่ง server และเว็บที่เรียก API เช่น React, Vue, Angular) ใช้ cookie ของพอร์ทัลที่ script อ่านไม่ได้ ตรวจกับแถวทุกคำขอ ส่วนแอป mobile ระบบอื่นที่ทำแทนผู้ใช้ และเว็บที่อยู่คนละ origin กับ API ใช้ JWT access token อายุ `auth.access_token_minutes` นาทีใน header `Authorization` คู่กับ refresh token ของเซสชันที่หมุนทุกครั้งที่ใช้ (AUTH-D31) เว็บคนละ origin ต้องอยู่ site เดียวกับ API (โดเมนย่อย) เพราะ cookie ของ refresh token เป็น `SameSite=Strict` เว็บที่อยู่คนละ site แพ็กนี้ไม่รองรับ บัญชีหนึ่งเปิดได้หลายเซสชัน
- **เหตุผล:** cookie ที่ script อ่านไม่ได้ไม่มี token ให้ขโมย ตัดเซสชันแล้วมีผลคำขอถัดไป และงานฝั่งหน้าเว็บน้อยกว่า token จึงใช้เฉพาะ client ที่ cookie ใช้ไม่ได้ ทั้งสองแบบยังตัดเซสชันจาก server ได้ และของที่หลุดจากฐานข้อมูลใช้เข้าระบบไม่ได้
- **ถ้าผิด:** แก้ยาก — วิธีรู้ว่าใครใช้งานของทุก endpoint และทุกหน้าเว็บ
- **ถามเมื่อ:** ไม่ถาม
- **ตัวเลือกอื่น:** b) เว็บที่เรียก API ใช้ token แม้อยู่ origin เดียวกัน ตรวจได้โดยไม่อ่านฐานข้อมูลทุกคำขอ แต่มีงาน refresh ฝั่งหน้าเว็บ และการตัดเซสชันมีผลช้าตามอายุ access token c) JWT ทุกแอป รวมเว็บที่ render ฝั่ง server ซึ่งต้องเก็บ token ไว้ใน cookie เอง

### AUTH-D10: เซสชันอยู่นานแค่ไหน
- **คำตอบ:** ไม่ใช้งานครบ `auth.session_idle_minutes` นาทีหมด และหมดเสมอเมื่อครบ `auth.session_max_minutes` นาทีหลังเข้า แต่ละพอร์ทัลมีค่าของตัวเอง การใช้งานคือคำขอที่มี cookie ของเซสชัน หรือการขอ access token ใหม่ด้วย refresh token แอปขอ access token ใหม่เมื่อมีคำขอที่ต้องใช้เท่านั้น ไม่ขอตามเวลา
- **เหตุผล:** ค่าเริ่มต้นยาวพอให้ทำงานทั้งวันโดยไม่เสียงานที่พิมพ์ค้าง เพราะแพ็กรุ่นนี้ยังไม่มีหน้าต่างเตือนก่อนหมดเวลา
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งระบบ เปลี่ยนแล้วมีผลกับคำขอถัดไป
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ไม่ใช้งานครบ 15–30 นาทีตามเอกสารลูกค้า พร้อมหน้าต่างเตือนก่อนหมดเวลา (ต้องสร้างเพิ่ม ไม่อยู่ในแพ็กนี้) c) ค่าสั้นโดยไม่มีหน้าต่างเตือน ผู้ใช้เสียงานที่พิมพ์ค้าง

### AUTH-D11: กันคำขอปลอมจากเว็บอื่นอย่างไร
- **คำตอบ:** เซสชันใน cookie: ทุกคำขอที่เขียนข้อมูลต้องมี header ที่ตรงกับ CSRF token ของเซสชัน เซสชันแบบ token: คำขอ API ใช้ header `Authorization` ที่ browser ไม่แนบเอง จึงไม่ต้องมี CSRF token ส่วน cookie ของ refresh token ตั้ง `SameSite=Strict` และส่งไปแค่ path ของการขอ token ใหม่และการออกจากระบบ คำขอเข้าระบบ ส่งรหัส ลืมรหัส ตั้งรหัสใหม่ ขอ token ใหม่ และออกจากระบบของเซสชันแบบ token ต้องมี `Origin` ตรงกับที่อยู่ของพอร์ทัลนั้น
- **เหตุผล:** กันเว็บอื่นสั่งงานแทนผู้ใช้ และกันเว็บอื่นพา browser เข้าระบบด้วยบัญชีของผู้โจมตี
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มการตรวจที่ middleware จุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D12: การเปลี่ยนแปลงไหนตัดเซสชันของบัญชี
- **คำตอบ:** สถานะที่ไม่ใช่ Active ถูกลบ อีเมลเข้าระบบเปลี่ยน รหัสผ่านเปลี่ยน และสิ่งที่กำหนดสิทธิ์เปลี่ยน (กลุ่มหรือ role ที่แพ็ก `permission` บอก) เซสชันที่เปลี่ยนรหัสหรืออีเมลของตัวเองอยู่ต่อ ชื่อหรือเบอร์โทรเปลี่ยนไม่ตัด การตัดต้องถูกแม้การเข้าระบบเกิดพร้อมกับการเปลี่ยน เซสชันแบบ token: refresh token ใช้ไม่ได้ทันที ส่วน access token ที่ออกไปแล้วใช้ต่อได้จนหมดอายุ ไม่เกิน `auth.access_token_minutes` นาที
- **เหตุผล:** สิทธิ์และตัวตนในเซสชันต้องตรงกับบัญชีเสมอ
- **ถ้าผิด:** แก้ยาก — ถ้าไม่ตัด คนที่ถูกปิดบัญชียังใช้งานต่อได้จนเซสชันหมด
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D13: รหัสผ่านต้องเป็นแบบไหน
- **คำตอบ:** ยาว `auth.password_min_length`–`auth.password_max_length` ตัว มีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก และตัวเลขเสมอ อักขระพิเศษเป็นสวิตช์ `auth.password_require_special` และห้ามซ้ำ `auth.password_history` รหัสล่าสุด รหัสที่ไม่ผ่านบอกทุกข้อที่ผิดพร้อมตัวเลขปัจจุบัน
- **เหตุผล:** ตรงกับนโยบายที่ลูกค้าองค์กรไทยส่วนใหญ่ขอ และผู้ใช้รู้ว่าต้องแก้อะไรในครั้งเดียว
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งระบบ รหัสที่ตั้งไว้แล้วใช้ต่อได้จนหมดอายุ
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D14: รหัสผ่านหมดอายุไหม
- **คำตอบ:** หมดอายุ `auth.password_expiry_days` วันตามปฏิทินนับจากเวลาที่ตั้ง ตามเขตเวลาของระบบ หมดแล้วเข้าได้แต่ต้องตั้งรหัสใหม่ก่อนทำอย่างอื่น เปลี่ยนค่าแล้วคำนวณวันหมดอายุของทุกบัญชีใหม่จากเวลาที่ตั้งรหัส ในการบันทึกเดียวกัน
- **เหตุผล:** นับตามปฏิทินไม่ต้องมีตารางวันหยุด และทุกบัญชีอยู่ใต้กฎเดียวกันทันทีที่เปลี่ยนค่า
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งระบบ วันหมดอายุคำนวณใหม่ได้จากเวลาที่ตั้งรหัส
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D15: เก็บรหัสผ่านอย่างไร
- **คำตอบ:** เก็บเฉพาะ hash แบบมี salt และช้าโดยตั้งใจ เช่น Argon2id ไม่มีจอไหน log ไหน หรือ Activity Log ไหนแสดงรหัสผ่าน hash โทเค็น หรือรหัส OTP
- **เหตุผล:** ฐานข้อมูลหลุดแล้วยังเดารหัสได้ยาก
- **ถ้าผิด:** แก้ยาก — เปลี่ยนวิธี hash ภายหลังต้องรอให้ทุกคนเข้าระบบใหม่
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D16: ลืมรหัสผ่านทำอย่างไร
- **คำตอบ:** ใส่อีเมลแล้วตอบข้อความกลางๆ เดียวกันเสมอ ส่งลิงก์เฉพาะบัญชีของพอร์ทัลนั้นที่เข้าได้ (Active หรือ Invited) และไม่เกิน `auth.link_requests_per_hour` ลิงก์ต่อชั่วโมง บัญชี Invited ใช้ลืมรหัสได้ แต่ยังต้องเข้าครั้งแรกเพื่อยอมรับ `{terms}`
- **เหตุผล:** ไม่บอกว่าอีเมลไหนมีบัญชี กันการยิงอีเมลใส่ผู้ใช้ และผู้ใช้ที่คำเชิญหมดอายุไม่ติดค้าง
- **ถ้าผิด:** แก้ทีหลังได้ — เงื่อนไขในจุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D17: ลิงก์ตั้งรหัสใหม่ทำงานอย่างไร
- **คำตอบ:** โทเค็นสุ่ม ใช้ครั้งเดียว อายุ `auth.link_hours` ชั่วโมง เก็บแค่ hash อยู่หลัง `#` ของลิงก์และส่งให้ API ใน body เท่านั้น ลิงก์ใหม่ยกเลิกลิงก์และรหัสเริ่มต้นเก่าที่ยังไม่ใช้ ใช้ได้เฉพาะพอร์ทัลของบัญชี ตั้งรหัสแล้วตัดทุกเซสชันของบัญชีและไม่พาเข้าระบบ
- **เหตุผล:** web server และ API ไม่ log โทเค็น และลิงก์ที่หลุดใช้ซ้ำไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — อายุเป็นค่าตั้งระบบ
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D18: บัญชีใหม่เข้าครั้งแรกด้วยรหัสเริ่มต้นได้ไหม
- **คำตอบ:** ได้ เมื่อแพ็ก `users` ส่งรหัสเริ่มต้นในอีเมลเชิญ: รหัสสุ่ม ใช้ครั้งเดียว อายุ `auth.starting_password_hours` ชั่วโมง เก็บแค่ hash คำเชิญใหม่ยกเลิกรหัสเก่า รหัสที่หมดอายุหรือใช้แล้วได้ข้อความบอกให้ใช้ลืมรหัสผ่าน และนับเป็นการเข้าผิด
- **เหตุผล:** คู่ค้าที่ถูกนำเข้าเป็นชุดเข้าได้ทันทีจากอีเมลเดียว โดยไม่ต้องกดลิงก์ก่อน
- **ถ้าผิด:** แก้ยาก — สิ่งที่ส่งถึงลูกค้าในอีเมลเชิญ
- **ถามเมื่อ:** แพ็ก `users` เลือกเชิญด้วยลิงก์ตั้งรหัสอย่างเดียว
- **ตัวเลือกอื่น:** b) ไม่มีรหัสเริ่มต้น ทุกบัญชีใหม่ได้ลิงก์ตั้งรหัส

### AUTH-D19: เข้าครั้งแรกต้องทำอะไร
- **คำตอบ:** ค้างเมื่อยังไม่มีรหัสของตัวเอง รหัสหมดอายุ หรือยังไม่ยอมรับ `{terms}` ระหว่างค้างเห็นได้แค่หน้าเข้าครั้งแรก ทุก API ยกเว้นข้อมูลผู้ใช้ปัจจุบัน การบันทึกหน้านี้ และออกจากระบบ ตอบ `FIRST_LOGIN_REQUIRED` บันทึกแล้ว Invited เป็น Active และเก็บเวลาและรุ่นของ `{terms}`
- **เหตุผล:** ทุกบัญชีมีรหัสที่ตั้งเองและยอมรับข้อกำหนดก่อนเห็นข้อมูลจริง ตาม PDPA
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มหรือลดส่วนของหน้าได้โดยไม่ย้ายข้อมูล
- **ถามเมื่อ:** ลูกค้าไม่ต้องการให้ยอมรับข้อกำหนดในระบบ
- **ตัวเลือกอื่น:** b) หน้าเข้าครั้งแรกมีแค่ตั้งรหัสใหม่ ไม่มีการยอมรับข้อกำหนด

### AUTH-D20: เข้าระบบแล้วไปหน้าไหน
- **คำตอบ:** ไปหน้าที่ขอไว้ (`next`) เมื่อเป็น path ของเว็บเดียวกันที่ขึ้นต้นด้วย `/` ตัวเดียว ไม่มี scheme host หรือ backslash และไม่ใช่หน้าเข้าระบบ ไม่อย่างนั้นไป `{start_page}` หน้าใดที่เปิดโดยไม่มีเซสชันพาไปหน้าเข้าระบบพร้อม `next`
- **เหตุผล:** ลิงก์ในอีเมลพาไปถึงหน้าที่ต้องการ และกันการพาออกไปเว็บอื่น
- **ถ้าผิด:** แก้ทีหลังได้ — กติกาในจุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D21: การเข้าระบบลง Activity Log แค่ไหน
- **คำตอบ:** ลงใต้บัญชีที่มีจริงเท่านั้น: เข้าสำเร็จ ออก เข้าผิด ถูกปฏิเสธเพราะสถานะ ถูกล็อก ขอลิงก์ เปลี่ยนรหัส และยอมรับข้อกำหนด ชื่อที่ไม่มีจริงอยู่แค่ในตารางการเข้าผิดที่ลบตามอายุ
- **เหตุผล:** มีหลักฐานของบัญชีจริงครบ และไม่เสี่ยงเก็บรหัสที่พิมพ์ผิดช่องไว้ถาวร
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มชนิดรายการภายหลังได้
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D22: ตารางชั่วคราวของการเข้าระบบเก็บนานแค่ไหน
- **คำตอบ:** งานรายวันลบเซสชันที่หมดอายุแล้ว `auth.purge_session_days` วัน การเข้าผิดเก่ากว่า `auth.purge_attempt_days` วัน (หรือนานกว่านั้นเมื่อหน้าต่างล็อกรวมเวลาล็อกยาวกว่า) การรอรหัส OTP และ browser ที่หมดเวลา และลิงก์ที่หมดอายุแล้ว `auth.purge_link_days` วัน ไม่ลง Activity Log
- **เหตุผล:** ตารางไม่โต และยังแยกลิงก์ที่หมดอายุจากลิงก์ที่ไม่มีจริงได้ช่วงหนึ่ง
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งระบบ
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D23: มี OTP ทางอีเมลไหม
- **คำตอบ:** มีกลไก OTP ทางอีเมลหลังรหัสผ่าน เปิดปิดแยกต่อพอร์ทัลบนหน้าตั้งค่าระบบ (AUTH-D24) ค่าเริ่มต้นปิด
- **เหตุผล:** environment ที่ยังไม่มีตัวส่งอีเมลยังเข้าระบบได้ และพอร์ทัลที่อยู่บน internet เปิดได้ก่อน
- **ถ้าผิด:** แก้ทีหลังได้ — เปิดปิดบนหน้าตั้งค่าระบบ ไม่ต้อง deploy
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) เปิดเฉพาะพอร์ทัลที่อยู่บน internet c) เปิดทุกพอร์ทัล d) ไม่มี OTP

### AUTH-D24: สวิตช์ OTP อยู่ที่ไหน
- **คำตอบ:** ค่า `auth.otp_enabled` ต่อพอร์ทัลบนหน้าตั้งค่าระบบ เปลี่ยนแล้วมีผลกับการเข้าครั้งถัดไป ไม่ตัดเซสชันที่เปิดอยู่ ปิดต้องยืนยันและลง Activity Log ทางฉุกเฉินเมื่ออีเมลส่งไม่ได้จนไม่มีใครเข้าระบบได้: env `AUTH_OTP_OFF` เป็น true ปิด OTP ทุกพอร์ทัลตั้งแต่ start โดยไม่แก้ค่าบนจอ และหน้าตั้งค่าแสดงว่าถูกปิดด้วย env
- **เหตุผล:** ผู้ดูแลเปิดปิดเองได้โดยไม่ต้องให้ IT แก้ env และ restart แต่ถ้าอีเมลล่ม ผู้ดูแลก็ผ่าน OTP เข้าหน้าตั้งค่าไม่ได้ จึงต้องมีทางปิดจาก env
- **ถ้าผิด:** แก้ทีหลังได้ — ค่าตั้งระบบหนึ่งค่ากับ env หนึ่งตัว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D25: ใส่รหัส OTP ผิดแล้วเป็นอย่างไร
- **คำตอบ:** ผิดแต่ละครั้งนับเป็นการเข้าผิดในล็อกเดียวกับรหัสผ่าน ผิดครบ `auth.otp_wrong_codes` ครั้งในการรอเดียวต้องเริ่มที่รหัสผ่านใหม่ รหัสที่หมดอายุไม่นับ ส่งรหัสใหม่ได้หลังรอ `auth.otp_resend_seconds` วินาที ไม่เกิน `auth.otp_codes_per_hour` รหัสต่อชั่วโมง
- **เหตุผล:** คนที่ได้รหัสผ่านไปแล้วเดารหัส OTP ต่อไม่ได้ และกันการยิงอีเมล
- **ถ้าผิด:** แก้ทีหลังได้ — ค่าตัวเลขปรับได้
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D26: จำ browser ที่ผ่าน OTP ไหม
- **คำตอบ:** จำต่อ browser และบัญชี `auth.otp_remember_hours` ชั่วโมงนับจากรหัสที่ถูก ไม่ต่ออายุตามการใช้ หนึ่ง browser จำได้หนึ่งบัญชีต่อพอร์ทัล ไม่ข้ามรหัสผ่าน ล็อก หรือสถานะ ลืมทุก browser ของบัญชีเมื่อรหัสผ่านหรือสิทธิ์เปลี่ยน ค่า 0 ถามทุกครั้ง
- **เหตุผล:** ผู้ใช้ไม่ต้องกรอกรหัสหลายครั้งต่อวัน แต่คนที่ได้รหัสผ่านไปยังต้องมี OTP บนเครื่องอื่น
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นค่าตั้งระบบ
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D27: ค่าตัวเลขของแพ็กปรับได้ไหม
- **คำตอบ:** ทุกค่าใน params.md อยู่บนหน้าตั้งค่าระบบของแพ็ก `settings` อ่านใหม่ทุกครั้งที่ใช้ ปรับได้เฉพาะในช่วงของ params.md ปลายช่วงคือค่าที่หลวมที่สุดที่ยอมให้ตั้ง การเปลี่ยนลง Activity Log ค่าที่เอกสารลูกค้ากำหนดเป็นค่าเริ่มต้นแทน และเป็นขอบใหม่ที่ห้ามหลวมกว่า กุญแจเซ็น token ไม่อยู่บนจอ (AUTH-D32)
- **เหตุผล:** ลูกค้าปรับนโยบายได้เองโดยไม่ deploy และไม่มีใครทำให้ระบบอ่อนกว่าที่ตกลงไว้
- **ถ้าผิด:** แก้ทีหลังได้ — ช่วงของค่าเปลี่ยนได้ในรุ่นถัดไป
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D28: บัญชีสำหรับทดสอบมาจากไหน
- **คำตอบ:** seed เฉพาะ Development และ Prototype ทุกบัญชีของพอร์ทัลหนึ่งใช้รหัสร่วมจาก env ของพอร์ทัลนั้น (`PROTOTYPE_<PORTAL>_PASSWORD`) ที่ต้องผ่านนโยบายรหัสผ่าน และมีบัญชีที่ถูกปิดหนึ่งบัญชีไว้ทดสอบ environment อื่นไม่มีบัญชี seed
- **เหตุผล:** ลองเข้าระบบจริงได้ตั้งแต่วันแรก และไม่มีรหัสใดอยู่ใน repo
- **ถ้าผิด:** แก้ทีหลังได้ — ข้อมูลทดสอบเท่านั้น
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D29: ตัวสลับผู้ใช้ของ prototype ทำงานอย่างไรเมื่อมีการเข้าระบบจริง
- **คำตอบ:** ต้องเข้าระบบก่อน แล้วสลับเป็นบัญชีอื่นของพอร์ทัลเดียวกันได้โดยไม่ถามรหัส เฉพาะโหมด prototype ไม่ถาม OTP และลง Activity Log ว่าเป็นการสลับ พอร์ทัลที่เปิดสู่ internet ไม่มีตัวสลับ
- **เหตุผล:** สาธิตหลายบทบาทได้เร็ว โดยไม่มีใครเข้าเป็นผู้ดูแลได้โดยไม่รู้รหัส
- **ถ้าผิด:** แก้ทีหลังได้ — ใช้เฉพาะ environment ทดสอบ
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D30: cookie ติด Secure เมื่อไร
- **คำตอบ:** cookie ทุกตัวของแพ็กนี้ (เซสชัน, refresh token, การรอรหัส OTP, browser ที่จำ) ติด Secure เสมอ ยกเว้น Development และ Prototype ที่ติดเมื่อคำขอมาทาง HTTPS เท่านั้น
- **เหตุผล:** server ทดสอบที่ยังเป็น HTTP เข้าระบบได้ ส่วน environment จริงไม่มีช่องโหว่
- **ถ้าผิด:** แก้ทีหลังได้ — ค่าใน startup
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D31: refresh token หมุนอย่างไร
- **คำตอบ:** ใช้กับเซสชันแบบ token refresh token เป็นค่าสุ่มของเซสชัน เก็บแค่ hash ทุกครั้งที่ขอ access token ใหม่ได้ refresh token ใหม่ และตัวเก่าขอต่อไม่ได้ ตัวเก่าที่ส่งมาอีกภายใน 30 วินาทีหลังหมุน (หลายแท็บขอพร้อมกัน) ได้ access token ใหม่ของเซสชันเดิมแต่ไม่ได้ refresh token ใหม่ ส่งมาหลังจากนั้นถือว่าหลุด เซสชันนั้นสิ้นสุดทันทีและลง Activity Log เว็บเก็บ refresh token ใน cookie ที่ script อ่านไม่ได้ และเก็บ access token ในหน่วยความจำเท่านั้น ไม่ลง localStorage แอป mobile รับ refresh token ใน body และเก็บใน secure storage ของเครื่อง
- **เหตุผล:** token ที่ถูกขโมยใช้ได้ไม่นาน และการใช้ตัวเก่าซ้ำบอกได้ว่ามีคนอื่นถืออยู่ ส่วน 30 วินาทีกันไม่ให้ผู้ใช้หลุดเพราะเปิดหลายแท็บ
- **ถ้าผิด:** แก้ทีหลังได้ — กติกาอยู่ที่ endpoint ขอ token ใหม่จุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### AUTH-D32: access token ถืออะไร และเซ็นด้วยอะไร
- **คำตอบ:** เซ็นด้วยกุญแจลับของแต่ละ deployment จาก env `AUTH_JWT_KEY` ยาวอย่างน้อย 32 ไบต์ ไม่อยู่บนหน้าตั้งค่าและไม่อยู่ใน repo token ถือ id บัญชี พอร์ทัลเป็น audience id เซสชัน เวลาออกและหมดอายุ และสิทธิ์ที่เซสชันถือ (แพ็ก `permission`) ไม่ถืออีเมลหรือข้อมูลส่วนบุคคลอื่น API ไม่รับ token ของพอร์ทัลอื่น ของ deployment อื่น ลายเซ็นไม่ตรง หรือหมดอายุเกิน 30 วินาที โปรเจกต์ที่มีแอปเรียก API แต่ขาดกุญแจหรือกุญแจสั้นเกิน API ไม่ start
- **เหตุผล:** ใครก็อ่าน JWT ได้โดยไม่ต้องมีกุญแจ จึงต้องไม่มีข้อมูลส่วนบุคคล และ token ของพอร์ทัลหนึ่งต้องใช้กับอีกพอร์ทัลไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนกุญแจแล้วทุกคนเข้าระบบใหม่
- **ถามเมื่อ:** ไม่ถาม
