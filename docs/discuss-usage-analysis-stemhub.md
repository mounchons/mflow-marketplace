## 1. ข้อสรุป

1. **ไม่ควร discuss ทุกเรื่อง และไม่ควรข้ามทั้งหมด** ให้ตัดสินด้วยคำถามเดียวว่า "ถ้าเดาผิด ต้องแก้อะไร" เรื่องที่เดาผิดแล้วต้องแก้ schema, สิทธิ์, สิ่งที่ส่งออกไประบบภายนอกหรือส่งถึงลูกค้า หรือเรื่องที่ผู้ใช้จะใช้คำของตัวเองแทนเอกสารลูกค้า ควรถามผู้ใช้ก่อน ส่วนเรื่องอื่นให้ OpenSpec ตัดสินเอง แล้วตรวจตอน proposal
2. **คำแนะนำของ Claude ถูกเลือกส่วนใหญ่ แต่ข้อที่ผู้ใช้เลือกต่างกระจุกอยู่ในเรื่องที่แพง** มี decision ที่ตอบแล้ว 91 ข้อ ผู้ใช้เลือกต่าง 12 ข้อ (13%) และ 10 ใน 12 ข้อเป็นเรื่อง schema, สิทธิ์, ผลต่อระบบภายนอก หรือการใช้คำของผู้ใช้แทนเอกสารลูกค้า (F01)
3. **discuss ช่วยกันไม่ให้ Claude อ่านเอกสารผิด และช่วยให้ได้ข้อมูลที่ไม่มีในเอกสาร แต่กันไม่ได้ในกรณีที่ผู้ใช้เพิ่งรู้ว่าต้องการอะไรหลังได้ใช้จริง** งานแก้ใหญ่ที่สุด (CR-002, CR-003) เกิดขึ้นทั้งที่ discuss ที่เกี่ยวข้องอนุมัติไปก่อนสร้างแล้ว (F05)
4. **ต้นทุนจริงของ discuss อยู่ที่เวลาอ่าน ไม่ได้อยู่ที่การตอบ** มี 3 ฉบับที่ยาวเกินเพดาน ~200 บรรทัดชัดเจน และ `check` ไม่เตือนเรื่องความยาว (F06)
5. **ทาง "ให้ OpenSpec ตัดสินเอง" มีอยู่แล้วใน fast track แต่ไม่มีกฎบังคับ** การจดข้อสมมติทำได้เพราะผู้ใช้พิมพ์ไว้ใน prompt หรือเพราะ Claude ทำเป็นนิสัย ไม่ได้มาจาก `openspec/config.yaml` (F09)
6. ข้อเสนอที่ควรทำก่อนคือ P01 (ป้ายบอกว่าถ้าผิดต้องแก้อะไร และการตอบรวมด้วย "ที่เหลือตามแนะนำ") กับ P02 (กฎใน `rules.proposal` ให้แสดงสิ่งที่ตัดสินแทนผู้ใช้ และถามเฉพาะข้อที่แพงก่อน proposal จะเสร็จ)

- `docs/manual-fast-track.md` §5 ให้ผู้ใช้ใส่ข้อความนี้ใน prompt ของ `/opsx:propose`: "กฎที่ยังไม่รู้ให้เลือกค่าที่สมเหตุสมผล เขียนเป็นข้อสมมติใน proposal และรวมเป็นรายการ 'คำถามตอนทดสอบ'" ข้อความนี้อยู่ใน prompt เท่านั้น
- `LINES` ใน `plugins/mflow/scripts/openspec-config.mjs` ไม่มีบรรทัดที่ให้จดสิ่งที่ตัดสินแทนผู้ใช้
- change `supplier-screens` ใน StemHub ก็ทำแบบนี้อยู่แล้ว (design D1/D6/D7 เปลี่ยนระหว่าง apply และบันทึกไว้ใน design พร้อมทำเครื่องหมาย "Import อยู่ใต้เมนู More ขณะที่ UAT S15-01 บอกว่ามีปุ่ม Import" ให้ผู้ใช้ยืนยันตอนใช้งาน) วิธีนี้ได้ผลกับเรื่องระดับ UI แต่เกิดจากนิสัยของ Claude ไม่ได้เกิดจากกฎ
- ตาราง "ไม่เหมาะกับ" ใน fast track §1 มีเรื่องเงิน กฎหมาย และสิทธิ์ที่ซับซ้อนมาก แต่ยังไม่มีเรื่องที่ "เขียนไประบบภายนอก" และ "ผู้ใช้จะใช้คำของตัวเองแทนเอกสารลูกค้า"

## 4. เกณฑ์เลือกระหว่าง discuss กับการให้ OpenSpec ตัดสินเอง

ถามว่า "ถ้าเดาผิด ต้องแก้อะไร" แล้วเลือกตามตารางนี้:

| ถ้าเดาผิดต้องแก้ | ทางที่ควรใช้ | หลักฐาน |
|---|---|---|
| schema, key, ตาราง, ความสัมพันธ์ | ถามผู้ใช้ก่อนสร้าง (discuss หรือถามตอน propose) | 06 D1, 07 D1, 04 D3 |
| สิทธิ์และขอบเขตข้อมูล | ถามก่อนสร้าง | 01 D4, 01 D6 → CR-001 |
| สิ่งที่เขียนไประบบภายนอกหรือส่งถึงลูกค้า (ลบไฟล์, สถานะใน DMS, อีเมล, บัญชี, รหัสผ่าน) | ถามก่อนสร้าง | 05 D1, 13 D1/D4/D5, 16 D1 |
| เอกสารลูกค้าไม่ได้พูดถึง พูดขัดกัน หรือผู้ใช้รู้มากกว่าเอกสาร | ถามก่อนสร้าง เพราะทางข้ามจะตาม SRS เสมอ | 03 D3, 16 D1, 16 D6 |
| UI, label, layout, template, filter, หรือเรื่องที่ตามแบบที่อนุมัติไปแล้ว | ให้ OpenSpec ตัดสิน แล้วตรวจที่ proposal และตอนทดสอบใช้งาน | doc 09, 10, `supplier-screens` |
| ขอบเขตงานที่ตัดออกแล้วเพิ่มทีหลังได้ | ให้ OpenSpec ตัดสินได้ | 16 D6 |
| flow ที่ขึ้นกับพฤติกรรมของระบบภายนอกที่ยังไม่เคยเห็นของจริง | spike กับของจริงก่อน แล้วค่อย discuss (สมมติฐาน รอทดลอง) | CR-002, CR-003 |

**ทดสอบเกณฑ์กับ doc 16:** ก่อนรู้คำตอบ เกณฑ์นี้บอกว่าควรให้ผู้ใช้อ่าน D1, D3, D7 และรับตามแนะนำได้ใน D2, D4, D5, D6
- ผลจริง: D1 ได้ตัวเลือกใหม่ d, D3 ได้เงื่อนไขเพิ่มที่ต่อมาถูกกลับคำ, D7 ตามแนะนำ
- ในกลุ่มที่บอกว่าปลอดภัย มี D6 ที่ผู้ใช้เลือกต่าง แต่เป็นการตัดขอบเขตซึ่งแก้ทีหลังได้ถูก
- ในตัวอย่างเล็กนี้เกณฑ์ไม่พลาดข้อที่แพง แต่สิ่งที่สำคัญกว่าคะแนนคือ D8–D11 ไม่มีอยู่ในร่างแรก เกณฑ์ใดก็คัดข้อที่ยังไม่มีไม่ได้ ต้องคุยถึงจะเกิดขึ้น

**ถ้าข้าม discuss ให้ตรวจที่ proposal ไม่ใช่ตอนโค้ดเสร็จ** ใน StemHub การแก้หลังสร้างต้องทำ migration, sync spec, archive และรัน full suite ประมาณ 40 นาที และสมมติฐานที่ฝังในโค้ดจะมองไม่เห็นถ้าไม่ได้จดไว้

### P01 — ป้าย "ถ้าผิด" ต่อ decision และการตอบรวม "ที่เหลือตามแนะนำ"

- **ทำอะไร:**
  - ทุก `### D<n>` มีบรรทัด `**ถ้าผิด:**` บอกว่าแก้ทีหลังได้ใน change เดียว หรือต้องแก้ schema, สิทธิ์, ระบบภายนอก, สิ่งที่ส่งถึงลูกค้า หรือเป็นการใช้คำของผู้ใช้แทนเอกสาร
  - หัวข้อ "วิธีตอบเอกสารนี้" เพิ่มคำตอบแบบ `/mflow:discuss NN D1 d, ที่เหลือตามแนะนำ`
  - revise mode จะใส่ตัวอักษรที่ Claude แนะนำลงใน `**เลือก:**` ของข้อที่ยังเปิด พร้อมต่อท้าย `(ตามคำแนะนำ)` แล้วเพิ่มข้อที่ป้ายบอกว่าแพงลงในหัวข้อ 5 เพื่อดูตอนทดสอบใช้งาน
- **ไฟล์:**
  - `plugins/mflow/skills/discuss/SKILL.md`: new mode ขั้น 3 และ revise mode ขั้น 3
  - `plugins/mflow/skills/discuss/assets/discussion.md`
  - `plugins/mflow/templates/docs/decisions/discuss/README.md`
- **ข้อจำกัดที่ต้องรักษา:**
  - ยังเป็นคำตอบของผู้ใช้ เพราะผู้ใช้เป็นคนพิมพ์คำว่า "ที่เหลือตามแนะนำ" เอง (คำตอบของผู้ใช้คือคำสั่งของลูกค้า)
  - ห้ามใช้กับคำแนะนำของ AI tool อื่น เพราะ SKILL.md ห้ามเติม `**เลือก:**` จาก pick ของ tool
  - gate ของ approve ยังเหมือนเดิม
- **ผลที่คาด:** ผู้ใช้อ่านละเอียดเฉพาะข้อที่แพง (10 ใน 12 ข้อที่เลือกต่างอยู่ในกลุ่มนี้) และยังเหลือบันทึกเหตุผลไว้ทุกข้อ

### P02 — กฎ `rules.proposal`: แสดงสิ่งที่ตัดสินแทนผู้ใช้ และถามเฉพาะข้อที่แพง

- **ทำอะไร:** เพิ่มบรรทัดใน `LINES["rules.proposal"]` ของ `plugins/mflow/scripts/openspec-config.mjs` ร่างตามนี้:
  > List every choice the sources, approved discussion docs and hotspots leave open, with the option taken and why. Mark each one that changes a table or key, a permission or data scope, a write to an external system or a message sent to the customer, or that departs from a customer document. Ask the user about the marked ones before the proposal is final; the rest stand as questions for testing.
- **ข้อจำกัดที่ต้องรักษา:**
  - ถามที่ขั้น propose เท่านั้น ห้ามถามระหว่าง apply เพราะ `operations.apply.guidance` บอกให้ "implement every task yourself without pausing to ask"
  - ใช้ key `rules.proposal` ที่ `mergeList` รู้จักอยู่แล้ว อย่าเพิ่ม key `rules.design` จนกว่าจะตรวจว่า schema ของ OpenSpec config รองรับ
  - โปรเจกต์ได้กฎใหม่ผ่าน `/mflow:init` ซึ่งเก็บถ้อยคำของโปรเจกต์ไว้ตามกฎของ 0.27
- **ไฟล์อื่นที่ต้องแก้:**
  - `docs/manual-fast-track.md` §1: เพิ่มแถว "เขียนไประบบภายนอก" ในตาราง "ไม่เหมาะกับ"
  - `docs/manual-fast-track.md` §5: ข้อความเรื่องข้อสมมติใน prompt เหลือแค่ชี้ไปที่กฎ
  - test ของ `openspec-config` ใน `tests/`
- **ผลที่คาด:** ทางข้าม discuss ได้ข้อสมมติที่มองเห็นได้ทุกครั้ง และจับกรณีที่ผู้ใช้จะใช้คำของตัวเองแทนเอกสารได้ตั้งแต่ก่อนสร้าง

### P03 — เตือน task `ทดสอบใช้งาน` ที่ค้างอยู่

- **ทำอะไร:** เมื่อ `/mflow:review` หรือการ archive พบว่า change อ้าง discuss doc ใดอยู่ ให้แสดงชื่อ task `ทดสอบใช้งาน` ที่ ref ไปยัง doc นั้นและยังเป็น To Do พร้อมเกณฑ์ตรวจรับที่ยังไม่ติ๊ก เป็นการเตือนเท่านั้น ไม่ขวางงาน
- **ไฟล์:** `plugins/mflow/skills/review/SKILL.md` (ตรวจก่อนว่าขั้นสุดท้ายของ review เป็นจุดที่เหมาะที่สุดหรือไม่)
- **ข้อจำกัดที่ต้องรักษา:** ไม่สั่งให้รัน E2E เพราะการทดสอบใช้งานคือผู้ใช้ลองเอง

### P04 — `check` เตือนความยาว และมีตารางสรุป decision ที่ต้นเอกสาร

- **ทำอะไร:**
  - `discuss.mjs check` คืน `proseLines` (ไม่นับ code block และแถวตาราง) พร้อมคำเตือนเมื่อเกินประมาณ 200 บรรทัด ไม่ขวาง approve เหมือน `mermaidWarnings`
  - template มีตารางสั้นที่ต้นเอกสาร มีคอลัมน์ D, คำถาม, ถ้าผิด และ Claude แนะนำ ให้ผู้ใช้ตอบได้จากตารางเดียว
- **ไฟล์:**
  - `plugins/mflow/scripts/discuss.mjs`
  - `plugins/mflow/skills/discuss/assets/discussion.md`
  - test ของ discuss
- **ทำคู่กับ P01**

### P05 — flow ที่ผูกกับระบบภายนอก: spike ก่อน discuss (สมมติฐาน)

- **ทำอะไร:** agenda mode ใส่ "ควรคุยก่อน" ของหัวข้อ flow ที่เขียนไประบบภายนอกเป็น "หลัง spike กับระบบจริง ก่อน `/opsx:propose` หน้าจอชุดแรก"
- **สถานะ:** ยังเป็นสมมติฐาน หลักฐานมีแค่ F05 ซึ่งยังไม่รู้ว่ากฎใหม่รู้ได้ก่อนหรือไม่
- **วัดผลอย่างไร:** ลองกับโปรเจกต์ถัดไปที่มีระบบภายนอก แล้วนับ CR ที่เกิดจาก flow ของระบบนั้น

### P06 — consult

ไม่เสนอให้เปลี่ยนหรือตัดออก คำสั่งของ §11 ยังเป็นทางเลือกตามข้อจำกัดเดิม F08 ใช้เป็นข้อมูลสำหรับ pilot

## 6. คำถามที่ยังเปิด

1. กฎ `dms_status` (Draft/Update/Complete) ของ CR-002/003 รู้ได้ก่อนสร้างหรือไม่ ถ้ารู้ได้ F05 จะกลายเป็นหลักฐานว่าควร discuss flow ก่อน ไม่ใช่หลักฐานของ P05
2. ป้าย "ถ้าผิด" ของ P01 ควรให้ Claude ใส่เอง หรือให้ `check` ตรวจว่ามีครบทุกข้อ
3. P02 ควรใช้ทั้งทางเต็มและ fast track หรือเฉพาะ fast track เพราะทางเต็มมี discuss และ hotspot อยู่แล้ว
4. ควรอ่าน `docs/reviews/code/` ของ StemHub เพิ่มหรือไม่ ว่ามีข้อบกพร่องที่มาจากเรื่องที่ไม่ได้ discuss หรือไม่
