# shell: ข้อที่ตอบไว้แล้ว

### SHELL-D01: ระบบที่มีหลายพอร์ทัลใช้ layout อย่างไร
- **คำตอบ:** หนึ่ง layout ต่อ `{portal}` สร้างจาก UI kit ชุดเดียวกัน แต่ละ layout มีเมนู ชื่อระบบ และหน้าแรกของตัวเอง หน้าของพอร์ทัลหนึ่งไม่เปิดใน layout ของอีกพอร์ทัล หน้าเข้าระบบใช้ layout เข้าระบบที่ไม่มีเมนู หน้าสาธารณะ (ถ้ามี) ใช้ layout สาธารณะ
- **เหตุผล:** ผู้ใช้แต่ละกลุ่มเห็นเมนูและชื่อที่ตรงกับงานของตัวเอง แต่ทุกพอร์ทัลยังใช้ component และกติกาชุดเดียว
- **ถ้าผิด:** แก้ยาก — route เมนู และการ deploy ของทุกพอร์ทัลเปลี่ยนตาม
- **ถามเมื่อ:** ระบบมีมากกว่าหนึ่ง `{portal}` หรือมีหน้าสาธารณะที่เปิดได้โดยไม่เข้าระบบ
- **ตัวเลือกอื่น:** b) layout เดียวทุกพอร์ทัล ต่างกันแค่เมนูตามสิทธิ์ c) พอร์ทัลรองไม่มี sidebar ใช้เมนูบนแถบบนอย่างเดียว

### SHELL-D02: กรอบของหน้าจอเป็นแบบไหน
- **คำตอบ:** sidebar ด้านซ้ายกับ top bar ตาม `AppShell` ของ kit จอกว้างแสดงเมนูเต็ม จอกลางหดเป็นแถบไอคอน จอเล็กซ่อนเป็น drawer ที่เปิดด้วย ☰ หน้าจอเติมแค่พื้นที่หลัก ไม่สร้างกรอบเอง ชื่อแท็บ browser เป็น "ชื่อหน้า · `{app_name}`"
- **เหตุผล:** จอเล็กหรือหน้าต่างครึ่งจอยังใช้งานได้ และทุกหน้าจอได้กรอบเดียวกันโดยไม่ต้องเขียนเอง
- **ถ้าผิด:** แก้ทีหลังได้ — กรอบอยู่ใน layout จุดเดียว หน้าจอไม่ต้องแก้
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D03: เมนูผู้ใช้มีอะไร
- **คำตอบ:** มุมขวาของ top bar แสดงชื่อและ role ของผู้ใช้ กดแล้วเปิดเมนู: Profile (เมื่อพอร์ทัลนั้นมีหน้า Profile ตามแพ็ก users) และ Sign out ทุกหน้าที่เข้าระบบแล้วมี Sign out เสมอ
- **เหตุผล:** ผู้ใช้รู้ว่าเข้าระบบเป็นใคร และหาทางออกจากระบบได้ที่เดียวกันทุกหน้า
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มรายการในเมนูผู้ใช้ที่ layout
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D04: เมนูแสดงรายการไหนบ้าง
- **คำตอบ:** เฉพาะรายการที่ผู้ใช้ถือคีย์ View ของหน้าจอนั้น จากคีย์ที่แพ็ก permission ส่งให้หน้าจอตอนเข้าระบบ กลุ่มเมนูที่ไม่เหลือรายการถูกซ่อน ทุกรายการอยู่ในนิยามเมนูที่เดียวพร้อมคีย์ของมัน หน้าจอไม่เพิ่มเมนูเอง โครงเมนูและลำดับกลุ่มมาจากเรื่อง `navigation`
- **เหตุผล:** ผู้ใช้เห็นแค่สิ่งที่เปิดได้ เพิ่มหน้าจอใหม่แก้ที่เดียว และการซ่อนเมนูไม่ใช่การกันสิทธิ์ server ยังตรวจทุกคำขอ
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการแสดงผล คีย์และการตรวจฝั่ง server ไม่เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D05: หน้าจอสร้างจากอะไร
- **คำตอบ:** จาก component ของ UI kit เท่านั้น ความต้องการใหม่สร้างเป็น component ใน kit ก่อน แสดงทุกสถานะใน style guide แล้วจึงใช้ สี ขนาด และระยะมาจาก token ของ kit หน้าจอไม่มีค่าสีตายตัว inline style หรือ CSS ของหน้าเอง และมีการตรวจที่ล้มเมื่อพบ
- **เหตุผล:** ทุกหน้าหน้าตาและพฤติกรรมเหมือนกัน แก้ kit ครั้งเดียวทุกหน้าตาม และ agent สร้างหน้าใหม่ได้ตรงแบบ
- **ถ้าผิด:** แก้ยาก — หน้าที่ประกอบเองต้องรื้อทีละหน้าเมื่อ kit เปลี่ยน
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D06: หน้าจอเอาข้อมูลจากไหน
- **คำตอบ:** ผ่านชั้น server ชั้นเดียวที่ตรวจสิทธิ์และขอบเขตข้อมูล (API ของระบบ หรือ application service ชุดเดียวกันในเว็บที่ render ฝั่ง server) หน้าจอไม่เปิดฐานข้อมูลเอง browser ไม่เรียกระบบภายนอกตรง และไม่แสดงข้อความดิบจาก server
- **เหตุผล:** สิทธิ์และขอบเขตตรวจที่จุดเดียว หน้าจอไหนก็ข้ามไม่ได้
- **ถ้าผิด:** แก้ยาก — หน้าที่อ่านข้อมูลเองต้องย้ายมาผ่านชั้นนี้ทีละหน้า และอาจแสดงข้อมูลนอกสิทธิ์ไปแล้ว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D07: ป้ายบนจอเป็นภาษาอะไร
- **คำตอบ:** ป้าย หัวคอลัมน์ ปุ่ม และข้อความ แสดงสองภาษาในป้ายเดียว เรียงตาม `shell.label_order` ไม่มีปุ่มสลับภาษา ข้อความผิดพลาดจาก server แสดงทั้งสองภาษาเช่นกัน ข้อมูลที่ผู้ใช้กรอกแสดงตามที่กรอก
- **เหตุผล:** ผู้ใช้ไทยและต่างชาติใช้หน้าเดียวกันได้ ทดสอบชุดเดียว และไม่มีข้อความที่ลืมแปลซ่อนอยู่หลังปุ่มสลับ
- **ถ้าผิด:** แก้ยาก — ป้ายของทุกหน้าจอ ทุก component และข้อความผิดพลาดทุกตัว
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) ไทยอย่างเดียว c) ปุ่มสลับภาษาไทยและอังกฤษ จำภาษาไว้ต่อผู้ใช้

### SHELL-D08: เก็บและแสดงวันเวลาอย่างไร
- **คำตอบ:** เวลาที่มีชั่วโมงนาทีเก็บเป็น UTC และแสดงตามเขตเวลาของระบบ `shell.time_zone` เสมอ ไม่ว่า browser หรือ server ตั้งเขตเวลาไว้อย่างไร วันที่ล้วน (วันครบกำหนด วันเกิด) เก็บเป็นวันที่ ไม่แปลงเขตเวลา "วันนี้" นับตามเขตเวลาของระบบ
- **เหตุผล:** ทุกคนเห็นเวลาเดียวกัน เวลาใกล้เที่ยงคืนไม่เลื่อนวัน และย้ายเครื่อง server ได้โดยข้อมูลไม่เพี้ยน
- **ถ้าผิด:** แก้ยาก — เวลาที่เก็บเป็นเวลาท้องถิ่นไปแล้วแปลงย้อนให้ถูกทุกแถวไม่ได้
- **ถามเมื่อ:** ผู้ใช้อยู่หลายเขตเวลา หรือเอกสารลูกค้าให้แสดงตามเครื่องของผู้ใช้
- **ตัวเลือกอื่น:** b) แสดงตามเขตเวลาของ browser c) เขตเวลาต่อผู้ใช้ เก็บในบัญชี

### SHELL-D09: รูปแบบวันที่และปี
- **คำตอบ:** วันที่ตาม `shell.date_format` วันเวลาตาม `shell.datetime_format` (24 ชั่วโมง) ปีตาม `shell.calendar` รูปแบบอยู่ในโมดูลเดียวของ kit หน้าจอไม่จัดรูปเอง และไม่ใช้ locale ของ browser หรือ server ช่องกรอกวันที่รับรูปแบบเดียวกับที่แสดง ค่าที่ส่งให้ server เป็นรูป ISO
- **เหตุผล:** locale ไทยของ browser และของ server ใส่ปี พ.ศ. ให้เองโดยไม่บอก วันที่ในจอเดียวกันจึงปนสองแบบได้ถ้าไม่ล็อกรูปแบบ
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนที่โมดูลเดียว แต่เอกสารและไฟล์ที่ออกไปแล้วยังเป็นรูปแบบเก่า
- **ถามเมื่อ:** ทุกโปรเจกต์
- **ตัวเลือกอื่น:** b) DD/MM/YYYY ปี พ.ศ. c) YYYY-MM-DD ปี ค.ศ.

### SHELL-D10: รูปแบบตัวเลขและเงิน
- **คำตอบ:** คั่นหลักพันด้วยจุลภาค ทศนิยมด้วยจุด เงินมีทศนิยม `shell.money_decimals` ตำแหน่งและชิดขวา ไม่ใส่สัญลักษณ์สกุลเงินในช่อง (หัวคอลัมน์หรือป้ายบอกสกุล) ติดลบใช้เครื่องหมายลบนำหน้า การปัดเศษทำที่ server หน้าจอแค่แสดง
- **เหตุผล:** อ่านตัวเลขเทียบกันได้ทั้งคอลัมน์ และยอดที่แสดงตรงกับยอดที่เก็บ
- **ถ้าผิด:** แก้ทีหลังได้ — รูปแบบอยู่ในโมดูลเดียวของ kit
- **ถามเมื่อ:** ระบบมีหลายสกุลเงิน หรือมีจำนวนที่ต้องใช้ทศนิยมเกินสองตำแหน่ง เช่น ราคาต่อหน่วยหรืออัตราแลกเปลี่ยน
- **ตัวเลือกอื่น:** b) รหัสสกุลเงินหลังจำนวนทุกช่อง และทศนิยมตามสกุล c) ติดลบในวงเล็บแบบงานบัญชี

### SHELL-D11: ตารางรายการทำอะไรได้บ้าง
- **คำตอบ:** ทุกรายการเป็น DataTable ของ kit: แบ่งหน้าที่ server เลือกจำนวนแถวต่อหน้าจาก `shell.page_sizes` เรียงตามคอลัมน์ที่หน้าจอเปิดให้เรียง ค้นด้วยแผงตัวกรองเหนือตาราง ตัวกรอง การเรียง และหน้าอยู่ใน address มีสถานะกำลังโหลด ว่าง ไม่พบตามตัวกรอง และอ่านไม่สำเร็จพร้อมปุ่มลองใหม่ และบอกจำนวนทั้งหมดใต้ตาราง
- **เหตุผล:** ผู้ใช้เรียนตารางครั้งเดียวใช้ได้ทุกหน้า ฐานข้อมูลไม่ต้องส่งทุกแถว และแชร์ลิงก์ของหน้าที่กรองไว้ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็น component เดียวของ kit
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D12: กดแถวแล้วไปไหน
- **คำตอบ:** แถวเปิดหน้ารายละเอียดของระเบียนด้วยลิงก์ที่ใช้คีย์บอร์ดได้และเปิดแท็บใหม่ได้ รายการที่ต้องดูเร็วโดยไม่ออกจากหน้าใช้ quick view ของ kit แทน แต่ไม่ใช้ทั้งสองแบบในตารางเดียว แถวที่มีข้อมูลย่อยกางใต้แถวได้ด้วยปุ่มกาง กางแถวหนึ่งไม่ปิดแถวอื่น และหน้าใหม่เริ่มด้วยทุกแถวปิด
- **เหตุผล:** กดแถวแล้วได้ผลแบบเดียวกันทุกหน้า และลิงก์ของระเบียนส่งต่อให้คนอื่นได้
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยนที่ตารางของหน้านั้น
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D13: ตารางมีปุ่ม export ไหม
- **คำตอบ:** ไม่มีโดยค่าเริ่มต้น รายการใดมี export รูปแบบไหน และใครกดได้ เป็นคำตอบของเรื่อง `import-export-print` เมื่อมี export ไฟล์ใช้ตัวกรองและการเรียงเดียวกับที่เห็นบนจอ
- **เหตุผล:** ไฟล์ที่ออกไปแล้วควบคุมไม่ได้ จึงเปิดเฉพาะรายการที่มีคนต้องใช้จริงและมีสิทธิ์กำกับ
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่มปุ่ม export ให้รายการนั้นใน change ถัดไป
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D14: เลือกระเบียนหนึ่งรายการจากรายการยาวอย่างไร
- **คำตอบ:** รายการคงที่และสั้น (ไม่เกิน `shell.select_max` ตัวเลือก เช่น สถานะ ประเภท) ใช้ select รายการที่โตตามข้อมูล (ลูกค้า สินค้า ผู้ใช้) ใช้ช่องเลือก: ช่องแสดงชื่อที่เลือก ปุ่มเลือกเปิด dialog ที่ค้นและแบ่งหน้าจาก server เลือกได้หนึ่งรายการ ยืนยันแล้วใส่ช่อง ยกเลิกแล้วช่องคงเดิม ปุ่ม × ล้างค่า
- **เหตุผล:** select ที่โหลดทุกแถวช้าและหาไม่เจอเมื่อข้อมูลโต dialog เดียวกันใช้ได้ทั้งในฟอร์มและในตัวกรอง
- **ถ้าผิด:** แก้ทีหลังได้ — เปลี่ยน select เป็นช่องเลือกที่ฟอร์มนั้น
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D15: หน้ารายละเอียดแสดงประวัติอย่างไร
- **คำตอบ:** ส่วนสุดท้ายของหน้ารายละเอียดเป็นตารางประวัติจาก Activity Log ของระเบียนนั้น ใหม่สุดก่อน คอลัมน์ เมื่อ โดย การกระทำ สถานะ (ก่อน → หลัง เมื่อเปลี่ยน) และหมายเหตุ อ่านจาก server ทีละหน้า ไม่มีการเรียงแบบอื่นและไม่มีช่องค้น ทำคำสั่งบนหน้าแล้วอ่านหน้าแรกใหม่ อ่านไม่สำเร็จแสดงข้อผิดพลาดพร้อมลองใหม่ ไม่ใช่ "ยังไม่มีประวัติ"
- **เหตุผล:** ตอบได้ว่าใครทำอะไรกับเอกสารนี้โดยไม่ต้องไปจอ Activity Log และทุกหน้ารายละเอียดเหมือนกัน
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการอ่านจาก log ที่เก็บอยู่แล้ว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D16: ฟอร์มบอกข้อผิดพลาดอย่างไร
- **คำตอบ:** ป้ายของช่องแสดงเสมอ ช่องบังคับมีเครื่องหมาย * ข้อผิดพลาดแสดงใต้ช่องที่ผิด browser ตรวจช่องบังคับและรูปแบบก่อนส่ง แต่ server เป็นผู้ตัดสิน ข้อผิดพลาดจาก server ที่ระบุช่องลงใต้ช่องนั้น ที่ไม่ระบุช่องแสดงเป็นแถบบนฟอร์ม focus ไปช่องแรกที่ผิด และค่าที่กรอกไม่หาย
- **เหตุผล:** ผู้ใช้เห็นทันทีว่าต้องแก้ช่องไหน และกฎที่ตรวจได้เฉพาะ server (ค่าซ้ำ สถานะ) ก็ยังชี้ที่ช่อง
- **ถ้าผิด:** แก้ทีหลังได้ — อยู่ใน FormField ของ kit กับตัวแปลงข้อผิดพลาดจุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D17: ออกจากหน้าที่ยังไม่บันทึกได้ไหม
- **คำตอบ:** หน้าที่มีการแก้ค้างถามก่อนออก: กดเมนู breadcrumb หรือลิงก์ในหน้า ขึ้น dialog ยืนยันของ kit ยกเลิกแล้วอยู่หน้าเดิมพร้อมค่าที่แก้ โหลดใหม่หรือปิดแท็บได้คำถามของ browser ปุ่ม Back ของ browser ถามด้วยเมื่อ stack ทำได้ หน้าที่ไม่มีการแก้ออกได้ทันที
- **เหตุผล:** งานที่พิมพ์ไว้นานไม่หายเพราะกดเมนูพลาด และหน้าที่ไม่มีอะไรค้างไม่ถามให้รำคาญ
- **ถ้าผิด:** แก้ทีหลังได้ — ตัวกันอยู่จุดเดียวที่ทุกฟอร์มเรียกใช้
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D18: กดส่งซ้ำแล้วเกิดอะไร
- **คำตอบ:** ปุ่มที่กดแล้วขึ้นสถานะกำลังทำ และกดหรือ Enter ซ้ำไม่ได้จนได้คำตอบ ได้คำตอบแล้วปุ่มกลับมาตามผล server ยังกันการทำซ้ำของคำสั่งสำคัญตามกติกา API ของโปรเจกต์
- **เหตุผล:** คลิกสองครั้งหรือเครือข่ายช้าต้องไม่ได้เอกสารสองใบ
- **ถ้าผิด:** แก้ยาก — เอกสารซ้ำที่เกิดขึ้นแล้วต้องไล่ยกเลิกด้วยมือ
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D19: แจ้งผลอย่างไร
- **คำตอบ:** สำเร็จแสดง toast สั้นที่หายเองใน `shell.toast_seconds` วินาที ข้อผิดพลาดแสดงในหน้าตรงจุดที่เกิด (ใต้ช่อง บนฟอร์ม ในตาราง ใน dialog) ข้อผิดพลาดของคำสั่งที่ไม่มีที่แสดงในหน้า (เช่นปุ่มในแถว) ใช้ toast ที่ค้างจนผู้ใช้ปิด ข้อความมาจาก server ตามภาษาของ SHELL-D07 ไม่มี JSON รหัสภายใน หรือ stack trace
- **เหตุผล:** ข้อความสำเร็จไม่ควรขวางงาน ส่วนข้อผิดพลาดต้องอยู่จนผู้ใช้อ่านและแก้ได้
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นการแสดงผลของ component ใน kit
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D20: ทำสิ่งที่ย้อนไม่ได้ต้องยืนยันไหม
- **คำตอบ:** ต้องยืนยันใน dialog ที่บอกว่าจะเกิดอะไรกับรายการไหน ด้วยเลขหรือชื่อของรายการ ปุ่มยืนยันเป็นแบบอันตราย focus เริ่มที่ปุ่มยกเลิก ระหว่างทำกดยืนยันซ้ำไม่ได้ ทำไม่สำเร็จแสดงข้อผิดพลาดใน dialog การบันทึกปกติไม่ต้องยืนยัน
- **เหตุผล:** ผู้ใช้รู้ว่ากำลังลบหรือยกเลิกรายการไหนก่อนกด และ Enter ที่กดพลาดไม่ทำลายข้อมูล
- **ถ้าผิด:** แก้ทีหลังได้ — เพิ่ม dialog ให้คำสั่งที่ขาด
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D21: หน้าข้อผิดพลาดมีอะไรบ้าง
- **คำตอบ:** path ที่ไม่มีแสดงหน้า 404 ใน layout ของพอร์ทัลพร้อมลิงก์ไป `{start_page}` ข้อผิดพลาดที่ไม่คาดคิดแสดงหน้า 500 หรือแถบในส่วนที่พัง พร้อมเลขอ้างอิงของคำขอและปุ่มลองใหม่ ไม่มีรายละเอียดทางเทคนิค เครือข่ายขาดบอกว่าเชื่อมต่อไม่ได้ ไม่มีสิทธิ์ใช้แผง no-access ของแพ็ก permission ระเบียนที่ไม่พบหรืออยู่นอกขอบเขตแสดง "ไม่พบรายการ" แบบเดียวกัน
- **เหตุผล:** ผู้ใช้ไม่เจอหน้าขาวหรือข้อความดิบ และเลขอ้างอิงช่วยทีมหา log ของคำขอนั้นได้ทันที
- **ถ้าผิด:** แก้ทีหลังได้ — หน้าข้อผิดพลาดอยู่ใน layout จุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D22: เซสชันหมดระหว่างใช้งานแล้วเกิดอะไร
- **คำตอบ:** เซสชันแบบ token: access token หมดอายุไม่นับเป็นเซสชันหมด แอปขอ token ใหม่แล้วทำคำขอซ้ำเอง คำขอใดที่ server ตอบว่าไม่มีเซสชันหรือเซสชันหมด หน้าจอพาไปหน้าเข้าระบบของ `{portal}` นั้น พร้อม `next` เป็น path และ query ของหน้าที่อยู่ และบอกว่าเซสชันหมดเวลา เข้าใหม่แล้วกลับหน้าเดิมตามกติกา `next` ของแพ็ก auth ค่าที่กรอกค้างไม่ถูกเก็บ ไม่มีหน้าต่างเตือนก่อนหมด
- **เหตุผล:** ผู้ใช้กลับมาทำงานต่อที่หน้าเดิมได้ทันที ไม่ค้างอยู่กับหน้าที่เรียกข้อมูลไม่ได้
- **ถ้าผิด:** แก้ทีหลังได้ — ตัวดักคำตอบอยู่จุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D23: หน้า style guide มีที่ไหน
- **คำตอบ:** มีในเครื่องพัฒนา เครื่องทดสอบ และโหมด prototype แสดงทุก component ทุกสถานะ ไม่มีใน production: build ของ production ไม่มีหน้านี้ หรือ route ตอบ 404
- **เหตุผล:** ทีมและลูกค้าดูและตรวจ kit ได้ที่เดียว โดยคนนอกไม่เห็นหน้าที่มีข้อมูลตัวอย่าง
- **ถ้าผิด:** แก้ทีหลังได้ — เป็นเงื่อนไขของ build หรือ route จุดเดียว
- **ถามเมื่อ:** ไม่ถาม

### SHELL-D24: การเข้าถึงต้องได้แค่ไหน
- **คำตอบ:** พื้นฐานทุกหน้า: ทุกช่องมีป้ายผูกกับช่อง ใช้คีย์บอร์ดได้ครบ เห็น focus เสมอ dialog รับ focus และคืน focus เมื่อปิด สถานะไม่บอกด้วยสีอย่างเดียว คอนทราสต์ตัวอักษรอย่างน้อย `shell.text_contrast_min` ตาม token ของ kit ไม่รับรองระดับ WCAG ทั้งระบบ
- **เหตุผล:** ผู้ใช้ส่วนใหญ่ได้ประโยชน์ด้วยต้นทุนต่ำ เพราะเกือบทั้งหมดอยู่ใน component ของ kit
- **ถ้าผิด:** แก้ทีหลังได้ — แก้ใน component ของ kit แล้วทุกหน้าตาม
- **ถามเมื่อ:** เอกสารลูกค้าระบุมาตรฐานการเข้าถึง เช่น ระบบของหน่วยงานรัฐ หรือมีผู้ใช้ที่ใช้โปรแกรมอ่านหน้าจอ
- **ตัวเลือกอื่น:** b) WCAG 2.1 ระดับ AA ทั้งระบบ ตรวจด้วยเครื่องมือและคนทุกหน้าจอ พร้อมรายงาน

### SHELL-D25: รองรับ browser อะไร
- **คำตอบ:** `shell.browsers` รุ่นล่าสุด `shell.browser_versions` รุ่นบน desktop และ browser ของแท็บเล็ตหรือมือถือเมื่อเครื่องที่ kit รองรับรวมอุปกรณ์เหล่านั้น ไม่รองรับ Internet Explorer การทดสอบอัตโนมัติใช้ Chromium ส่วน browser อื่นตรวจด้วยมือก่อนส่งมอบ
- **เหตุผล:** browser รุ่นใหม่มีความสามารถที่ kit ใช้ครบ และการรองรับรุ่นเก่ามีต้นทุนทุกหน้า
- **ถ้าผิด:** แก้ยาก — รองรับ browser เก่าภายหลังต้องเปลี่ยน CSS และ script ของ kit ทั้งชุด
- **ถามเมื่อ:** เอกสารลูกค้าระบุ browser หรือรุ่น หรือเครื่องของลูกค้าล็อกรุ่น browser ไว้
- **ตัวเลือกอื่น:** b) Chrome และ Edge เท่านั้น สำหรับองค์กรที่คุมเครื่อง c) รุ่นเก่าที่ลูกค้าระบุ พร้อมบอกต้นทุนที่เพิ่ม
