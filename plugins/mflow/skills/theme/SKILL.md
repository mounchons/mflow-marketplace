A theme is the shared kit every screen is built from, the way a housing project picks one set of doors, tiles and switches for every house. Screens stay consistent because they can only be assembled from the kit: colors come from tokens, inputs and tables come from components, and nothing is styled inline.

Run this before the first `/mflow:screen`. Run `/mflow:theme update <what>` to change the kit; every screen follows automatically because none of them carry their own styles. `/mflow:theme update access` builds or refreshes only the access seams (step 3) from the current approved access-control discussion doc. That includes `users.json` and `roles.json`, which follow the schema-change rule once screens exist. Projects themed before mflow 0.5 need it before their next screen. `/mflow:theme update responsive` builds or refreshes only the responsive parts: the device question in step 1, the layout tokens in step 2, the `AppShell` in step 3, the "Narrow" lines of the components, and the style guide's layout section. Kits built before mflow 0.11 need it to get the ☰ menu and the reflowing pages. It first compares the existing shell and components with `AppShell` and the "Narrow" lines, lists only the gaps, and changes nothing before the user says yes. A kit that already complies only gets its Devices, acceptance-size and Breakpoints lines in design-system.md. `/mflow:theme update components` brings an older kit up to the current contracts: before mflow 0.14 the pager, optional header search, `DatePicker` and `DateRangeField`, and `Button`, `Card`, `Dialog`, `SidePanel`, `Alert`, `Tabs`, `Dropdown`, `Tooltip`, `Loading` and `DetailView`; before 0.21 `QuickView` and the `DataTable` icon column with its icon sets; before 0.23 the top bar's parts (search, notifications, scope chip, user), the optional bottom tab bar, the sidebar's groups and footer, and the breadcrumb's one home; before 0.24 a hue per status in each `StatusBadge` dictionary, the `DataTable` format `person` with its initials avatar, the KPI card's icon tile and the counter badges. The kit gains the components only: existing screens take them up through `/mflow:screen <name> <what>`. `/mflow:theme update date-picker` does only the date parts: it asks the date format (step 1), writes it to design-system.md, builds the two date components, and points `FormField` type `date` at them, so every screen follows. Both compare first, list only the gaps, and change nothing before the user says yes. Both also refresh `.claude/rules/ui.md` (the allowed-component list, the header-search line, the quick-view line, the hue line, the date line and the date-picker text exception) and `docs/ui/design-system.md` (the Quick view, Icon sets, Hues, Status colors and Date format decisions, the component table, the page patterns, and the quick-view and date lines under Do / don't) from the current assets, keeping what the project added. Before the header search becomes off by default, `update components` finds every column that shows a header search today, marks it `searchable` explicitly and names those screens in its gap list, so no existing screen loses its search row. `/mflow:theme update look` redoes the visual direction (step 1) on an existing kit, as [references/visual-direction.md](references/visual-direction.md) describes, with the `frontend-design` skill when it is listed; for a kit made before 0.23 that means moving it to the house style ([references/house-style.md](references/house-style.md)) with the customer's CI kept in the brand family, and for a kit made before 0.24 adding the house style's bright hues where color carries meaning (house-style.md, "Where color lives"). It changes only the tokens and the kit's stylesheet, adds the tokens an older kit lacks (before 0.21: `--app-sidebar-*`, `--app-font-heading`, `--app-radius-lg`, `--app-radius-pill`, `--app-shadow-float`, `--app-motion`; before 0.23: the text steps `--app-primary-text` and `--app-<tone>-text`, `--app-heading`, `--app-text-hint`, `--app-control-border`, `--app-control-height`, `--app-shadow-sm`, `--app-fs-*` and the new sidebar tokens; before 0.24: the hues `--app-hue-*` with their `-text` and `-subtle` steps, `--app-sidebar-bg-2` and `--app-shadow-md`, plus the kit's exact sidebar hover and shadows), and shows the style guide before and after; it changes nothing before the user says yes.

Stack: read AGENTS.md `## Stack`. If `## Stack` is missing (projects set up before mflow 0.10) or its profile is `TODO`, ask first, as "Asking" in `${CLAUDE_PLUGIN_ROOT}/skills/init/references/stacks.md` describes, and write the section before anything else. Paths and names below are for the `mvc-htmx` profile. Under another profile, use the matching rows of `## Stack` (tokens file, app shell, components, style guide, prototype-mode flag) and keep every contract.

## Where the kit is built

- **In the stack** (the default): steps 1 to 6 below.
- **As a static preview** (`/mflow:theme preview`): plain HTML, CSS and JavaScript in `docs/ui/theme/`, approved before the app exists, as [references/preview.md](references/preview.md) describes. Steps 1 to 6 still apply, with the differences listed there.
- **Port** (`/mflow:theme port`): builds the kit in the stack from the approved preview, then freezes the preview ([references/preview.md](references/preview.md), "Porting it").

Plain `/mflow:theme` when the app does not exist yet (the App shell path in `## Stack` is missing): ask first. Offer a) a static preview now, recommended while the app is not scaffolded, and b) scaffold the app first through `/opsx:propose`, then run theme in the stack. A letter is a full answer.

`/mflow:theme update <what>` follows the kit's current home. If `docs/ui/theme/README.md` says `draft` or `approved`, it edits the preview; `frozen` means the stack kit, and the frozen preview is never edited again.

## 1. Brand input

Collect in one batch: logo, primary color or the customer's CI guide (`$ARGUMENTS` may reference files), the look in the user's own words (default: a modern admin or back-office template), the app's feel (dense back-office vs. spacious), the Thai font preference, the target devices with their acceptance sizes ([references/responsive.md](references/responsive.md) §1), and the date format (`DatePicker` in [references/component-contracts.md](references/component-contracts.md)): a pattern, a) `DD/MM/YYYY` (recommended), b) `DD-MM-YYYY`, c) `DD.MM.YYYY` or d) `YYYY-MM-DD`, and the year, ค.ศ. (recommended) or พ.ศ. A letter and a year is a full answer. Then decide the visual direction as [references/visual-direction.md](references/visual-direction.md) describes, starting from mflow's house style ([references/house-style.md](references/house-style.md)) and adapting it through the `frontend-design` skill when the session lists it: the customer's CI goes into the brand family, and the hues, sidebar, type, icons and shape stay unless the user asks for a new look. The house style is bright and colorful on purpose (the user's choice): keep the hues as they are. If the customer has no CI, propose three directions rendered on the style-guide page and let the user choose. A customer mockup (HTML or screenshots in `docs/source/`) is the starting point when one exists: take its colors, type and density, and list every place the kit departs from it, such as filling the window instead of a fixed canvas, or adding icons the rail needs.

Done when: the look (the direction, with its primary color and font), density, target devices, acceptance sizes and the date format are decided, or the direction is explicitly delegated to the three-direction choice.

## 2. Tokens

Create `wwwroot/css/tokens.css` from [assets/tokens.css](assets/tokens.css), with the values of the visual direction: brand colors, semantic colors (success, warning, danger, info), the hues, surfaces, text, sidebar, radius and shadow scale, motion, spacing, font stacks, layout (sidebar and rail width, top bar and banner height, main padding, content max width, backdrop, touch target), plus the Bootstrap 5.3 variable overrides so native Bootstrap classes follow the brand. Include light values; add a dark block only if asked.

Done when: every color, radius and font used anywhere in the app resolves to a token.

## 3. App shell

`Views/Shared/_Layout.cshtml`, built to the `AppShell` contract in [references/component-contracts.md](references/component-contracts.md): `SidebarMenu` with its expanded, rail and drawer states, top bar (☰ toggle, page context, then the search, notifications, scope chip and current user the contract lists), the optional bottom tab bar when phones are among the devices, main area with page header slot, toast container, and the prototype banner partial with the role switcher, rendered when `Prototype:UseFakeData` is true. Write the breakpoints from [references/responsive.md](references/responsive.md) §2 into design-system.md Decisions, adjusted so that each acceptance size lands in the intended state. Load order: Bootstrap CSS → `tokens.css` → `app.css` (component styles only, token-based) → Bootstrap JS → HTMX.

The shell needs to know who is logged in, so build the access seams here, exactly as "Current user, permissions and the role switcher" in `${CLAUDE_PLUGIN_ROOT}/skills/screen/references/prototype-data.md` describes them. Files opened with Read are not substituted: where that file writes the plugin-root variable (CLAUDE_PLUGIN_ROOT), use `${CLAUDE_PLUGIN_ROOT}`. Take the roles, users and scopes from the approved access-control discussion doc. With none approved, use the single all-permission user it describes.

Done when: the style guide renders the `SidebarMenu` sample twice, each with an explicit permission-set stub, and the two show different items. When `users.json` holds more than one user, switching in the banner also changes who the top bar shows. At each acceptance size the sidebar is in the state the breakpoint table names, and ☰ and the drawer behave as `AppShell` describes. Started as Production with the prototype-mode flag on, the app refuses to start, and the negative tests in "Production safety" pass.

## 4. Components

Build every component in [references/component-contracts.md](references/component-contracts.md) as Razor partials or view components under `Views/Shared/Components/` (or tag helpers where noted). Follow each contract exactly; these contracts are what makes screens predictable for both people and agents. Put the date format in one config of the kit's format module, and turn the DatePicker's parser table into a unit test in the Unit tests project of `## Stack`.

Done when: each contract has an implementation, the style guide shows it (the DataTable pager at pages 1, 5 and 20 of 20, one table without header search, an icon column with each state, a `person` column with five different avatars, every status of each `StatusBadge` dictionary in its hue, a KPI strip, a `QuickView` open in a `Dialog` and one in a `SidePanel`, and the DatePicker in every state with its three calendar views), and the parser test passes.

## 5. Style guide page

`/_styleguide` (development and prototype only): every token swatch (the hues as a row of fill, text and tint), typography scale, every component in every state (default, hover/focus, disabled, error, loading, empty), a `SidebarMenu` sample with two items behind different permissions, rendered for two stub permission sets, a full sample list page (with an icon column whose icons open a section in a `Dialog`, and an eye action that opens the record in a `SidePanel`) and a sample form page assembled only from components (and a sample dashboard if the product has a home dashboard). Two sections open the page:
- **การตัดสินใจของ theme:** each decision (look and its bold place, palette and hues, font, density, devices and acceptance sizes, breakpoints, date format and year, departures from the mockup) with its source tag, as in discussion docs: `[ที่มา: …]`, `[ยืนยัน]`, `[เสนอ]`.
- **โครงหน้าและเมนู:** the page itself is the shell. Buttons force expanded, rail, auto-by-width and open-drawer, and a table gives window width → menu state → content layout, from design-system.md. A line next to them says "ลองย่อหรือขยายหน้าต่างดู".

This page is what the user approves once, for the customer, instead of approving colors screen by screen.

## 6. Rules for agents

- Write `docs/ui/design-system.md` from [assets/design-system.md](assets/design-system.md): which component for which need, the do-and-don't list, how to add a component.
- Write `.claude/rules/ui.md` from [assets/ui-rule.md](assets/ui-rule.md), setting `paths:` to the UI files row of AGENTS.md `## Stack`. It loads only when Claude opens a UI file.
- Add one pointer line to AGENTS.md under Conventions: `UI: build screens only from the components in docs/ui/design-system.md; colors and spacing only from tokens.css.`

Done when: the build command in AGENTS.md passes, the style guide renders and passes the checks in [references/responsive.md](references/responsive.md) §5 at the acceptance sizes in `docs/ui/design-system.md` (or reports them `(unverified)` as §5 allows), the three files above exist, the critique in [references/visual-direction.md](references/visual-direction.md) is done, and STATUS.md records the theme decisions (look, palette, font, density, devices, breakpoints, date format). **What comes next:** give the user the style guide's URL to approve the look, then one next command: `/mflow:screen inventory`, or a not-yet-approved agenda topic the screens depend on (`/mflow:discuss access-control`).
