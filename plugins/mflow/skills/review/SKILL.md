A review answers one question: does this diff do what the spec says, the way this project does things, with proof? It reports, then fixes its blockers and majors without asking (section 4); minors and nits wait for the user's word.

## Levels

How much review a change needs follows from the files it touched (`git diff --name-only` of the target). `/opsx:apply` writes the level into the change's row of `docs/reviews/pending.md`; the user's word decides.
- **full** (the default): the change touches business rules (domain or application code), permissions or data scope, queries, migrations or the data model, an integration with another system, or startup and dependency wiring. Every check below.
- **short** (`--short`): any other code change, such as a screen that only shows what the API sends, and a fix after a review, whose diff then starts at the commit the last report of the target reviewed (`Reviewed: … at <commit>`); for `fix/<change>-review`, the fix of a `pending` row, the diff is `git diff main...fix/<change>-review` and the findings are those of the row's report (`Reviewed: <change> <base>..<end>`). Checks 1 and 2 for what changed, each finding of that report marked fixed or still open, and checks 3–7 only on the changed lines.
- **skip**: only documents (Markdown, `openspec/`, `backlog/`, `docs/`, `STATUS.md`), stylesheets and tokens, or the text of labels (the diff changes no condition, query or data shape). No review: merge on the user's yes, with a passing `/mflow:test` record at the commit when anything but documents changed.

## 1. Scope the diff

- Branch: `git diff main...<branch>`; `--uncommitted`: working tree; change name: the commits and files of `node "${CLAUDE_PLUGIN_ROOT}/scripts/pending.mjs" range <name>`, which finds the change in `openspec/changes/<name>/` or, once archived, in `openspec/changes/archive/<date>-<name>/`; TASK-ID: the task's `modifiedFiles` and linked commits.
- `pending`: the changes in `docs/reviews/pending.md` that are already merged, reviewed after the merge. Run `pending.mjs status`; add each `missing` change first (`pending.mjs add <change> --level … --why … --applied <archive date>`, the level by "Levels" from the files of its range). Take the rows in list order whose Review is open, whose level is not skip and whose work `HEAD` holds (`landed: true`), or the one row named after `pending`. A row with `changes-requested` waits for its fix branch, which is reviewed as a branch. For each row: the diff is `pending.mjs range <change>` (`git diff <base> <end>`, its `codeFiles` for the checks; commits of other changes in that range belong to their own rows), the level is the row's, and the change's artifacts are read from its `folder`. Review one row at a time, each with its own report; when the context has grown large, stop after a finished report and tell the user to `/clear` and run `/mflow:review pending` again, which starts at the next open row.
- Leave out of the code checks the copy of mflow for the web, `.claude/skills/mflow/`: it is the plugin, written by `/mflow:init`, not the project's code.
- Load what the diff must satisfy: the change's `proposal.md`, `tasks.md` and delta specs; the Backlog task's acceptance criteria; AGENTS.md, including `## Stack` (if it is missing or its profile is `TODO`, ask first, as "Asking" in `${CLAUDE_PLUGIN_ROOT}/skills/init/references/stacks.md` describes, and write the section); `docs/ui/design-system.md` for view changes; the hotspot `rules.md` if it implements one.

## 2. Check

1. **Spec coverage:** each Scenario in the delta specs and each acceptance criterion has a test that exercises it. List any without one. Where the change lets one role set or send something another role or an outside party then sees or answers (an invitation, a questionnaire, a returned form, a decision such as approve, reject or withdraw), the specs need a Scenario for what the receiving side sees, matching what was set, and, when the receiving side is an outside party (a supplier, a customer), one for a second party of that kind seeing none of it. Where the change adds or alters a setting one role makes once (a system setting, a master list, a switch, a template) that changes what another role or web shows, the specs need a Scenario on the receiving side for each of its states (set and cleared, on and off), for whom it reaches when it reaches only some, and when it takes effect (a Scenario per setting, or a table of when each setting applies with a Scenario for each kind of timing). A missing one is a major finding, with the Scenario to add. A scenario that crosses the UI is covered by unit tests of the rules and services behind it; its E2E test is written per screen with `/mflow:e2e` when the user calls it, so a missing one is not a finding: name those screens in one line, `E2E on request: <screens>`.
2. **Tests:** for a `pending` row, the record in its Test column (a passing whole-suite or `since` run on a commit that holds the change, ticked by `/mflow:test`); cite it and do not run anything. A row whose Test is still open gets the verdict `none (tests not run)` unless the user says to run them now. Otherwise, proof of the whole suite at the reviewed commit, as `/mflow:test` defines it: the newest record in `docs/reviews/tests/` with `Tested: … at <the reviewed commit>`, no "with uncommitted changes", and `Scope: whole suite` or `Scope: since <base>`, whichever tool ran it (`By:` claude, codex or opencode; a record without `By:` was Claude's). Cite it (file, result, counts, and who ran it) and do not run it again. Without one, when a whole-suite record exists at an ancestor of the reviewed commit, run the "Since the last whole run" step of `/mflow:test` yourself and record it the same way; it usually takes minutes. Ask once only when that step needs the whole suite or there is no base, unless the review message already says which: a) run the whole suite now, the way `/mflow:test` does and recorded the same way (say how long the newest record took), or b) review the rest now and leave the tests to `/mflow:test`. `--uncommitted` runs the `since` step over the working tree; nothing can reuse that record. Report the actual output summary. A review never runs E2E tests.
3. **Domain placement:** business rules live in the domain layer (aggregates, value objects, domain services); controllers, views and repositories do not re-implement them. Invariants from rules.md are enforced where their owning aggregate is.
4. **UI kit:** views use kit components and tokens only; lists use DataTable with paging in the database query, the FilterPanel above the table, and header search only on columns marked searchable; a row's details open through `QuickView` and compared features through the icon column with a kit icon set; statuses, avatars, KPI tiles and category icons take their hues from the kit, never from the screen; dates go through `FormField` type `date` or `DateRangeField` (no `<input type="date">`, no date formatting in a screen) and reach the server as ISO `YYYY-MM-DD`; screen files hold no media or container queries, fixed widths or page-level grids; the changed pages pass at the acceptance sizes in `docs/ui/design-system.md` (§5 of `${CLAUDE_PLUGIN_ROOT}/skills/theme/references/responsive.md`: screenshots at those sizes, or an `/mflow:e2e` record of the page).
5. **Data access:** queries page and filter in the database, no N+1 in lists, migrations reversible. Entities, columns, types, precision and nullability match `PrototypeData/README.md` and the approved data-model doc, or the change states the difference; the indexes the doc lists for screen filters exist.
6. **Security basics:** a `Permissions` key checked on every endpoint that changes data, and on every read the access-control discussion doc restricts; data scope applied in the query, not the view, including each quick-view endpoint, which checks the list's view key and scope; restricted fields masked in the ViewModel mapping that exports reuse; no role-name comparisons (contract: "Current user, permissions and the role switcher" in `${CLAUDE_PLUGIN_ROOT}/skills/screen/references/prototype-data.md`); `FakeCurrentUser` and `/_prototype/*`, or their equivalents, registered only under the prototype-mode flag in AGENTS.md `## Stack` (`Prototype:UseFakeData` in the .NET profiles), with the startup check that refuses the flag outside a development or prototype environment and its negative tests ("Production safety" in the same file); no raw SQL built from input, no secrets in code or config.
7. **Leftovers:** `// PROTOTYPE:` markers still in code that this change was meant to replace; TODOs without a task.

Done when: every check has a result, with file:line for each problem.

## 3. Report

Write `docs/reviews/code/<date>-<target>.md` (`<date>-<change>.md` for a `pending` row): the commit reviewed (`Reviewed: <target> at <git rev-parse of it>`, plus "with uncommitted changes" for `--uncommitted`; for a `pending` row `Reviewed: <change> <base>..<end>` from its range, and `Change: <change>`), `Reviewer:` (claude, codex or opencode) and `Author:` (the tool that wrote the code: from the branch name `agent/<tool>/…`, else as the user says, `user` for their own code; when neither tells, ask in one line), the level (`Level: full` or `Level: short`, with the earlier report a short one follows), the test run it relies on (record path, or "run by this review"), verdict (`approve` / `changes-requested` / `none`), findings by severity (blocker, major, minor, nit) with location, problem, and fix. `approve` needs passing proof of the whole suite at the reviewed commit (a whole run there, or a `since` run there; for a `pending` row, the record in its Test column, on a commit that holds the change); when the tests were left for later and nothing else blocks, the verdict is `none (tests not run at <commit>)`. Blockers: failing tests, a scenario with wrong behaviour, a domain rule implemented outside the domain, missing authorization or data scope, prototype user switching reachable outside prototype mode, a prototype-mode flag that production could turn on without the app refusing to start. A review by Codex or OpenCode of code that the same tool wrote (Reviewer and Author name the same tool) is a self-review: write the verdict, but it never counts toward a merge; name a review by another tool as the next step.

For a `pending` row, and for a fix branch of one (it names the change in its report), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pending.mjs" tick-review <change> --report <report path> --verdict <verdict>`: it fills Review, and moves the row to `## Done` when Test is filled too.

**Checks in use.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/discuss.mjs" checks --change <name>` for the change the target builds (a branch or TASK-ID: the change its diff belongs to; none: skip this). It lists the `ทดสอบใช้งาน` tasks of the discussion docs the change cites that are not Done, with their unticked criteria. Put them in the report under `Checks in use:` (task, doc, each unticked criterion) and name them to the user: try them in the running system, then `/mflow:review-notes` ticks or reopens them. A reminder only: they never change the verdict or hold up a merge.

For a second opinion, offer `/mflow:delegate <target> --to <tool> --mode review`; when it returns, `/mflow:assess` checks its findings against this report.

## 4. Fix

When the report has blockers or majors, fix them now, without asking, so the review does not stop for a pick from its findings.
- **Where:** for a `pending` row, on a branch `fix/<change>-review` from `main`; for a branch target, on that branch; for `--uncommitted`, in the working tree, left uncommitted (it is the user's work in progress). The report, `docs/reviews/pending.md` and STATUS.md stay uncommitted while you fix: they come along when you switch branches, and a fix branch holds code only.
- **How:** each fix as its finding says, with the unit test that proves it. Run the build, every unit test and the tests the fixes added or changed, filtered to them, as `/opsx:apply` does after a task; the rest is `/mflow:test since`. Commit the fixes on that branch without asking, their files added by name (never `git add -A`), with a message that names the change and says review fixes. Then switch back to the branch you started on. For `pending`, fix each row right after its report, before the next row.
- **Left for the user**, each named in the reply: a finding whose fix needs a choice the specs, the approved designs in the discussion folder and the hotspots leave open (a business rule, a permission or data scope, what the customer or an outside party sees), as a numbered question with options a), b), c); a fix that needs a new table, screen or endpoint, as an `/opsx:propose` change; a failing test whose cause lies outside the diff. Minors and nits stay in the report, fixed only when the user says so.

**What comes next:** for `pending`, the next open row (`/mflow:review pending`), or nothing when none is left; on `changes-requested`, `/mflow:test since` on `fix/<change>-review`, where section 4 committed the fixes, then `/mflow:review fix/<change>-review --short`, whose approval settles the row. Otherwise: on `approve`, merge after the user's word (asked once, in one line), then `git diff --stat openspec/specs` (`/opsx:apply` archived the change; a change it did not archive takes `/opsx:archive` first), and the checks in use when any are open; on `changes-requested`, `/mflow:test since` on the fixed branch, then `/mflow:review <branch> --short`; on `none`, `/mflow:test`, then `/mflow:review` again, which reuses that run. Name what section 4 left for the user with it. Write it into STATUS.md `## Now`. Add one line on why it is next: what it unblocks, or which risk it settles. Then commit what the review wrote (the report, `docs/reviews/pending.md`, STATUS.md), added by name, on the branch you started on, without asking; push and merge only on the user's yes.

Done when: the report exists, its blockers and majors are fixed and committed or named to the user with the reason, STATUS.md records the verdict, what the review wrote is committed, and the user has the next command. A `pending` row is already on `main`, so its review merges nothing; its fix branch follows the rule that comes next. Merge only on `approve` (not a Codex or OpenCode self-review; Claude reviewing code it wrote counts as before) and the user's yes, and only while the target still points at the reviewed commit: an approval covers what was reviewed, so commits added since are reviewed first (`git diff <reviewed commit>..<target>`).
